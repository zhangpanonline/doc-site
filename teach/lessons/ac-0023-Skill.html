本课目标

完成本课后，你将能：

  1. 说清 Skill 要解决的问题——为什么把大段场景化提示词全部塞进系统提示词会导致「严重的提示词膨胀」

知识速览

先花几分钟把「为什么需要 Skill、Skill 长什么样、本章怎么把它接进 Agent」这条线过一遍——细节都在《23.Skill》里，测验和面试会考。

动机：提示词膨胀

  • 两个典型场景：SaaS 系统里用户「有时候」要销售数据分析，得告诉模型数据从哪来、字段什么含义、有哪些常见分析方式、结果怎么展现；智能客服系统里用户「经常」问产品，得告诉模型产品清单、参数、用法、价格、活动、购买链接、建议组合……
  • 直接后果：如果在系统提示词中完整地塞入这些内容，会导致严重的提示词膨胀
  • 关键观察：像这些提示词只有在某些场景下才会触发——「有时候」要数据分析、「经常」问产品，都不是每一轮都需要
  • 结论：用更优雅的方式完成提示词的注入。课件给的定义是——Skill 是一套可插拔的专业提示词模块，每个 Skill 对应一个特定场景（如处理越权提问、数据分析、客服应答等），只有当用户问题匹配该场景时，Skill 的内容才会被注入上下文，这种按需加载的机制避免了系统提示词的无限膨胀

SKILL.md 的结构：清单常驻，正文按需

  • 落盘位置：agent/.agents/skills/<技能名>/SKILL.md；本章有两个——自写的 no-permission（description：「当用户和你和开发无关的问题时，使用此技能」，正文是统一回复话术）与安装来的 frontend-design
  • 文件结构：文件开头是一段被 --- 包住的 YAML frontmatter（本章用到 name、description），紧跟 Markdown 正文
  • 清单进系统提示词：system.j2 的「## 当前可用的 Skill」小节只渲染 - **{{ skill_name }}**: {{ skill_meta.description }}——模型第一眼看到的是「技能名 + 一句话说明」，而不是全文
  • 正文按需加载：模型判断用户问题属于某个 Skill 描述的场景时，调用 use_skill 工具，加载后该 Skill 的完整指令追加到当前上下文，模型需严格遵守其中的要求
  • 一句话记忆：description 决定「什么时候想起来」，正文决定「想起来之后怎么做」

本章工程链路（新增 2 个文件、修改 3 个文件）

  • 新增 agent/tool/use_skill.py：SKILL_BASE_DIR = Path(__file__).parent.parent / ".agents" / "skills"；parse_skill_file 拼出 SKILL_BASE_DIR / skill_name / "SKILL.md"，不存在就 raise FileNotFoundError(f"未找到 Skill: {skill_name}")；再把内容按 "---" 切分、yaml.safe_load(parts[1]) 取 meta，最终 json.dumps 出 {meta, content, path}
  • 修改 agent/prompt.py：新增 list_skills()——遍历 SKILL_BASE_DIR 下的每个目录，读到 SKILL.md 就把 {技能目录名: meta} 收集起来；render_prompt 把它作为 skills 变量传给模板
  • 修改 agent/prompt/system.j2：用两层循环渲染清单——外层 {% for skill_item in skills %}，内层 {% for skill_name, skill_meta in skill_item.items() %}，所以模板层要配合 list_skills() 的「单键字典列表」形态
  • 修改 agent/tool/__init__.py：registry.register(use_skill)——技能工具和 read_file / write_file / bash_command / web_search / fetch_url 一样，注册后由 registry 统一导出 schema、解析模型返回的 tool_calls
  • 新增 agent/skills-lock.json：登记公共 Skill 的来源与完整性——source: "anthropics/skills"、sourceType: "github"、skillPath: "skills/frontend-design/SKILL.md"、computedHash: "4eabc661…"
  • 安装公共 Skill：npx skills add https://github.com/anthropics/skills --skill frontend-design（需要先装 node）；公共 Skill 可查 https://www.skills.sh/

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《23.Skill》覆盖的内容。

🌱 初级测验 · 概念

1. 课件开头用「SaaS 销售数据分析」和「智能客服产品知识」两个场景引出 Skill。这两个场景共同暴露的核心问题是？
课件原文：如果在系统提示词中完整地塞入这些内容，会导致严重的提示词膨胀；而实际上，像这些提示词只有在某些场景下才会触发——因此可以用更加优雅的方式完成提示词的注入。
2. 本章要求编写的 agent/.agents/skills/no-permission/SKILL.md，文件结构是？
课件里的 SKILL.md 正是这个形态：--- 之间是 name 与 description，下面跟着正文「统一回复：我是一个编程助手……」。本章 use_skill.py 也是按 "---" 切分后用 yaml.safe_load(parts[1]) 取这份 meta，同时把整份文件内容作为 content 返回。
3. 本章 agent/prompt/system.j2 的「## 当前可用的 Skill」小节，往系统提示词里注入的是什么？
模板里只有一层列表项：- **{{ skill_name }}**: {{ skill_meta.description }}。课件也把机制说明白了——「只有当用户问题匹配该场景时，Skill 的内容才会被注入到你的上下文中」，所以第一眼进入系统提示词的只能是清单，正文走按需加载。

🌿 中级测验 · 应用

4. 按本章 agent/tool/use_skill.py 的实现，use_skill("frontend-design") 会去读取哪个文件？
本章实现：SKILL_BASE_DIR = Path(__file__).parent.parent / ".agents" / "skills"，再拼 skill_name / "SKILL.md"；文件不存在就 raise FileNotFoundError(f"未找到 Skill: {skill_name}")。__file__ 是 agent/tool/use_skill.py，parent.parent 即 agent/——所以真正读取的永远是本地技能目录。skills-lock.json 里的 skillPath 只是「这份技能当初从哪来」的登记，不是运行时读取路径。
5. list_skills() 的返回值形如 [{"no-permission": {…}}, {"frontend-design": {…}}]。system.j2 为什么必须写成两层 for？
prompt.py 里是 skills.append({skill_dir.name: meta})——列表的每个元素都是一个「单键字典」。要在模板里拿到技能名与 description，就必须先迭代这个字典的 items()，所以 system.j2 写成 {% for skill_item in skills %} 里再套 {% for skill_name, skill_meta in skill_item.items() %}。
6. 把 no-permission 的 description 从「当用户和你和开发无关的问题时，使用此技能」改成「用于所有问题」。按本章机制推演，最可能的后果是？
进入系统提示词的只有「技能名 + description」，模型就是靠这份清单判断该不该加载——description 等于触发条件。课件里的测试用例 agent.invoke("最近天气如何？") 正是靠「和开发无关的问题」这句话命中 no-permission；把条件改成「所有问题」，拦截范围就从越权提问扩到全部开发问题。这也解释了为什么说写 Skill 时最该打磨的就是 name 与 description。

🎯 高级测验 · 综合

7. 同事写了个技能元信息解析器：parts = content.split("---")，meta = yaml.safe_load(parts[1]) if len(parts) >= 3 else {}。以下哪种情况会让它静默给出错误结果（不报错、但元信息丢了）？
规范要求的形态是「文件以 YAML frontmatter 开头」，而这段代码判断的是「按 --- 切出来至少三段」——两者并不等价：缺 frontmatter 时它不报错，只把 meta 悄悄变成 {}，于是 system.j2 的技能清单里少了一条触发线索。反过来，正文里出现 --- 只会多切出几段，parts[1] 仍是 frontmatter，所以那条「一定解析失败」不成立（真正会截断 frontmatter 的是 --- 出现在 frontmatter 内部）。而 yaml.safe_load 恰恰是更安全的选择——官方警告 yaml.load 与 pickle.load 一样能调用任意 Python 函数，不该用于任何外部数据，而第三方 SKILL.md 正是外部数据。更稳的写法：断言文件以 --- 开头、用 split("---", 2) 限定切分次数或换成熟的 frontmatter 解析器，并对必需字段做非空校验。
8. 团队给 Agent 装了 5 个技能，每个 SKILL.md 正文约 3000 字。为保证「模型一定遵守」，他们把 5 份正文全部拼进 system.j2。相比本章的按需加载，代价最准确的描述是？
课件对按需加载的定位很明确：「这种按需加载的机制避免了系统提示词的无限膨胀」。官方把渐进式披露拆成三级——启动时只预载每个 Skill 的 name 与 description（第一级），SKILL.md 正文在判定相关时读入（第二级），技能目录里被正文引用的附加文件再按需读取（第三级）；并指出带文件系统的 Agent「不必把整个技能读进上下文窗口」，因此可打包的上下文「effectively unbounded」。全部预载等于把第二、三级常驻化：既让每一轮都背上无关指令，也把这份「可插拔模块」重新变成膨胀的系统提示词。
9. 用 npx skills add https://github.com/anthropics/skills --skill frontend-design 装好技能后，工程里多了 agent/skills-lock.json，其中记着 source、skillPath 与 computedHash。关于这道「权限与信任边界」，说法正确的是？
课件把 Skill 定义为「可插拔的专业提示词模块」——插进来的正文会逐字进入模型上下文，它和代码一样有权限面。官方在安全一节说得很直接：恶意 skill 可能在使用它的环境里引入漏洞，或指使模型外泄数据、执行意外操作；建议只从可信来源安装，来源不够可信时先彻底审计，「特别注意代码依赖以及图片、脚本这类捆绑资源」，并留意技能里那些让模型连接不可信外部网络源的指令。skills-lock.json 的 computedHash 解决的是「装的是不是同一个版本」（可复现、可追溯、可对账），并不回答「这个版本是否安全」。
