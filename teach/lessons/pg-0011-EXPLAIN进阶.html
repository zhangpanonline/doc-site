EXPLAIN 进阶与查询优化

来源：官方文档 §14.1 使用 EXPLAIN（postgres.cn）非渡一课程内容预计 15–20 分钟9 道分级测验 + 4 道最终考核 + 面试实战

本课目标

完成本课后，你将能：

  1. 说出官方对查询计划与规划器的定位（计划选择对性能绝对关键）
  2. 用 EXPLAIN ANALYZE 做「估算 vs 实际」对照，定位规划器估错之处
  3. 解释官方注意事项：估算为何有偏差（随机样本统计 + 平台相关）
  4. 从「行数数量级对不上」判断统计信息过期并 ANALYZE 表

知识速览

先花几分钟把核心机制过一遍——细节与测验依据都来自官方文档 §14.1。

官方定位与工具

  • 每个查询产生一个查询计划；选择正确计划对性能绝对关键——系统内置复杂规划器（官方原文）
  • EXPLAIN：察看计划（估算成本与行数）；阅读查询计划是一门艺术（官方原文）
  • 输出格式：默认 text；程序分析用 XML/JSON/YAML 机器可读格式

EXPLAIN ANALYZE：估算 vs 实际

  • ANALYZE 选项：实际执行查询，显示每个计划节点真实行数与真实运行时间，同时保留估算值（官方原文）
  • 两相对照：(cost=... rows=10) 估算 vs (actual time=... rows=98000) 实测——估错一目了然
  • 官方注意事项：估算与行数略有不同是常态——ANALYZE 统计是随机样本不是精确值；成本依赖平台
  • 判断标准：看数量级——估算 10 行实际 10 万行 = 统计过期，该 ANALYZE 表

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与官方文档覆盖的内容。

🌱 初级测验 · 概念

1. 官方说选择正确的查询计划对性能意味着什么？
官方原文：选择正确的计划来匹配查询结构和数据的属性对于好的性能来说绝对是最关键的。
2. EXPLAIN 命令的作用是？
官方原文：你可以使用 EXPLAIN 命令察看规划器为任何查询生成的查询计划。
3. 官方说阅读查询计划是什么？
官方原文：阅读查询计划是一门艺术，它要求一些经验来掌握——但本节覆盖基础。

🌿 中级测验 · 应用

4. EXPLAIN ANALYZE 与普通 EXPLAIN 的区别是？
官方原文：EXPLAIN 实际执行查询，显示每个计划节点内累积的真实行数和真实运行时间，以及普通 EXPLAIN 显示的相同估算值。
5. 官方说估算成本与行数可能略有不同的原因是？
官方原文：ANALYZE 的统计信息是随机样本而不是精确值，并且成本本质上在某种程度上依赖于平台。
6. 想给程序分析 EXPLAIN 输出，官方建议用什么格式？
官方原文：把输出交给程序做进一步分析，应该使用机器可读输出格式（XML、JSON 或 YAML）；text 是给人读的。

🎯 高级测验 · 综合

7. EXPLAIN ANALYZE 显示估算 rows=10 但 actual rows=98000。这说明什么？
估算偏差几倍是常态，但数量级对不上（10 vs 10 万）就是统计过期——规划器依据错误统计选错计划，ANALYZE 表刷新统计。
8. 生产环境排查慢查询，直接跑 EXPLAIN ANALYZE 有什么风险？
ANALYZE 选项真的执行查询（官方原文）——生产上先普通 EXPLAIN 看计划，确认无副作用再上 ANALYZE。
9. 查询优化的标准流程（结合本课方法论）是？
官方方法论：先看规划器选了什么（EXPLAIN）、再看实际发生了什么（ANALYZE）、再决定干预——盲目加索引是反面教材。

最终考核

四道题覆盖本课全部要点——答完它们，EXPLAIN 进阶就过关了。

考核一：EXPLAIN 输出里 (cost=4.65..118.50) 两个数字分别是什么？
官方例（Nested Loop cost=4.65..118.50）：区间形式是启动成本..总成本——优化排序/首行延迟看前者，全量看后者。
考核二：官方文档的示例数据经过了什么处理？为什么？
官方原文：示例来自回归测试数据库，经过一次 VACUUM ANALYZE——统计新鲜计划才可信。
考核三：看到计划里的 Seq Scan 是否一定需要优化？
官方方法论是「对照数据属性」：小表或要读大部分行时顺序扫最快——计划好坏看匹配不匹配数据，不是看节点名字。
考核四：一个查询有时快有时慢（同一 SQL），EXPLAIN 相关的最可能原因？
同一 SQL 不同参数/统计变化 → 规划器可能切换计划（这正是 EXPLAIN 要观察的对象）——官方「选择正确计划」的难度就在这。
