模型接口契约

本课目标

完成本课后，你将能：

  1. 说出七种本地模型运行方案的定位差异，并解释为什么本章选 Ollama 作为默认入口
  2. 用一串 CLI 命令把本地模型跑起来：ollama pull / list / rm / show / run / ps，并看懂 http://localhost:11434/v1/ 这套 OpenAI 兼容接口
  3. 读懂一次调用的完整链路：.env → utils/config.py → OpenAI() → chat.completions.create() → resp.json 的字段结构
  4. 讲清流式响应里的 delta、推理与正文的「分车道」解析，以及视觉输入为什么要把图片转成 Base64 的 data URL

知识速览

先花几分钟把「本地模型 → OpenAI 兼容接口 → SDK 调用 → 流式/视觉」这条链路走一遍——细节都在《15.模型接口契约》里，测验和面试会考。

本地模型的七种打开方式

  • Pytorch + Transformers：主要用于本地训练、微调，也能推理，但需要自行适配硬件加速
  • Ollama：一键部署和运行开源大模型的命令行工具，内置量化支持和 GPU 加速——本章的主角
  • llama.cpp：高性能 C/C++ 推理引擎，主打 CPU 推理和多种量化方案
  • vLLM：高吞吐量推理框架，基于 PagedAttention 技术，适用于生产环境部署
  • MLX：Apple 官方 ML 框架，专为 Apple Silicon 设计的本地推理方案
  • LM Studio：带图形界面的桌面应用，一键下载和运行本地开源模型；LocalAI：提供 OpenAI 兼容 API 的本地推理服务，方便现有应用无缝切换
  • 一句话抓手：训练微调找 Transformers，命令行体验找 Ollama，压榨 CPU 找 llama.cpp，上生产要吞吐找 vLLM

从 .env 到 resp.json：一次非流式调用的全链路

  • 准备模型：ollama pull qwen3-vl 拉取模型，ollama list 看已下载，ollama show 看信息，ollama ps 看服务；访问 http://localhost:11434/ 确认服务在跑；可用 OLLAMA_MODEL_SERVER 环境变量换镜像源
  • 不写代码先测接口：curl http://localhost:11434/v1/models 列模型；curl -X POST .../v1/chat/completions 带 {"model":"qwen3-vl","messages":[...],"stream":false} 直接问一句
  • 装依赖：uv add openai==1.74.0 python-dotenv==1.2.2——SDK 负责协议，dotenv 负责把 .env 读进环境变量
  • 读配置：utils/config.py 用 os.path.dirname(os.path.abspath(__file__)) 推出模块上一级的 .env，load_dotenv() 后导出 OPENAI_API_KEY / OPENAI_BASE_URL / OPENAI_MODEL 三个常量
  • 建客户端：client = OpenAI()——不传参时，SDK 自己从环境变量取 key、base_url，所以本地 Ollama 用的是同一套代码
  • 发请求：client.models.list() 拿模型清单（.to_json() 看原始结构）；client.chat.completions.create(model=config.OPENAI_MODEL, messages=[{"role":"user","content":"你是谁"}]) 发起对话
  • 改非标准参数：关闭思考链要写 extra_body={"thinking": {"type": "disabled"}}；课件特别注明 qwen3-vl 无法直接关闭思考模式——不同模型的推理开关并不统一
  • 看返回：resp.json 里 choices[0].message 同时有 content（正文）与 reasoning（思考过程），另有 finish_reason；usage 给出 prompt_tokens / completion_tokens / total_tokens，满足 $total\_tokens = prompt\_tokens + completion\_tokens$

流式与视觉：把「打字机效果」和「看得见的输入」拆开

  • 开流式：create(..., stream=True) 之后得到的是可迭代的流对象，for chunk in stream 逐块消费；课件里还配了 sys.stdout.flush() 才能看到实时输出
  • 取文本的位置变了：非流式读 choices[0].message.content，流式要读 choices[0].delta.content——delta 里可能是一条 role 标记、一段 content，也可能是空的
  • 推理与正文分车道：utils/stream_resp.py 定义 @dataclass Chunk(type, content)，chunk_generator 用 is_on_reasoning 状态机把推理与正文分开，依次产出 reasoning_start → reasoning… → reasoning_end → content_start → content… → 最后固定一个 content_end
  • 两个兼容细节：推理文本先取 delta.reasoning_content，取不到再退回 delta.reasoning（课件注释写的是「为了兼容性，尝试获取两个字段的值」）；循环开头 if len(chunk.choices) == 0: continue 是为了跳过没有 choices 的帧，避免 choices[0] 直接越界
  • 渲染层：utils/stream_print.py 的 print_stream 按 chunk.type 打印提示语，推理用青色、正文用红色（ANSI 转义），每块都 flush
  • 视觉输入：utils/img_base64.py 的 to_base64 读文件并做 Base64 编码，to_dataurl 按扩展名推断 MIME，拼成 data:image/png;base64,...（认不出的扩展名退回 image/octet-stream）
  • 多模态消息：把 content 从字符串换成数组——[{"type":"text","text":"请描述这张图片的内容"}, {"type":"image_url","image_url":{"url":dataurl}}]，文本与图片是同一条 user 消息里的两个 part

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《15.模型接口契约》覆盖的内容。

🌱 初级测验 · 概念

1. 「一键部署和运行开源大模型的命令行工具，内置量化支持和 GPU 加速」——课件里这句话描述的是？
课件「本地模型」原文：Ollama——一键部署和运行开源大模型的命令行工具，内置量化支持和 GPU 加速。对照记忆：LM Studio 是带图形界面的桌面应用；llama.cpp 是 C/C++ 推理引擎、主打 CPU 推理与量化；vLLM 是高吞吐推理框架、基于 PagedAttention、面向生产部署。
2. 本地 Ollama 服务起来之后，本章用哪套地址测试它的 OpenAI 兼容接口？
课件「下载安装」：访问 http://localhost:11434/ 查看服务是否正在运行；测试接口用的就是 curl http://localhost:11434/v1/models 与 curl -X POST http://localhost:11434/v1/chat/completions。OpenAI 兼容路径统一挂在 /v1/ 下，端口是 Ollama 的默认 11434。
3. 开 stream=True 之后，想取这一块的正文文本，应该读哪个字段？
非流式的返回值里正文在 choices[0].message.content；一旦开流式，返回的是一个个 chunk，正文增量在 choices[0].delta.content（课件 utils/stream_resp.py：delta = chunk.choices[0].delta，再取 delta.content）。chunk.content、chunk.delta 都不存在——chunk 不是 delta 本身。

🌿 中级测验 · 应用

4. utils/config.py 里为什么用 os.path.join(os.path.dirname(os.path.abspath(__file__)), "../.env") 来定位 .env，而不是直接写 load_dotenv(".env")？
课件那三行就是干这件事：_current_dir = os.path.dirname(os.path.abspath(__file__)) → 拼出上一级的 .env → load_dotenv(_env_file)。这样配置的锚点是模块自身的位置，与「从哪个目录启动 Notebook / 脚本」无关；直接写相对路径时，换个工作目录就会静默读到 0 个变量，后面 OpenAI() 拿不到 key 才报错。注意它不负责加密，也不改变 dotenv 的参数规则。
5. 要把一张本地图片交给视觉模型，本章 to_dataurl + 消息组装的做法是？
课件「使用视觉能力」：dataurl = to_dataurl("menu.png")，消息里 content 变成数组——{"type": "text", "text": "请描述这张图片的内容"} 与 {"type": "image_url", "image_url": {"url": dataurl}} 两个 part。to_dataurl 内部先 base64.b64encode，再按 .png/.jpg/.jpeg/.gif/.webp 推断 MIME，兜底 image/octet-stream，最后拼成 data:{mime};base64,{...}。模型看不到你的本地磁盘，路径字符串对它没有意义；Base64 会把字节撑大约三分之一（$4 \times \lceil n/3 \rceil$ 个字符），这也是视觉请求更大的原因。
6. chunk_generator 取推理文本时，先试 delta.reasoning_content，取不到再退回 delta.reasoning。课件注释写的是「为了兼容性」——这个兼容性指的是什么？
课件那两行写得很直白：reasoning_content = getattr(delta, "reasoning_content", None)，if not reasoning_content: reasoning_content = getattr(delta, "reasoning", None)，注释是「推理内容，为了兼容性，尝试获取两个字段的值」。原因是思考文本属于各家扩展：OpenAI 兼容层只保证基础字段，推理字段名因服务端与模型而异（Ollama 的兼容文档也把推理控制描述成模型定义的取值）。所以工程上的稳妥写法是 getattr + 兜底，而不是假设字段一定存在——否则遇到叫另一个名字的服务端，思考内容会被静默丢掉。

🎯 高级测验 · 综合

7. 推演：某个模型这一次只输出正文、完全没有思考过程。chunk_generator 依次 yield 的 type 序列是？
看状态机的两个条件：reasoning_start / reasoning / reasoning_end 只在 reasoning_content 有值时才产出；content_start 只在「从推理切到正文」的那一次翻转里产出（if is_on_reasoning: 分支内）。一次都没进过推理，is_on_reasoning 始终是 False，所以只有一串 content 加循环结束后固定 yield 的 content_end。这也意味着渲染层不能假设 content_start 一定会来——只按「收到什么画什么」写，才不会漏字或错位。
8. 关闭思考链时课件写的是 extra_body={"thinking": {"type": "disabled"}}。为什么走 extra_body，而不是在 create() 里直接写 thinking={...}？
extra_body 的语义就是「把这份字典直接合并进请求 JSON」。它的价值在协议分层：model / messages / stream / tools 这些是契约内的字段，SDK 有类型与校验；而「关掉思考」这种能力不在 OpenAI 契约里——课件自己都注明 qwen3-vl 无法直接关闭思考模式，Ollama 兼容文档也把推理控制列为由模型定义的取值。凡是要用某家服务端的扩展能力，就该走扩展通道，并且清楚这段代码换模型后可能失效（本地模型与云模型混用时，这类参数是最典型的「换供应商即失效」依赖）。
9. 产品要求「边出字边展示，并且这次请求结束后要把真实 token 用量写进日志」。用流式请求时，用量该怎么拿？
这正好把本课的两处细节接在一起。① 拿用量：按官方 Cookbook 对 stream_options={"include_usage": True} 的说明，会额外流出一个作为收尾的 chunk——「除最后一个 chunk 外，所有 chunk 的 usage 字段都是 null」，而「最后一个 chunk 的 choices 字段永远是空数组」，全量统计在这个 chunk 的 usage 上。② 解析时不能崩：正是因为存在这种 choices 为空的帧，课件 chunk_generator 开头才写 if len(chunk.choices) == 0: continue——先跳过，再取 choices[0]。所以「加总每个 chunk 的 usage」拿到的是全 null，估算则会把答案变成猜的，重发一次非流式请求更是白白多算一遍钱。
