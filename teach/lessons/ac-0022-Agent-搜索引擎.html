Agent 搜索引擎

配合《22.Agent 搜索引擎》使用预计 15–20 分钟9 道分级测验 + 面试实战

本课目标

完成本课后，你将能：

  1. 说清 web_search 工具到底该把什么返回给 AI——为什么传统搜索引擎的页面不能直接喂给 Agent
  2. 复述本章列出的五个 Agent 专用搜索引擎，以及 Tavily 三类能力（search / extract / crawl）各自的输入与输出
  3. 读懂 agent/tool/web.py 与 agent/config.py 里 TavilySettings 的配合：环境变量前缀、@tool 装饰器、registry.register
  4. 走通「注册工具 → 模型发起 tool_call → registry 执行 → 结构化 JSON 回填上下文」的完整链路，并识别其中常见的静默失败点

知识速览

先花几分钟把「为什么要换搜索引擎、换完之后工具长什么样」过一遍——细节都在《22.Agent 搜索引擎》里，测验和面试会考。

问题的关键：web_search 该返回什么

  • 本章开篇就点题：问题的关键是，web_search 工具应该返回给 AI 什么调用结果？
  • 直接把传统搜索引擎的结果页（或被大量标签、样式、JS 代码污染的网页）交给 Agent，会踩一串坑：更多的 token 消耗、注意力被分散、很多 CSR 的页面无法得到内容、包含大量无关信息（广告图片、菜单、banner 等）、深层链接无法一次性获取
  • 结论：需要一个更适合 Agent 调用的搜索引擎——本章列了五个：Firecrawl、Tavily、AnySearch、Brave、Exa
  • 一句话记忆：Agent 要的不是「网页」，而是已经洗干净的、结构化的、带来源的结果

Tavily 的三类能力（本章用到的全部 API）

  • client.search(query="…")：用关键词搜索，返回结构化搜索结果——这是 web_search 工具的主体
  • client.extract(urls=[…], include_images=…)：给定 URL 数组，抓取网页内容——这是 fetch_url 工具的主体；本章集成版里显式写了 include_images=False，不要图片
  • client.crawl(url=…, max_depth=…, limit=…, instructions="…")：从根 URL 出发按深度与数量上限遍历站点，可以用自然语言 instructions 说明想找什么（课件示例：max_depth=3, limit=50, instructions="找到所有和网络相关的知识"）
  • 依赖与密钥：uv add tavily-python==0.7.26；API KEY 从 Tavily 官网获取后保存到环境变量，代码里经 tavily_settings.api_key 读取——绝不写进源码

集成进 Agent：从原理图到注册代码

  • 原理图（AI搜索原理）的链路：用户问题 → 模型（上下文 + 工具）→ 发起 web_search 工具调用 → 调用结果回填 → 进入 Reasoning / Acting 循环 → 得到普通回复 → 退出循环
  • 两个工具的定义（新增文件 agent/tool/web.py）：@tool(query="搜索关键字") 修饰 web_search、@tool(urls="要抓取的url链接数组") 修饰 fetch_url；装饰器里的说明就是给模型看的参数描述
  • 注册进 registry：registry.register(web_search)、registry.register(fetch_url)；agent/tool/__init__.py 里 from agent.tool.web import web_search, fetch_url 并完成注册
  • 返回值一定是字符串：两个工具都用 return json.dumps(response, ensure_ascii=False)——ensure_ascii=False 让中文原样输出，不转成 \uXXXX
  • 配置层新增：agent/config.py 加 TavilySettings（model_config = {"env_prefix": "TAVILY_"}，即读 TAVILY_API_KEY），本章 agent/ 变更 = 新增 1 个文件（tool/web.py）、修改 3 个（config.py、model.py、tool/__init__.py）、删除 1 个（分析.md）

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《22.Agent 搜索引擎》覆盖的内容。

🌱 初级测验 · 概念

1. 本章开篇提出的「问题的关键」是什么？
课件原文第一句：问题的关键是，web_search 工具应该返回给 AI 什么调用结果？后面列出的五个痛点（token 消耗、注意力分散、CSR 页面抓不到、无关信息、深层链接）都是在回答这个问题——所以才需要「更适合 Agent 调用的搜索引擎」。
2. 下列哪一项不属于本章列出的、更适合 Agent 调用的搜索引擎？
本章清单是 Firecrawl、Tavily、AnySearch、Brave、Exa 五个。选项 D 描述的正是本章要抛弃的东西——「内容被大量的标签、样式、JS代码污染」，它带来的恰是 token 消耗、注意力分散、无关信息这些被列出的问题。
3. 本章的 Tavily API KEY 存在哪里、由谁读取？
课件「获取 API-KEY」一节明确要求：将获取到的 API KEY 保存到环境变量。本章 agent/config.py 新增的 TavilySettings(BaseSettingsWithEnv) 里 model_config = {"env_prefix": "TAVILY_"}，配合基类从 .env 读取，所以工具里只写 TavilyClient(api_key=tavily_settings.api_key)。

🌿 中级测验 · 应用

4. 用户对 Agent 说「帮我查一查苹果最新发布了哪些产品？」。按本章的实现，最先被调用的是哪个工具、它拿到什么参数？
本章 fetch_url 的入参是 URL 数组（@tool(urls="要抓取的url链接数组")）——模型手里一开始并没有 URL，必须先由 web_search 用关键词检索出候选链接。这正是为什么本章要同时注册两个工具，也是原理图里第一跳是 web_search 的原因。
5. 本章的 fetch_url 用的是 client.extract 而不是 client.search，两者的分工是？
课件里三个 API 的入参一目了然：search(query=…) 吃关键词；extract(urls=[…]) 吃 URL 列表（示例一次传了两个百度百科链接）；crawl(url=…, max_depth=…, limit=…) 才是从根 URL 出发的站点遍历。所以 web_search 对应 search、fetch_url 对应 extract，D 描述的是 crawl。
6. web_search 的最后一行是 return json.dumps(response, ensure_ascii=False)。这个字符串最终去了哪里？
本章 agent/tool/__init__.py 的 _ToolRegistry.invoke 里，工具返回值被组装成 {"role": "tool", "tool_call_id": id, "name": name, "content": result}——也就是说工具结果以 tool 消息的形式回到会话，成为模型下一轮推理看到的上下文。这也解释了为什么两个工具都要返回字符串：content 字段承载的就是这段文本。（ensure_ascii=False 保证中文原样输出。）

🎯 高级测验 · 综合

7. 审查本章 _ToolRegistry.invoke 里的这段代码：tool = self._tools[name]，紧接着 result = ""、if not tool: result = "无此工具，请仔细检查你传递的工具名称是否正确"。当模型给出一个不存在的工具名（幻觉）时，实际会发生什么？
字典下标访问在键不存在时直接抛 KeyError，而 if not tool 只有在取值成功之后才有机会执行——索引不到时根本走不到那一行，所以这行兜底文案是死代码。用 .get(name) 才会得到 None，兜底分支才真正生效。这类「看着有容错、实际不生效」的写法在工具层很危险：Agent 一旦幻觉出工具名，整轮直接崩在异常上，而不是把纠错信息回给模型。
8. 假设把 agent/tool/web.py 里的 fetch_url 删掉，只留 web_search。这会带来什么后果？
两个工具是互补的：search 负责「按关键词找候选来源」，extract 负责「按已知 URL 取正文」，本章正是用 web_search + fetch_url 覆盖这两跳。只留检索，Agent 只能看到标题与摘要，遇到需要读细节的问题就答不实；只留抓取，模型无链接可抓——这与本章开头「深层链接无法一次性获取」的痛点呼应。注意二者是独立函数，少一个只是能力缺失，不会报错。
9. 用户问「苹果最新发布了哪些产品？」，模型连发 3 次 web_search、又抓了 5 个页面，最后把 Tavily 的完整响应 JSON（每条都带 raw_content、还开了图片）原样留在会话里。这个做法的主要问题是什么？
本章把传统搜索的第一条罪状就列为「更多的 token 消耗」，第二条是「注意力被分散」；换成 Tavily 只是让结果更干净，并不等于可以把 raw_content 整页正文和各种附加字段统统塞回上下文。工具结果在会话里是累积的：多轮检索后，噪声会一直占着窗口，还会把真正相关的几条结果淹掉。本章集成版 extract(..., include_images=False) 的思路就是「只拿我要的字段」——需要正文时再按需抓取、并只回传必要片段。
