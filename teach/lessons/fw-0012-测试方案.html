知识速览

先花几分钟把核心机制过一遍——细节都在《12.测试方案》里，测验和面试会考。

五层测试选型（课件）

  • 单元（unit/）：屏蔽外部，测单函数/类——复杂重要的代码
  • 集成（integration/）：多模块交互——核心，覆盖率的主力
  • 系统（e2e/system）：真实运行系统启动验证，happy path
  • e2e：一个用例跑完整个业务功能链——主要功能链必做
  • 冒烟：底线/红线/生命线，未通过 = 灾难性事故（五条判定）

Stub 与 Mock

  • Stub：固定返回的替身（SmsServiceStub 永远返回 999999）——只关心「不真发短信」
  • Mock：可验证的替身——调用次数/参数/顺序、side_effect 多返回值、抛异常、调用记录、reset
  • 课件结论：绝大部分情况下 Mock 可以平替 Stub
  • 冒烟标记：@pytest.mark.smoke 一行即可；覆盖率门禁 --cov-fail-under=80

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《12.测试方案》覆盖的内容。

🌱 初级测验 · 概念

1. TLD 和 TDD 的区别是？
课件：TLD = Test-Last Development（开发先行，测试后行）；TDD = Test-Driven Development（测试先行，开发后行）。新功能两者选一（开发日常第 1 条）。
2. 冒烟测试在课件里的定位是？
课件原文：冒烟测试是系统的底线/红线/生命线，冒烟测试未通过可视为灾难性事故。且往往不针对新功能，而是已上线、稳定运行一段时间的旧功能。
3. 测试覆盖率怎么算？
课件定义：测试覆盖率 = 运行所有测试用例执行到的代码 / 全量的代码。有些团队硬性要求 80% 否则无法 PR（课件 Makefile --cov-fail-under=80）。

🌿 中级测验 · 应用

4. 「登录接口」这种挂掉用户就进不来的功能，属于哪条冒烟红线？
课件五条红线第一条：登录挂了→用户进不来；下单挂了→收不到钱；支付回调挂了→钱付了但订单没更新。核心任务链路的功能必须冒烟。
5. Stub 模式里 monkeypatch.setattr("app.services.sms.SmsService", SmsServiceStub) 干了什么？
课件 Stub 示例：SmsServiceStub.send_verify_code 固定返回 {"code": 999999}——测试里不真发短信，login 业务逻辑照跑，断言拿到的就是桩返回值。
6. Mock 比 Stub 多出的核心能力，课件表格第一条是？
课件七大能力表：验证调用次数（assert_called_once）、验证参数（assert_called_with）、调用顺序（assert_called_before）、动态返回（side_effect）、抛异常、调用记录（call_args_list）、重置（reset_mock）。

🎯 高级测验 · 综合

7. 「获取用户 Token 是所有需要登录接口的前提」属于哪条冒烟红线？
课件第三条：获取用户 Token 是所有需要登录接口的前提，它挂了后面几十个接口都测不了——前置依赖类功能必须冒烟。
8. 系统测试与 e2e 测试的区别是？
课件选型表：系统测试——测试整个真实运行的系统，验证真实环境启动是否会带来新问题，走 happy path 即可；e2e——在系统测试基础上测试某个业务功能链，一个用例跑完整个功能链。
9. 课件开发日常的顺序是？（第 3 步为什么排在提交前）
课件开发日常：① 新功能选 TLD/TDD → ② 新增/修改的测试通过 → ③ 冒烟测试通过 → ④ 可选覆盖率达标 → ⑤ 提 PR → ⑥ 进流水线。冒烟未通过 = 灾难性事故，必须修了才能提交。
