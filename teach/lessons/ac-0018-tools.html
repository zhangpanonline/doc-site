本课目标

完成本课后，你将能：

  1. 说清 Tool Calling 的分工边界——模型只产出「调用意图」，真正执行函数的是你自己的代码
  2. 复述工具描述的三层结构（type / function.name+description / parameters 的 JSON Schema），并说明它为什么能左右模型的选型
  3. 读懂本章 agent/events.py 与 agent/model.py 的事件流改造：EventEmitter 与 ReasoningBuilder / ContentBuilder / ToolCallsBuilder 三个构建器
  4. 走通「绑定工具 → 调用模型 → 解析 tool_calls → 执行 → 回填结果」的闭环，并说清其中的坑

知识速览

先花几分钟把「模型为什么需要工具、工具描述长什么样、流式事件怎么拼」这三件事过一遍——细节都在《18.tools》里，测验和面试会考。

为什么需要 Tool Calling：模型只会「文本进、文本出」

  • 能力边界：大模型只能处理输入得到输出，没有任何其他功能。读文件、执行命令、联网搜索这些事，模型都无法直接处理
  • 于是有了 Tool Calling：需要模型完成「文本输出之外的功能」时，就把工具描述交给模型，让它输出「要调用哪个函数、参数是什么」
  • 最关键的一条：模型不执行函数。课件原注：「get_weather 函数功能需由用户提供，模型本身不执行具体函数」；官方文档说得更直白——API 不会真的执行任何函数调用，执行是开发者的责任
  • 闭环四步：① 带上 tools 调模型 → ② 模型返回 tool_calls（finish_reason 为 tool_calls）→ ③ 你的代码执行函数、把结果作为 role: "tool" 的消息追加回上下文 → ④ 再次调用模型，让它基于工具结果生成自然语言回答
  • 本章的两个示例工具：read_file(filepath) -> str 与 write_file(filepath, content) -> None；文档字符串（docstring）是写工具描述时的现成素材

工具描述：模型能看到的「函数签名」

  • 外层固定："type": "function"，目前各家 API 只支持 function 这一种工具类型
  • 函数名：function.name，会影响模型输出结果，通常直接取函数名（官方约束：由 a-z、A-Z、0-9、下划线、连字符组成，最长 128 字符，且必须唯一）
  • 函数描述：function.description，自然语言描述功能，模型能理解——官方定义它「供模型理解何时以及如何调用该 function」。这是选型准确率的第一抓手，写「文件操作」这种含糊描述等于把选择权交给运气
  • 参数 schema：function.parameters 用 JSON Schema 描述，顶层 "type": "object" 固定；properties 逐项写 type + description；required 列出必填参数。read_file 要 ["filepath"]，write_file 要 ["filepath", "content"]
  • 参数描述要写清后果：课件的 content 描述是「要写入的内容，该内容会完全覆盖文件原本内容」——把破坏性行为写进描述，模型才会谨慎
  • 工具被放去哪：厂商通常把工具定义拼到系统上下文的末尾（课件展示了 # Tools / namespace functions 的注入形态）。这意味着工具定义每一轮都要随请求重发，成本随工具数量线性增长：
    $T_{\text{prompt}} = T_{\text{sys}} + \sum_{i} T_{\text{tool}_i} + \sum_{j} T_{\text{msg}_j}$

事件流：把「流式的一堆 delta」拼回一条完整消息

  • 为什么要它：流式响应里每块都是 delta 而不是 message；正文、思考、工具调用三路内容可能在同一次响应里交错下发，散在几百个 chunk 里
  • 事件清单：agent/events.py 用 Event 常量把事件定型——REASONING_START/REASONING/REASONING_END、CONTENT_START/CONTENT/CONTENT_END、TOOL_CALL_START/TOOL_CALL/TOOL_CALL_END、COMPLETE
  • 发布订阅：EventEmitter 用 @dataclass + _listeners: dict[str, list[Callable]]（default_factory=lambda: defaultdict(list)）实现 on(event, callback) 与 emit(event, **data)；Model 直接继承 EventEmitter，所以模型自己就是事件源
  • Builder 模式：Builder.emit(chunk) 每次取 chunk.choices[0].delta，按 _key_names(delta) 给出的字段名与起止事件名走「首块发 START 事件 → 后续块 append_value → is_end 为真发 END 事件并置 compoleted = True」这套流程
  • 三个构建器：ContentBuilder 管 content；ReasoningBuilder 用 _get_reasoning_field_name 兼容 reasoning_content / reasoning 两种字段名；ToolCallsBuilder 管 tool_calls
  • 工具调用最特殊：append_value 按 tc_delta.index 归位、不够长就补占位字典，再按字段累加——arguments 是分片下发的 JSON 字符串，要 +=；_normalize_tool_calls 把 SDK 对象统一压成 {"id", "type", "function": {"name", "arguments"}} 的字典，好让消息能进会话历史
  • 提前收尾：ReasoningBuilder.is_end 返回 bool(delta.content) or bool(delta.tool_calls) or super().is_end(chunk)——模型「先思考、再直接发起工具调用」时不会产出 content，只看 finish_reason 会让思考段一直不结束
  • 监听与打印：ModelPrinterListener 遍历 Event.__dict__ 里所有事件名逐个 model.on(...) 订阅，用 self.listening 开关一键静音（课件里 listener.listening = False 之后再发起那次写文件的调用）

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《18.tools》覆盖的内容。

🌱 初级测验 · 概念

1. 关于 Tool Calling 的分工，下面哪一句是对的？
课件原注：get_weather 函数功能需由用户提供，模型本身不执行具体函数。官方 Cookbook 也写着：API 不会真的执行任何函数调用，用模型输出去执行函数是开发者的责任。模型交付的是「调用意图」——函数名 + JSON 参数。
2. 绑定到 session.tools 的每个工具对象，骨架是怎样的？
课件原文："type": "function" 是固定值，function 里依次是 name（工具名称，会影响模型输出结果，通常为函数名）、description（自然语言描述函数功能，模型能理解）、parameters（参数的 schema 描述）。函数对象和纯字符串都无法让模型知道参数长什么样。
3. read_file 的参数 schema 里写了 "required": ["filepath"]，它的含义是？
课件把 required 注释为「必填参数」：read_file 必填 ["filepath"]，write_file 必填 ["filepath", "content"]。类型由 properties 里各自的 type 决定，两者是并列信息。

🌿 中级测验 · 应用

4. 你把 read_file 与 write_file 的 description 都写成「文件操作」，结果模型在只想读文件时频繁调用 write_file。按本章与官方文档，根因与修法是？
官方文档对 description 的定义是「function 的功能描述，供模型理解何时以及如何调用该 function」；本章课件也注明它「自然语言描述函数功能，模型能理解」。工具选择靠的就是名字 + 描述 + 参数说明这几段文本，含糊描述会直接劣化选型准确率。required 管的是参数是否必填，与「选哪个工具」无关。
5. 取到 tool_calls[0]["function"]["arguments"] 之后，为什么要先 json.loads？
课件执行工具一节就是这条路：tool_name = tool_calls["function"]["name"]、arguments = json.loads(tool_calls["function"]["arguments"])。官方 API 文档把 arguments 定义为「要调用的 function 的参数，由模型生成，格式为 JSON」的字符串字段；直接 ** 展开字符串会报 TypeError: argument after ** must be a mapping。
6. 模型返回 {"filepath": "a.md", "content": "x", "encoding": "utf-8"}，而 write_file 的签名是 (filepath, content)。直接 func(**arguments) 的后果与应有的防线是？
关键判断：模型的输出是「建议」，不是「可信输入」。官方 API 文档在 function.arguments 字段下的原话就是「模型并不总是生成有效的 JSON，并且可能会臆造出你函数模式中未定义的参数。在调用函数之前，请在代码中验证这些参数」。用 **kwargs 全盘接收等于放弃校验，把不可信参数直接带进业务逻辑。

🎯 高级测验 · 综合

7. ToolCallsBuilder.append_value 必须按 tc_delta.index 归位再累加。为什么不能直接 += 到第一个工具上？
本章代码给了两处线索：while len(tool_calls) <= idx: tool_calls.append({...占位...}) 说明 index 是「第几个工具调用」；tc["function"]["arguments"] += args 说明参数是分片拼接的。官方 Cookbook 也确认「较新的模型可以在一轮里调用多个函数」（并行函数调用）。一旦交错到达的片段被错误合并，json.loads 就会在解析处炸掉——而这是 Agent 里最常见的「诡异 JSON 报错」来源之一。
8. 读 ReasoningBuilder.is_end：它为什么返回 bool(delta.content) or bool(delta.tool_calls) or super().is_end(chunk)，而不只用基类那套 finish_reason 判断？
基类 is_end 只看 chunk.choices[0].finish_reason，而它是整条流最后才出现的信号。思考模式下的典型轨迹是「思考 → 直接给 tool_calls」，中间没有正文；ReasoningBuilder 于是把「正文开始」或「工具调用开始」都当作思考结束的界标。兼容字段名的活由 _get_reasoning_field_name 干，两者是不同层的职责。
9. 生产 Agent 里照抄课件的 func = globals().get(tool_name) + if callable(func): func(**arguments) 做派发，最大的风险与改法是？
先用 globals().get() 再 callable 判断，意味着查不到时什么都不发生——工具调用被静默吞掉，比报错更难查。而「名字来自模型」这件事本身就把执行面暴露了出去。课件用 globals() 是为了在 Notebook 里演示闭环最短路径；工程化的正确答案是显式注册 + 白名单派发 + 参数校验——这正是下一章《19.封装tools》要解决的问题。
