知识速览

先花几分钟把核心机制过一遍——细节都在《05.事务》里，测验和考核会考。

转账为什么需要事务

UPDATE B 加 100 ─ 若第二步失败 ─▶ 只加不减 = 凭空多 100
BEGIN → 两步 UPDATE → COMMIT ─ 要么全成功 ─▶ 总金额恒为 1500
任何一步出错 → ROLLBACK ─ 要么全失败 ─▶ 回到 500 / 1000

⚙️ 事务 = 一组操作打包成「不可分割」的整体：全成功（COMMIT）或全撤销（ROLLBACK）。

ACID 一句话记忆

  1. A 原子性：要么全成功、要么全回滚，不存在做一半。
  2. C 一致性：事务前后数据都满足约束（总金额不变、余额 ≥ 0）——是最终目的，另外三个特性都为它服务。
  3. I 隔离性：并发事务互不干扰「应该」——注意「应该」二字，实际由隔离级别决定能隔离到什么程度。
  4. D 持久性：COMMIT 后永久生效，断电也不丢。

并行问题 × 隔离级别矩阵（PG 版）

               脏读   不可重复读   幻读   更新丢失
READ COMMITTED   ❌     可能       可能    可能     ← PG 默认，够用
REPEATABLE READ  ❌      ❌         ❌     可能     ← 快照实现，PG 防幻读
SERIALIZABLE     ❌      ❌         ❌      ❌      ← 抢购/库存扣减

PG 没有 READ UNCOMMITTED（设置了也按 READ COMMITTED 处理）

记忆点：不可重复读 = 同一条数据被改（UPDATE/DELETE）；幻读 = 数据集多了/少了行（INSERT）。隔离级别越高，并发性能越差。

分级测验

三道一组，先做后点——点击选项立刻出对错与解释。

🌱 初级 · 概念

1. 事务（Transaction）是什么？
事务 = 打包执行的一组操作，全成功或全失败。转账案例：加款与扣款两步必须同时生效或同时撤销，否则钱会凭空多出来。
2. 事务中执行了修改，最后执行 COMMIT 的作用是？
COMMIT = 提交：事务内所有修改永久生效、对其他事务可见。ROLLBACK 才是撤销。注意 pgAdmin 默认自动提交每条 SQL——演示事务时要先关掉自动提交。
3. ACID 中的 D（Durability 持久性）指的是？
持久性：COMMIT 之后的修改写进磁盘（WAL 预写日志），断电、崩溃重启后依然在。银行转账成功但系统宕机，钱不能丢。

🌿 中级 · 应用

4. 事务里执行了 3 条 UPDATE 后设置 SAVEPOINT a，再执行 2 条 UPDATE 后执行 ROLLBACK TO SAVEPOINT a，结果是？
SAVEPOINT = 事务内的存档点：ROLLBACK TO a 只撤销 a 之后的 2 条，之前的 3 条保留，且事务仍继续（还能再 COMMIT）。全撤销要直接 ROLLBACK。
5. 「事务 B 读到了事务 A 未提交、随后被回滚的修改」这是什么问题？
脏读 = 读未提交：A 改了没提交，B 读到了；A 回滚，B 手里就是「脏数据」。PostgreSQL 不会出现脏读（最低的 READ COMMITTED 也不允许）。
6. PostgreSQL 的默认事务隔离级别是？
PG 默认 READ COMMITTED。注意与 MySQL 对比：MySQL/InnoDB 默认 REPEATABLE READ；PG 还压根没有 READ UNCOMMITTED（设置了也按 READ COMMITTED 处理）。查看：SHOW transaction_isolation;

🎯 高级 · 综合

7. 同一事务内两次查询「余额 > 500 的用户」：第二次比第一次多了一行。这是？
区分口诀：不可重复读 = 同一行被 UPDATE/DELETE 变了值；幻读 = 范围查询的行数多了/少了（别的 INSERT）。本题是「多了一行」→ 幻读。别被「读到了新数据」迷惑成脏读——插入已提交，不是未提交。
8. 关于幻读，PostgreSQL 的 REPEATABLE READ 与 MySQL 有何不同？
SQL 标准里 REPEATABLE READ 允许幻读，MySQL 需靠临键锁补防；PG 的 RR 用快照隔离实现，整个事务读同一版本数据，天然防幻读——本课矩阵也标了 ❌。面试被问「RR 防不防幻读」一定要分数据库答。
9. 「两个事务同时读余额 1000，各扣 200/300，先提交的被后提交的覆盖，只剩 700」——哪个隔离级别能防住？
这是更新丢失。本课矩阵：READ COMMITTED 可能、REPEATABLE READ 可能、只有 SERIALIZABLE 标 ❌。工程上抢购/库存扣减常选 SERIALIZABLE 或改用原子 UPDATE（如 balance = balance - 200 的读改写）。

最终考核

下面是《05.事务》源课程作业的四道复述题改编——这就是本课的最终考核。规则：不查资料，先在心里回答，再点击核对。全部答对且能讲清理由，才算过关。

考核一（作业 1）：下面哪个场景最需要用事务？
判据：多步操作要么全成功要么全失败——转账（扣一加一）、下单（扣库存+建订单）、对账批量更新。单条查询天然原子，DDL 语句本身不可分割，都不需要事务包裹。
考核二（作业 2）：转账过程中发现第二步扣款失败，正确的操作序列是？
失败处理 = ROLLBACK：撤销事务内所有未提交修改（包括已成功的加款），账户回到初始状态。第二项把加款先 COMMIT 掉再扣款，一旦扣款失败钱就凭空多了；事务范围外的 UPDATE 不受事务保护。
考核三（作业 3）：关于 ACID，下列说法正确的是？
ACID = 原子性 / 一致性 / 隔离性 / 持久性。一致性是最终目的（数据始终满足约束），原子性保证「不做一半」，隔离性管并发互扰，持久性管提交不丢。四条是一个整体。
考核四（作业 4）：抢购场景「库存扣减防超卖」，推荐哪个隔离级别？
课件推荐表：抢购/库存扣减/防超卖 → SERIALIZABLE（唯一完全防更新丢失的级别）。日常 Web 应用默认 READ COMMITTED 就够；READ UNCOMMITTED 在 PG 中不存在。
