表间关系

本课目标

完成本课后，你将能：

  1. 判断 1:1 / 1:N / M:N 场景，并说清每种关系的建表实现方式——最终考核考的就是这个
  2. 说清外键 4 种约束行为（NO ACTION / RESTRICT / CASCADE / SET NULL）的差异
  3. 读懂 ERD 实体关系图，并能给错误的 ER 图找茬

知识速览

先花几分钟把核心机制过一遍——细节都在《03.表间关系》里，测验和考核会考。

三种关系的实现口诀

任意一方放外键 + UNIQUE ─ 1:1 ─▶ 一配一，拆表为性能
「多」的一方放外键，不加 UNIQUE ─ 1:N ─▶ 最常见：部门↔员工
中间表：两个外键做联合主键 ─ M:N ─▶ 学生↔课程，附加选课日期

⚙️ 判断口诀：先问「一个 A 对应几个 B，一个 B 对应几个 A」——两边都是 1 是 1:1；一边多一边 1 是 1:N；两边都多是 M:N。

外键四种约束行为

  1. NO ACTION（PG 默认）：有子记录就不许删/改父表，支持延迟检查（DEFERRABLE，配合事务用）。
  2. RESTRICT：与 NO ACTION 行为相同，但不支持延迟检查——立即报错。
  3. CASCADE 级联：删父表记录，子表关联记录自动跟着删；改父表主键，子表外键自动更新。方便但误删风险大。
  4. SET NULL：父表删除/更新后，子表外键列置为 NULL——要求外键列允许 NULL（软解绑）。

ERD 符号速记

矩形 = 实体（表）   连线 = 关系
||--||   一对一
||--o{   一对多
}o--o{   多对多（用中间表实现）
PK 主键 / FK 外键 / UK 唯一键

分级测验

三道一组，先做后点——点击选项立刻出对错与解释。

🌱 初级 · 概念

1. 一对一关系在数据库中的实现方式是？
1:1 = 任意一方放外键 + UNIQUE（保证一个 B 只配一个 A）。用户与 user_profiles 就是典型。理论上可合并成一张表，为性能/权限/行大小才拆分。
2. 一对多关系中，外键应该放在哪边？
外键放「多」的一方：employees.dept_id → departments.id，且不加 UNIQUE（多个员工可同属一个部门）。放反了就成了「一个部门属于一个员工」。
3. 多对多关系为什么不能直接用外键实现？
M:N 是「双向一对多」：一个学生选多门课、一门课被多个学生选。任何单表外键只能表达「多对一」，所以必须用中间表：两个外键指向两张主表、组成联合主键，还可存放关系属性（如选课日期）。

🌿 中级 · 应用

4. PostgreSQL 中外键不写 ON DELETE 选项时的默认行为是？
PG 默认 NO ACTION：存在关联子记录时禁止删除/更新父表，且支持 DEFERRABLE 延迟到事务提交时再检查。RESTRICT 行为相同但不支持延迟检查。现阶段可把两者视为等同。
5. ON DELETE CASCADE 的效果是？
CASCADE = 级联：删部门，该部门所有员工跟着删。方向是父 → 子。想「软解绑」用 SET NULL（外键列需允许 NULL）。级联方便，但误删父表会连带清掉子表数据，生产上要慎用。
6. 中间表除了两个外键外，还可以放什么？
中间表可存关系属性：student_courses 里的 enroll_date、order_items 里的 quantity/price——这些数据只属于「这段关系」。这正是中间表比两个外键更常用的原因。

🎯 高级 · 综合

7. 「一次挂号只对应一个医生」——医生与挂号的关系是？
拆成两个方向判断：「一个医生能接几次挂号」→ 多次；「一次挂号对应几个医生」→ 一个。所以医生 1:N 挂号，外键放挂号表（doctor_id）。这类「X 对 Y 的关系」判断是 ERD 设计的基本功。
8. 「用户可以关注其他用户」应该怎么建表？
关注 = 用户 M:N 用户（自关联多对多）：一张 follows 中间表，follower_id 与 followee_id 都 FK → users.id，组成联合主键。单列 follower_id 只能存「一个」关注对象；JSON 数组则失去关系型约束。
9. ERD 中 分类 ||--o{ 商品 这条线表示？
ERD 符号：|| = 恰好 1，o{ = 0 到多。||--o{ 即 1:N——分类一侧是 1、商品一侧是 0..N。含义：一个分类有多个商品，每个商品只属一个分类（category_id 外键在 product 表）。

最终考核

本节源课程没有作业，下面四道题由《03.表间关系》的练习题（场景判断 + ERD 找茬）改编——这就是本课的最终考核。规则：不查资料，先自己在脑中画表，再点击核对。全部答对且能讲清理由，才算过关。

考核一（场景题·选课系统）：学生与课程的关系及「选修后记录成绩」怎么实现？
学生可选多门课、一门课被多个学生选 → M:N。中间表 = (student_id, course_id) 联合主键 + 成绩列（关系属性）。另外：院系 1:N 学生、院系 1:N 老师、老师 1:N 课程。
考核二（场景题·视频平台）：「用户收藏视频」的关系与实现是？
一个用户收藏多个视频、一个视频被多个用户收藏 → M:N，用中间表收藏表实现。同场景里还有：用户 1:N 视频（上传）、分类 1:N 视频、视频 1:N 弹幕、弹幕 N:1 用户。注意「上传」与「收藏」是两段不同关系，别混在一张表。
考核三（找茬题·超市收银 ERD）：下图中隐藏了一处错误关系，错在哪？
场景：每张小票记录多个商品及数量。一个商品可以出现在多张小票的明细里 → 商品与小票明细是 1:N，原图却画成 ||--|| 一对一。正确应为 商品 ||--o{ 小票明细。其余关系（会员 1:N 小票、小票 1:N 明细、分类 1:N 商品、供应商 1:N 商品）都是对的。
考核四（设计题）：为「多对多 + 附加属性」设计建表语句，下面哪条最合适？
中间表标准姿势：两个外键 组成联合主键（同一组合不重复）、关系属性 enroll_date 独立成列。陷阱项：单个外键表达不了双向多；JSONB 绕开关系模型，失去外键约束与联合查询能力；给单个外键加 UNIQUE 会把关系错变成 1:N。

💼 面试实战

下面是真实面试官会问的问题，选自中文互联网面试题集（出处附后）。先自己回答，再点击核对。三级面试难度：中级考应用，高级考陷阱，专家考机制与设计。

⚡ 中级面试题

面试题一（外键基础）：外键（Foreign Key）的作用是什么？
外键指向父表主键，作用：① 建立表间关联；② 数据库层面自动约束（防止插入不存在的父记录、防止误删被引用的父记录）。代价是每次写入都要检查、降低写性能。出处：php.cn「MySQL 外键使用面试题解析」
面试题二（级联删除）：ON DELETE CASCADE 的优缺点各是什么？
级联删除「方便」是真方便：删一条主记录，关联数据自动清理。但误删父表一条记录可能连带删掉订单、购买记录等关键数据，且难以追溯——所以《阿里巴巴开发手册》明确禁止使用级联。生产上慎用，宁可显式在应用层删除。出处：博客园「为什么大厂都不推荐使用外键」

🔥 高级面试题

面试题三（大厂必问）：「为什么大厂都禁止使用外键？」最核心的原因是？
三座大山：① 性能——每次 INSERT/UPDATE/DELETE 都要检查父表、维护关联索引，高并发下成瓶颈，死锁概率上升；② 架构演进——分库分表/微服务后数据跨库，外键物理上无法生效；③ 级联风险——误删连带、难以追踪。辩证收尾：单机低并发、一致性优先的项目（ERP/财务）仍可用。出处：博客园「为什么大厂都不推荐使用外键」
面试题四（SET NULL 细节）：外键选了 ON DELETE SET NULL，有什么前提条件？
SET NULL 要把外键列置空，所以该列必须允许 NULL（不能带 NOT NULL）——「软解绑」场景（父记录没了、子记录保留但失去关联）用它。与之相对，RESTRICT/NO ACTION 是默认的「硬禁止」。出处：php.cn「MySQL 外键使用面试题解析」

🧠 专家面试题

面试题五（架构设计）：不用外键后，靠什么保证数据一致性？
标准答案组合拳：① 应用层校验（写子表前查父表，配合事务保证原子性）② 定时巡检（每日 SQL 扫「孤儿记录」对账、告警）③ 逻辑外键（应用层维护字段关联）④ 事件驱动/柔性事务保证最终一致。触发器模拟不推荐：逻辑隐蔽、难调试。出处：博客园「为什么大厂都不推荐使用外键」
面试题六（场景权衡）：什么场景适合用外键，什么场景必须禁用？
分场景：单体、低并发、数据量小、强一致（传统企业/ERP/财务）→ 用外键，省代码且数据库兜底；高并发、分布式、分库分表、微服务 → 禁用，物理外键跨库失效且拖累性能。盲目跟风禁用和盲目使用都是错的。出处：博客园「为什么大厂都不推荐使用外键」
