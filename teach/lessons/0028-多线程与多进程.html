知识速览

场景选型表

场景推荐方案
CPU 密集型multiprocessing / ProcessPoolExecutor
同步 I/O 密集（文件、阻塞数据库驱动）threading / ThreadPoolExecutor
异步 I/O 密集（爬虫、Web 服务）asyncio / 协程
调用第三方同步库asyncio.to_thread 或 run_in_executor 包装

三个要点

  1. GIL：同一时刻只有一个线程执行 Python 字节码：多线程无法加速 CPU 密集任务；I/O 等待时 GIL 会释放，所以 I/O 密集仍有效。官方文档：GIL
  2. 竞态条件出在「检查与扣款」的间隙：if balance >= amount 与 balance -= amount 不是原子操作——用 with lock: 把检查+扣款整体包成临界区。官方文档：Lock
  3. Lock 不可重入、RLock 可重入：同一线程重复 acquire 普通 Lock 会死锁；递归函数要用 RLock。多把锁交叉获取会死锁——固定锁的获取顺序是通用解法。

分级测验

点击选项立即获得反馈。答错也没关系——仔细读解释，它会把文档里对应的小节指给你。三级难度：初级考概念，中级考应用，高级考综合与陷阱。

🌱 初级测验 · 概念

1. CPU 密集型计算任务，最优方案是？
CPU 密集要利用多核：多线程受 GIL 限制、协程单线程——只有多进程能真正并行计算。详见「何时用线程，何时用协程」选型表。
2. GIL 保证的是？
GIL（全局解释器锁）让 CPython 同一时刻只有一个线程执行字节码——多线程不能加速 CPU 密集任务。详见「GIL」一节。
3. 守护线程（daemon=True）的特点是？
主线程退出时守护线程被强制终止（非守护线程会阻止进程退出）。守护线程里不应操作资源（可能被半途终止）。详见「守护线程」一节。

🌿 中级测验 · 应用

4. 竞态条件（Race Condition）的根源是？
「查余额 → 扣款」两步之间线程可能被切换，另一个线程插入——两个人都看到 1000 都取 800。详见「线程安全与竞态条件」一节。
5. 同一线程对普通 Lock 连续 acquire 两次会？
普通 Lock 不可重入：没释放就再次 acquire → 死锁。需要重入（如递归）用 RLock。详见「Lock 死锁问题」与「RLock」两节。
6. 两个线程交叉获取两把锁导致互相等待，这叫什么？
task1 拿 A 等 B、task2 拿 B 等 A → 互相等待 = 死锁。解法：所有线程按相同顺序获取锁。详见「死锁」一节。

🎯 高级测验 · 综合

7. 账户 1000 元，两个线程同时取 800（无锁版本，检查后 sleep 0.1 再扣款）。最可能的结果是？
时间线：两人几乎同时读到余额 1000 且都 ≥ 800 → 都进入取款 → sleep 后各自扣 800 → 余额 1000 - 800 - 800 = -600。「检查+扣款」不是原子操作，锁不住就出负余额。加 with account._lock: 包住检查与扣款后，才会是一人成功一人失败。
8. 同一台机器上，用两个线程跑两次 cpu_intensive()（纯 Python 大循环），对比单线程顺序跑两次，结果是？
GIL 让两个线程轮流执行字节码而不是并行——纯 Python 计算用多线程不会更快（还有切换开销）。要加速 CPU 密集任务得用 multiprocessing 多进程。
9. ThreadPoolExecutor.map(f, urls) 返回结果的顺序是？
executor.map 返回按传入顺序的结果迭代器（即使后面的任务先完成，也等前面的就绪才产出）——与 submit 返回 Future 列表的用法区分开。详见「ThreadPoolExecutor 线程池」一节。

最终考核

源课程本章没有作业，以下四道为覆盖本章核心能力的等效考核。规则：不查资料、不运行代码，先在心里算出答案，再点击核对。

考核一（竞态预测）：账户 1000 元，两个线程同时取 800（无锁版本，检查后 sleep 0.1 再扣款）。最可能的结果是？
时间线：两人几乎同时读到余额 1000 且都 ≥ 800 → 都进入取款 → sleep 后各自扣 800 → 余额 1000 - 800 - 800 = -600。「检查+扣款」不是原子操作，锁不住就出负余额。加 with account._lock: 包住检查与扣款后，才会是一人成功一人失败。
考核二（Lock 修复）：修复上述竞态，下列做法中正确的是？
临界区 = 检查 + 扣款整体：with account._lock: 包住从查询余额到扣款完成，同一时刻只有一个线程进入。第二个只锁扣款，检查窗口仍在 ✗；第三个两把锁互不排斥 ✗；第四个加重竞态 ✗。
查看参考答案（Lock 修复竞态条件） 
class BankAccount:
    def __init__(self, balance):
        self.balance = balance
        self._lock = threading.Lock()

def withdraw(account, amount, person_name):
    with account._lock:            # 临界区：检查 + 扣款
        if account.balance >= amount:
            time.sleep(0.1)        # 模拟输入密码、出钞
            account.balance -= amount
            return True
        return False
考核三（GIL 预测）：同一台机器上，用两个线程跑两次 cpu_intensive()（纯 Python 大循环），对比单线程顺序跑两次，结果是？
GIL 让两个线程轮流执行字节码而不是并行——纯 Python 计算用多线程不会更快（还有切换开销）。要加速 CPU 密集任务得用 multiprocessing 多进程。
考核四（死锁预测）：task_1 先拿 lock_a 再拿 lock_b；task_2 先拿 lock_b 再拿 lock_a，两个线程同时启动。会发生什么？正确解法是？
经典 ABBA 死锁：task_1 持 A 等 B，task_2 持 B 等 A，谁也走不了。解法：固定锁的获取顺序（两个任务都先 A 后 B）。第四个去掉 sleep 只是缩小窗口，不能根治 ✗。
