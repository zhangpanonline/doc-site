实现MCP服务器

配合《27.实现MCP服务器》使用预计 15–20 分钟9 道分级测验 + 面试实战

本课目标

完成本课后，你将能：

  1. 说出 FastMCP 替你接管了哪些活：连接管理、协议合规、消息路由
  2. 解释一个普通 async def 函数是怎么变成 tools/list 里的工具定义：函数名 → name、类型标注 → inputSchema、docstring → description
  3. 说清 run(transport="streamable-http") 为什么是生产部署首选的传输方式，以及默认端点是 /mcp
  4. 用 MCP Inspector 连上自己的服务、列出工具并实调一次 get_weather，并指出生产上线前必须补的安全边界

知识速览

先花几分钟把「服务端最小形态 → 协议定义 → 传输方式 → 上线边界」这条链路过一遍——细节都在《27.实现MCP服务器》里，测验和面试会考。

服务端最小形态：四步走

  • 装包：uv add mcp==1.28.1——课程锁定 mcp 1.28.1（对应 python-sdk 的 v1.28.1 标签），安装前先看清对应版本的官方文档
  • 建服务：from mcp.server.fastmcp import FastMCP → mcp = FastMCP("Weather Service", json_response=True)
  • 注册工具：@mcp.tool() 装饰一个带类型标注和文档字符串的函数（本章是 async def get_weather(city: str = "成都") -> dict[str, str]）
  • 跑起来：mcp.run(transport="streamable-http")——底层用 starlette + uvicorn 起一个 HTTP 服务；Notebook 里则把它丢进独立线程（threading.Thread(target=run).start()），否则会阻塞整个单元格

一个装饰器，换来一份协议级工具定义

  • 你不用写 JSON Schema：官方原话是「no JSON Schema、no request parsing、no validation code、no protocol handling」——类型标注就是 schema（a: int, b: int is the schema），docstring 就是给模型看的工具描述
  • 协议侧长什么样：服务端在 tools/list 里回给你 name / title / description / inputSchema / outputSchema；description 与 inputSchema 里每个参数的说明，直接决定模型选不选这个工具、参数填得对不对
  • 返回类型不是装饰品：返回类型标注与结构化输出、outputSchema 校验直接相关——返回值「是提示符、还是结构化数据」，取决于标注
  • 能暴露的不止工具：@mcp.tool() 是「执行动作、可能有副作用」，@mcp.resource() 是「读数据、别做重计算、别有副作用」，@mcp.prompt() 是「可复用的提示词模板」——三者对应服务端三张能力表

传输方式与运行地址

  • 三种标准传输：stdio（客户端把服务端当子进程拉起，走 stdin/stdout）、Streamable HTTP（HTTP POST + 可选 SSE 流）、以及被它取代的 SSE
  • 为什么选它：官方把 Streamable HTTP 标为「the recommended transport for production deployments」，好处是有状态/无状态两种运行模式、支持断线重连（resumability）、JSON 或 SSE 两种响应格式、多节点部署扩展性更好；json_response=True 让响应直接从 SSE 流切到 JSON，stateless_http=True 则进一步去掉会话状态
  • 记住端点：Streamable HTTP 默认挂在 /mcp（SSE 默认 /sse），本地默认 http://localhost:8000/mcp
  • Inspector 是参考工具：npx -y @modelcontextprotocol/inspector 起 Web UI，在界面里连 http://localhost:8000/mcp；也可以 --cli / --tui，CI 里常用 npx @modelcontextprotocol/inspector --cli ... --method tools/list

上线前必须补的边界（课程代码没写，但面试会问）

  • 传输安全：规范要求服务端必须校验 Origin 头（防 DNS rebinding），本地运行应只绑 127.0.0.1，并对所有连接做认证
  • 工具安全：服务端必须校验全部工具入参、做访问控制、对调用限流、清洗工具输出；客户端侧则应弹确认、向用户展示调用参数、做超时与审计日志
  • 错误分两层：协议错误（未知工具、参数不合法）走 JSON-RPC error；执行错误（API 失败、业务逻辑失败）走结果里的 isError: true——别把业务失败当成协议失败抛出去
  • npx 版本要对齐：课程用的是 @modelcontextprotocol/inspector@1.0.0，而官方文档已演进到需要 Node 22.19.0+ 的新版本——老版本连新协议的服务端可能握手失败，先统一版本再排查业务代码

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《27.实现MCP服务器》覆盖的内容。

🌱 初级测验 · 概念

1. 给 get_weather 加上 @mcp.tool() 之后，客户端在 tools/list 里看到的工具描述与参数结构（JSON Schema）从哪来？
官方 SDK 文档把这点写得很直白：你没有写 JSON Schema、没有写请求解析、没有写校验代码、没有写协议处理——「两个带类型标注的 Python 函数加一个 docstring」（a: int, b: int is the schema）就是全部。所以工具的名字来自函数名、参数结构来自类型标注、给模型看的描述来自 docstring。本章的 get_weather 正是这个套路。
2. 关于 mcp = FastMCP("Weather Service", json_response=True) 这个实例的职责，下列说法正确的是？
官方文档对 FastMCP 的定义是：it handles connection management, protocol compliance, and message routing。决策与工具选择是客户端/模型侧的事（工具在 MCP 里是 model-controlled），服务端只负责把工具按协议暴露出去并在被调用时执行；本章注册的 get_weather 会在 tools/call 到达时真正被调用。
3. 本章的 json_response=True 与 mcp.run(transport="streamable-http") 配套使用，它改变的是？
官方在 Streamable HTTP 一节给出的配置示例就是 FastMCP("StatelessServer", stateless_http=True, json_response=True)，并列出该传输支持的四种能力：状态/无状态两种模式、可恢复（resumability）、JSON 或 SSE 两种响应格式、更好的多节点扩展性。json_response=True 命中的正是响应格式这一项——它既不改返回值类型，也不换传输，更不会动协议版本。

🌿 中级测验 · 应用

4. 接第 3 题：Streamable HTTP 的「两种响应格式」是客户端能自由选择、还是服务端已经定死的？规范怎么说？
规范原文：对 JSON-RPC request，服务端「MUST either return Content-Type: text/event-stream, to initiate an SSE stream, or Content-Type: application/json, to return one JSON object. The client MUST support both these cases.」也就是说选择权在服务端，兼容义务在客户端。这正好解释了 json_response=True 的意义：它把服务端从默认的 SSE 流切换到一次性 JSON——写本地工具、接简单客户端时最省事，但要清楚这是服务端的配置决定，不是客户端点菜。
5. get_weather 内部调用真实天气 API 时被限流，报错信息应该怎么给到客户端？
规范把错误分成两层：协议错误（未知工具、参数不合法、服务端错误）走 JSON-RPC error；工具执行错误（API 失败、输入数据问题、业务逻辑错误）走结果里的 isError: true + 文本内容。限流属于典型的执行期失败。FastMCP 的三种写法是：抛 ToolError("...")（推荐）、让异常自然抛出（框架会捕获并转成 isError=True 的响应，不会弄崩服务端）、或直接返回 CallToolResult(isError=True)。假造成功数据是最糟的选项——模型会把脏数据当成事实继续推理。
6. 你要为 Agent 再暴露一份「城市气候说明文本」，它只是被读、不做计算也没有副作用。该用哪个装饰器，为什么？
官方文档给三种原语划了边界：Resources「similar to GET endpoints in a REST API - they provide data but shouldn't perform significant computation or have side effects」；Tools「let LLMs take actions through your server. Unlike resources, tools are expected to perform computation and have side effects」；Prompts 是「reusable templates」。所以「只读数据」选 @mcp.resource()。选工具并不会报错，但会让模型以为这是一个「动作」并可能在没有必要时调用它，也丢掉了资源订阅、变更通知这一层语义。

🎯 高级测验 · 综合

7. 你按本章把服务跑起来（transport="streamable-http"，其余保持默认），同事用 curl 打 http://localhost:8000/ 得到 404，于是断定服务没起来。最站得住脚的判断是？
官方文档写明默认挂载路径：「By default, SSE servers are mounted at /sse and Streamable HTTP servers are mounted at /mcp」；SDK README 给的客户端示例也直接连 http://localhost:8000/mcp。规范进一步要求 Streamable HTTP 服务端提供单一 MCP 端点同时支持 POST 与 GET（POST 送消息、GET 可选开 SSE 流），所以根路径 404 完全正常。另外用裸 curl 直接 POST 还缺规范要求的 Accept 头（必须同时列出 application/json 与 text/event-stream）——真要用命令行验证，用 Inspector 的 CLI 模式更省事。
8. 服务上线后 Agent 反馈：想查「北京」的天气，模型却始终只拿到成都数据。按本章代码找根因，并给出最小修法。
FastMCP 直接把函数签名映射成 inputSchema，而 JSON Schema 的规矩是：有默认值的参数不会进 required。于是 city: str = "成都" 在模型眼里变成了「可选参数」，它不传就是合法的，服务端照文档原样回成都。这不是传输、也不是 json_response 的问题，更与返回类型无关。修法有两种：真必填就去掉默认值让 city 进 required；确实想留默认值，就得让 docstring/描述把默认语义讲清楚——因为工具的 description 与参数说明是模型决定「传什么」的全部依据，这也是官方强调「docstring 就是你唯一的说明书」的原因。
9. 这个天气服务要提供给公司内网的其他 Agent 调用，你打算把 host 改成 0.0.0.0 并跳过认证「先跑通再说」。按规范与官方文档，最该指出的问题是？
规范在 Streamable HTTP 的 Security Warning 里写了三条硬要求：① 服务端 MUST validate the Origin header on all incoming connections to prevent DNS rebinding attacks；② 本地运行时 SHOULD bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0)；③ SHOULD implement proper authentication for all connections。原理很直白：本地 MCP 服务端对浏览器里的任意网页来说都是可达的，没有 Origin 校验就可能被恶意站点借你的服务去调工具。再叠加工具一节的要求（校验入参、访问控制、限流、清洗输出），「先跑通再说」在内网同样不成立。
