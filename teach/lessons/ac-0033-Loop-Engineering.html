Loop Engineering

配合《33.Loop Engineering》使用预计 15–20 分钟9 道分级测验 + 面试实战

本课目标

完成本课后，你将能：

  1. 说清 Loop Engineering 在课程里的位置——它解决的不是「单轮怎么走」，而是「循环怎么自我推动到交付」
  2. 复述课件列出的循环内五件事：自主发现未完成任务、并行子代理 + 工作树隔离、自主沉淀知识、自主接入工具、子代理分工
  3. 把《21.Agent》的循环判据和工程控制手段接起来：什么时候停、停了怎么算完成、跑飞了怎么兜底
  4. 为循环补上三项工程能力——预算与最大迭代、失败重试与退避、可观测与可续跑（进度文件 + 结构化交接物）

知识速览

本章源文档很精炼，就一句话定位加五条循环内的动作；下面把「定位 → 循环的三个工程问题 → 可观测与沉淀」这条线铺开，细节都能在《33.Loop Engineering》与《21.Agent》里对上。

Loop Engineering 是什么：让 Agent 自我推动到「可交付」

  • 课件定位（原文）：Loop Engineering 关注的是如何让 Agent 自我推动，最终完成一个可交付的产品；它的实现方式是循环
  • 循环里做的五件事（课件原文）：① 自主发现还未完成的任务；② 驱动多个子代理并行任务，并使用工作树隔离；③ 自主沉淀知识；④ 自主接入工具；⑤ 不同的子代理分工
  • 和前面几章的关系：第 20 章 ReAct 解决「一步怎么走」——思考 → 行动 → 观察；第 21 章把 Model / Session / Tool / Listener 装配成 Agent，用一个 while True 驱动 ReAct 循环；本章接着问第三个问题——这个循环怎么在没人盯着的时候一直转、并且转到能交付
  • 边界（沿用第 21 章的判据）：官方把 workflow 定义为「LLM 与工具按预定义代码路径编排」，agent 定义为「LLM 动态决定自己的流程与工具使用」。下一步取决于上一步结果、路径写不死的，才值得放进自主循环；路径固定的动作应该抽成工具或固定流程
  • 一句话记住：ReAct 管一步，Agent 管一圈，Loop Engineering 管「这一圈怎么自我推动到终点、并且在失控前停下」

循环的三个工程问题：终止条件、预算控制、失败重试与退避

  • 终止判据要外化到环境：第 21 章的退出条件是 registry.invoke(session.messages[-1]) 返回 None（这一轮没有 tool_calls），它只说明「模型这一轮不想调工具」，不等于任务已完成。Loop 场景的目标是可交付，完成判据必须来自环境里可验证的事实：验收项通过、测试跑绿、产物文件存在。官方记录过对应的失效模式——模型倾向于把功能标记为完成却没做端到端验证，解法是给它一份功能清单并自验证，只有通过测试才允许标记
  • 最大迭代是兜底，不是失败：官方原文「任务通常在完成时终止，但通常也要包含停止条件（例如最大迭代次数）来保持控制」。超限时应当有界退出并保留现场（进度文件 + 已完成/未完成清单 + 会话快照），而不是静默继续烧钱
  • 预算要按复杂度分配、在循环里实时结算：官方数据里 agent 大约用掉聊天 4× 的 token，多代理系统大约 15×；对应的分配经验是——简单事实查找 1 个代理、3–10 次工具调用；直接对比 2–4 个子代理、每个 10–15 次调用；复杂研究才上 10 个以上子代理并明确分工。写成式子就是每轮成本累加不超过预算 $B$：$$\sum_{k=1}^{N}\left(c_{in}\cdot T^{in}_{k}+c_{out}\cdot T^{out}_{k}\right)\le B$$其中 $T^{in}_k$ / $T^{out}_k$ 是第 $k$ 轮的输入、输出 token 数，$c_{in}$ / $c_{out}$ 是单价——一旦超限就停在当前轮，别等任务结束再算总账
  • 失败重试：先分类，再退避：官方 SDK 的默认策略是「某些错误自动重试 2 次，带一个短的指数退避」——连接错误、408、409、429 与 ≥500 默认重试，而且只有请求体可以安全重发时才重试。退避可以写成 $$t_n=\min\left(t_{max},\; t_0\cdot 2^{\,n}\right)+\text{jitter}$$ 也就是第 $n$ 次重试等待「指数增长但封顶」再加上一份随机抖动，避免大量子代理在同一时刻集体重试。参数错误、权限错误属于不可重试，应当立刻上报；同一个工具连续失败要熔断换路，而不是无限重试
  • 错误会累积，所以要能续跑：官方提醒 agentic 系统里「小故障可能造成灾难性后果」，而且不能简单地从头重启（贵且用户难受）——他们做的是「从出错时 Agent 所在的位置恢复」，并把「重试逻辑」与「定期检查点」这类确定性保障和模型自身的适应能力结合起来

可观测性与自主沉淀：让循环每一圈都留下痕迹

  • 第 21 章的监听层就是现成的观测面：ModelListener 挂在 reasoning_* / content_* / tool_call_* / complete 全部事件上，派生出审计监听器即可在 tool_call_end 记下工具名、参数、调用 id 与时间。官方在生产系统里的经验是——加上完整 tracing 之后才能系统性地定位「为什么没找到信息」；至少要能回答：每一轮决定了什么、调了什么工具、结果如何、花了多少 token 与时间、循环因为什么停下
  • 自主沉淀知识 = 把状态写到 Agent 之外：每个新会话都是「没有上一班记忆的新工程师」。官方的做法是先跑一个初始化会话搭好环境（init.sh、一份进度文件、一次初始提交），之后每个会话只做增量推进并留下结构化更新；关键洞察是「让 Agent 在全新上下文里能快速搞清工作状态」——靠的正是进度文件加 git 历史。另一个实战收获是让 Agent 用描述性的提交信息提交进度、把进展写进进度文件，这样它既能回退坏改动，也能恢复可用状态
  • 工作树隔离：并行的前提：官方 git 文档写得直白——一个仓库可以挂多个工作树，从而同时 checkout 多于一个分支；git worktree add <path> 会关联出一个新的工作树（最简单的形式下顺带创建同名分支），而只想做实验、不想打扰既有开发时可以用 git worktree add -d <path> 建一个「丢弃式」工作树。落到本章：每个并行子代理各占一个工作树，主工作树只负责汇总与合并——否则几个子代理在同一份工作拷贝里互相覆盖
  • 子代理分工要写到提示词里：官方把循环失败模式总结得很具体——早期版本会「为简单问题开 50 个子代理」、子代理之间重复劳动（一个查 2021 年芯片危机，另外两个重复查 2025 供应链）。有效做法是每个子任务都带目标、输出格式、可用工具与来源、清晰的任务边界，并把子代理的产出直接落成文件、只把轻量引用传回主代理，避免「传话游戏」式的信息损耗

🌱 初级测验 · 概念

1. Loop Engineering 关注的核心问题是？
课件原文：「Loop Engineering 关注的是如何让 Agent 自我推动，最终完成一个可交付的产品。它的实现方式是循环。」——它不改进单次生成的措辞，也不涉及训练，而是研究循环这一层的工程问题：怎么自己找活干、怎么并行、怎么沉淀、怎么收工。
2. 课件列出的循环动作里，「驱动多个子代理并行任务」配套的隔离手段是？
课件第二句原文就是「驱动多个子代理并行任务，并使用工作树隔离」。git 官方文档的说法是：一个仓库可以支持多个工作树，允许同时 checkout 多于一个分支——这正是让并行子代理各写各的、最后由主工作树汇总的物理基础。解释器、提示词、数据库都不是课件提到的隔离手段。
3. 回看《21.Agent》：这一版 Agent.invoke 的循环退出判据是什么？
第 21 章的循环是 resp = model.invoke_stream(session) → call_msg = registry.invoke(session.messages[-1])，为 None 就 break，否则把工具结果并进会话继续下一轮。记住这个判据的语义边界：它只表示「模型这一轮没要求调工具」，并不等于「任务已完成」——这正是本章要接手的问题。

🌿 中级测验 · 应用

4. 课件里的「自主发现还未完成的任务」，落到工程实现上最关键的动作是？
官方的长任务实践是：初始化会话搭好环境（init.sh、进度文件、初始提交），后续会话只做增量推进并留下结构化更新，关键洞察是「让 Agent 在全新的上下文里快速搞清工作状态」。所以「自主发现」靠的不是模型记忆，而是外部状态：进度文件 + git 历史 + 功能清单。把它想成「接班的工程师」，就知道为什么清单必须写在环境里。
5. 循环里工具调用失败时，哪种处理策略最符合本章的工程要求？
官方 SDK 的默认行为是「某些错误自动重试 2 次，带一个短的指数退避」，覆盖连接错误、408、409、429 与 ≥500，并且只在请求体可以安全重发时才重试——所以「无限重试」和「一律不重试」都错。参数校验失败重发同样的请求必然再失败，属于该立刻上报的那一类。再加一条本章视角的要求：重试要有上限，同一工具连续失败要熔断换路，否则循环会把预算烧在同一个坏工具上。退避写成 $t_n=\min(t_{max}, t_0\cdot 2^{n})+\text{jitter}$。
6. 要给一个「循环 + 多子代理」的 Agent 加预算控制，下面说法正确的是？
官方数据：agent 约用掉聊天 4× 的 token，多代理系统约 15×；因此他们把「按查询复杂度伸缩投入」写进了提示词（简单查找 1 个代理 3–10 次调用，直接对比 2–4 个子代理各 10–15 次，复杂研究才 10 个以上子代理）。「事后再统计」等于没有控制；「有最大迭代就不超 token」也不成立——单轮的 token 就可以非常大，轮数与预算必须分别设限。预算约束就是 $\sum_{k=1}^{N}\left(c_{in}T^{in}_{k}+c_{out}T^{out}_{k}\right)\le B$。

🎯 高级测验 · 综合

7. 同事说：「自主循环本来就是让 Agent 一直跑下去，加 max_iterations 就退化成 workflow 了，所以不该加。」这个说法错在哪？
官方的区分标准是路径由谁决定——workflow 按预定义代码路径编排，agent 由 LLM 动态决定流程与工具使用；加一个最大迭代次数并不改变这一点，Agent 依然是「LLMs using tools based on environmental feedback in a loop」。官方同时点明这类系统「有更高的成本与误差累积风险」，因此建议在沙箱中充分测试并配上护栏；而停止条件就是最基本的护栏。所以两件事要分开：软判据（环境验证任务是否完成）决定「什么时候算做完」，硬上限（迭代/预算/超时）决定「最坏情况下什么时候必须停」。
8. 「最终完成一个可交付的产品」，这个完成判据该怎么定？
官方的失效模式描述得很具体：不做显式要求时，模型会改代码、也会跑单元测试或 curl，但意识不到功能并没有端到端跑通，于是过早把功能标记为完成；解法是给它一份功能清单、要求自验证，只有仔细测试后才允许标记为通过。对应到本章：完成判据必须落在环境上（可执行的验收脚本、测试结果、产物文件），轮数上限只是「最坏情况下的刹车」，不能反过来当成功信号。
9. 排错：一个自我推动的循环跑了 40 轮还没停，token 花掉很多，最后产物也不对，而日志里只有每轮对话、没有别的信息。按本章工程要点，首先该补的三件事是？
三个症状正好对应本章三块工程能力：停不下来说明没有硬上限与退出原因记录（第 21 章的 while True 只靠「这轮没调工具」退出，模型反复试探就永远不停）；不知道为什么跑飞说明缺少 tracing——官方在生产系统里正是靠「完整 tracing」才能定位失败，监听层 tool_call_* 事件就是现成的挂点；产物不对还接着跑说明完成判据与进度没有外化，模型在自说自话。只调模型、日志级别或监听开关都不解决这三件事。
