Context Engineering

配合《31.Context Engineering》使用预计 15–20 分钟9 道分级测验 + 面试实战

本课目标

完成本课后，你将能：

  1. 说清「提示词工程 → 上下文工程」这次提法的变化，以及上下文工程自己的两个关注点：编排与治理
  2. 用注意力偏差的四条特点——长度稀释、长度分布外（OOD）、信噪比、首尾强化——解释「上下文不是越多越好」
  3. 把「放什么、留多久、怎么压缩、排在哪」四个取舍落到一个真实 Agent 的上下文装配逻辑里
  4. 把本章判据与第 16/17 章的既有原则接上：系统提示词保持静态、历史只增不改、思维链不删——因为它们直接决定缓存命中与 token 成本

知识速览

先花几分钟把「为什么难 → 难在哪 → 工程上管什么」这条线过一遍——细节都在《31.Context Engineering》里，测验和面试会考。本章是取舍，不是清单：四类取舍（放什么、留多久、怎么压缩、排在哪）背后是同一件事——注意力的预算有限。

从「写提示词」到「管上下文」

  • 提法的变化：2025 年 6 月，Shopify 的 CEO Tobi Lütke 在社交媒体上表示，他更喜欢用「上下文工程」这个词来替代「提示词工程」，因为它更准确地描述了为 LLM 提供充分信息以完成任务的核心技能
  • 本章的硬判据：上下文唯一的影响着模型的输出质量——模型权重在推理时是固定的，你能动的只有「这一次采样看到哪些 token」
  • 上下文里到底有什么：系统提示词、用户问题、消息历史、工具定义、MCP、Skill、检索到的外部数据……它们都属于「上下文」的一部分，不只是提示词那一段
  • 一句话抓手：提示词工程管「话怎么写」，上下文工程管「此刻窗口里该有哪几样东西」

上下文不是越多越好：注意力偏差（Attention Bias）

  • 长度稀释：上下文越长，注意力就被分散到更多 token 上，关键信息的权重被摊薄，模型更容易漏掉信息——「都放进去」不等于「都被读到」
  • 长度分布外（OOD，Out-of-Distribution）：当上下文长度超过训练语料常见长度后，模型回复的置信度会有明显下降——长上下文是「渐变」，不是「无损」
  • 信噪比问题：噪声信息越多，越会挤占模型对关键信息的注意力预算——无关的工具原始输出、过期的中间结论都是噪声
  • 首尾强化：模型对开头（系统提示词）和结尾（最近输入）的关注度天然高于中间，这是位置偏差（Positional Bias）——所以「关键约束埋在长历史中间」是结构性问题，不是模型笨

上下文工程的两个关注点：编排与治理

  • 编排：提示词、用户问题、工具、MCP、Skill 等内容在上下文中如何排列？什么时间加入什么内容？——对应「放什么、排在哪、什么时候放」
  • 治理 · 可信：如何确保上下文的内容安全可信？——工具返回、检索结果、外部网页都是不可信输入，进了上下文就可能被当成指令
  • 治理 · 膨胀：如何在持续的循环中，管理和优化不断膨胀的上下文？——对应「留多久、怎么压缩」
  • 与前面章节接上：第 16 章要求系统提示词精简、自洽、全局约束、保持静态、结构化；第 17 章要求历史只增不改、新消息追加到末尾、思维链不删——静态前缀 + 只追加的尾部既保住提示词缓存命中，也压缩了无谓的 token 支出

分级测验

🌱 初级测验 · 概念

1. 本章用哪句话概括上下文与输出质量的关系？
《31.Context Engineering》原文就一句：「上下文唯一的影响着模型的输出质量」。这句话不是「上下文越长越好」（第 2 项错），也不是「只有提示词重要」（第 3 项错）——恰恰相反，系统提示词、用户问题、消息历史、工具定义、MCP、Skill 都属于上下文的一部分。
2. 关于本章「上下文工程」的提法，下列哪一条是原文事实？
课件开头引用的就是这句表态。上下文工程不是模型架构（第 1 项错），也不是「永不修改」（第 2 项错，与第 17 章的缓存原则也不冲突）；它管的范围比措辞大得多（第 4 项错）——本章末尾把关注点落在编排与治理两件事上，后者明确包含「在持续的循环中管理和优化不断膨胀的上下文」。
3. 本章把上下文工程的关注点归纳为哪两项？
原文的两条：编排——提示词、用户问题、工具、MCP、Skill 等内容在上下文中如何排列、什么时间加入什么内容；治理——如何确保上下文内容安全可信，以及如何在持续循环中管理和优化不断膨胀的上下文。压缩只是治理里的一种手段（第 2 项以偏概全），采样/解码属于第 13 章推理机制，微调/蒸馏属于第 14 章训练阶段。

🌿 中级测验 · 应用

4. 某个 Agent 把检索到的一整份 8000 token 的产品文档塞进上下文，但用户只问了「退货运费谁承担」。按本章的四条注意力偏差，最直接的失效机制是？
原文明确定义：长度稀释是「上下文越长，注意力就被分散到更多 token 上，关键信息的权重被摊薄，模型更容易漏掉信息」；信噪比问题是「噪声信息越多，越会挤占模型对关键信息的注意力预算」。8000 token 远未触及窗口上限（第 1 项把 OOD 说成硬性拒绝，也不对——原文说 OOD 的表现是回复置信度明显下降，是渐变）。第 3 项错在「一定读不到」（首尾强化是相对关注度差异），第 4 项忽略了这个场景真正的变量——上下文构成。
5. 关于「长度分布外（OOD）」，下列说法正确的是？
原文：「当上下文长度超过训练语料常见长度后，模型回复的置信度会有明显下降」。它和长度稀释是两条不同机制——稀释讲注意力被摊薄，OOD 讲长度本身落在训练分布之外（第 3 项错）；也不是「短上下文才出现」（第 2 项）或「直接报错」（第 1 项）——超窗报错是另一回事，OOD 是性能层面可感知的下降。
6. 一条工具返回里，真正相关的只有 3 个字段，其余 200 行是原始日志。按本章判据，正确的处理姿势是？
本章「信噪比问题」：噪声越多，越挤占模型对关键信息的注意力预算；而「治理」这一关注点要求的正是「在持续的循环中管理和优化不断膨胀的上下文」。所以方向是提高信噪比 + 上下文之外留旁路。第 2 项直接把噪声堆进注意力预算；第 3 项把数据丢干净，既不省事也不可追溯；第 4 项是靠提示词修补结构问题——第 16 章的「精简」原则本来就要求能不说的不说，而不是先塞进去再求模型忽略。

🎯 高级测验 · 综合

7. 一个编码 Agent 的系统提示词里包含：角色与硬性规则、当前工作目录、今天的日期时间、工具使用规范。代码在每一轮都重新拼装这份系统提示词后发请求。结合第 16/17 章，最该先修的是什么？
两章判据叠加：第 16 章要求系统提示词保持静态（反面案例正是「当前用户 X，时间是 Y」这类动态内容）且结构化（Markdown/XML 分层，第 1 项把它改掉是倒退）；第 17 章给出成本侧的机制——多轮要命中提示词缓存，必须把新元素追加到 messages 数组末尾、历史上下文不可修改。每轮重拼系统提示词 = 每轮换前缀，缓存难命中；正确做法是让系统提示词这一段前缀跨轮逐字不变，动态事实在尾部按需出现（工具查询、或作为追加的消息）。第 2、4 项都在加剧前缀变化与长度稀释。
8. 一个会话连问 20 轮，每轮请求都会把整条历史重发，且历史里堆着前几轮工具的完整原始输出。这个形态同时压上来两笔账，最准确的描述是？
把两章接起来看：第 17 章算过 token 账——每轮把整份历史放进报文，属「只增不改」的代价，累计发送量随轮数平方级增长；本章给的是注意力账——长度稀释、信噪比、首尾强化都在说「历史越长，关键信息越容易被淹掉」。第 1、2 项各自只看了一半；第 3 项最危险：第 17 章明确「历史上下文不可修改」是缓存命中的前提，就地改写历史会同时让缓存失效并丢掉推理上下文——压缩必须做得克制、且尽量不破坏已有前缀。
9. 某 Agent 的单轮上下文已经膨胀到接近窗口上限，需要做「压缩」。按本章的判据，决定压缩是否安全的关键是？
本章「治理」的两个问题里，「放什么」是前提——上下文工程本质是取舍：放什么、留多久、怎么压缩。若不先想清判据，压缩就只能按 token 数量机械裁剪，最可能丢掉的恰是「当时不起眼、后面才关键」的信息。第 2 项是无判据的截断（还会破坏第 17 章强调的前缀与思维链）；第 3 项只动了系统提示词这一段，解决不了不断膨胀的历史；第 4 项是推迟决策，不是治理。
