知识速览

先花几分钟把本章的骨架过一遍——细节都在《29.子代理》里，测验和面试会考。

问题：一个轮次跑完所有事 → 超级庞大的上下文

  • 课件开场给的是「开发一个业务功能并暴露成 FastAPI 接口」这种任务：一个 Agent 在一个轮次里要经历 reasoning（需求分析、方案设计）+ 一个超级庞大的 ReAct 循环
  • 这个循环里塞着：建立 ORM 数据层 → 实现数据迁移 → 执行迁移命令 → 创建 DTO → 创建 Service → 创建接口 → 创建多个测试脚本 → 运行测试脚本 → 解决错误（循环）
  • 每一步的工具调用与工具结果都会沉积进同一条 session.messages，于是「你最终会得到一个超级庞大的上下文，这会带来诸多问题」
  • 子代理就是为了解决这个问题：把「探索、实现、调试」这些趟脏活的过程挪出主上下文，主 Agent 只留下被压缩过的结论

更友好的设计：主代理管宏观，子代理并行干活

  • 主代理：reasoning 只做宏观需求分析与方案设计，再在 ReAct 循环里派活
  • 子代理（各带一条用户提示词）：实现数据层 / 实现 DTO / 实现接口 / 完成测试——各干一件事
  • 收口：等待所有子代理完成，汇总结果（课件配图 assets/子代理.svg 讲的就是这个分派与汇总的形状）
  • 关键差别：子代理跑的是自己的会话——run_sub_agent 里 agent = Agent()，每个子代理用自己的 Session，与主代理的消息历史不共享；主代理拿回的只是最后一条消息的 content

实现：create_agent 这个工具怎么跑

  • 注册：agent/tool/__init__.py 里 from agent.tool.create_agent import create_agent，再 registry.register(create_agent)——和 read_file、bash_command、use_skill、use_mcp 同一条注册链
  • 入参：agent_config: list[dict[str, str]]，每项形如 {"name": "sub-agent-1", "query": "这是一个测试，请说：你好！"}；name 用来给结果贴标签，query 是子代理的初始用户提示词
  • 返回：json.dumps(results, indent=2, ensure_ascii=False)，每项形如 {"name": "sub-agent-1", "result": "子代理1的完成结果"}——result 取的是子代理 responses[-1] 的 message["content"]
  • 执行：为每个配置起一个 threading.Thread(target=run_sub_agent, args=(name, query)) 并 start()；所有线程起完后逐个 join()；results.append 用 threading.Lock 保护
  • 落盘：每个子代理结束前 agent.session.save(f"{name}-")——片段存成 <name>-<id>.json，事后能单独回看某个子代理到底干了什么
  • 用法：主代理只要说一句「请开启多个子代理，创建两个页面，分别画小猪佩奇和海绵宝宝。」，模型就会调 create_agent 分派，最后 agent.session.save() 保存整轮会话

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《29.子代理》覆盖的内容。

🌱 初级测验 · 概念

1. 课件说「一个 Agent 单独完成业务功能会得到超级庞大的上下文」，这个上下文是怎么长起来的？
课件原文：一个轮次里要经历 reasoning 加「一个超级庞大的 ReAct 循环」——建立 ORM 数据层、实现数据迁移、执行迁移命令、创建 DTO、创建 Service、创建接口、创建多个测试脚本、运行测试脚本、解决错误（循环）。这些步骤的工具调用与返回都进同一条会话，于是「你最终会得到一个超级庞大的上下文」。子代理正是为此而生。
2. 主代理调 create_agent 之后，子代理执行任务时的上下文来自哪里？
run_sub_agent 的第一行就是 agent = Agent()——不传 session，于是 Agent.__init__ 走 self.session = session or Session()，每个子代理各自新建一条会话。它只接收 agent.invoke(query) 这一条用户消息，主代理的历史既不继承、也不共享；多个子代理之间同样互不可见。这就是「上下文隔离」在代码里的落点。
3. create_agent 返回给模型的是什么形状？
课件「返回结果示例」写得很明确：[{"name": "sub-agent1", "result": "子代理1的完成结果"}, ...]，最后 return json.dumps(results, indent=2, ensure_ascii=False)。注意返回的是摘要——responses[-1].message.get("content", "")，子代理的中间过程不上行；需要回看完整过程时去读 agent.session.save(f"{name}-") 落盘的会话文件。

🌿 中级测验 · 应用

4. 去掉这段代码里的 for thread in threads: thread.join()，最直接的后果是什么？
Python 官方文档对 join() 的定义是「Wait until the thread terminates…blocks the calling thread until the thread whose join() method is called terminates」。课件正是在 start() 完所有线程之后才逐个 join()，这就是「等待所有子代理完成，汇总结果」那一步的实现。没有它，主线程可能在子代理还没 append 完就跑到了 return json.dumps(results, ...)，把不完整的结果交回模型。
5. results.append({...}) 外面为什么要套 with results_lock:？
results 在主线程创建，却被所有子代理线程同时 append——这是典型的共享可变状态。Python 官方文档在 threading 介绍里就点明加锁的用途：「Locks are…to protect shared data」，因此本课用 threading.Lock 把它包住。注意它只保证写入不被撕裂，不保证顺序：谁先 append 取决于线程调度，返回值里 name 的先后不能当作 agent_config 的顺序。
6. 主代理准备派两个子代理，配置应该写成什么样？
工具签名是 create_agent(agent_config: list[dict[str, str]])，循环里取的是 config.get("name", "unnamed") 与 config.get("query", "")：列表 + 每项 name/query。工具描述也写明「每个子代理要配置名称、用户提示词，子代理会根据提示词启动任务」——query 就是子代理唯一的任务交代，省略它子代理会带着空提示词开工（代码里 get 的默认值是空字符串，不会报错，所以这个坑很安静）。

🎯 高级测验 · 综合

7. 某个子代理的 agent.invoke(query) 中途抛了异常，跑 create_agent 的主代理会看到什么？
Python 官方文档说明：线程的 run() 里抛出的未处理异常由 threading.excepthook() 处理，默认是「printed out on sys.stderr」，它不会传播到调用 join() 的主线程；而 join() 的定义是等线程终止（「either normally or through an unhandled exception」），照样正常返回。课件这段实现里 run_sub_agent 没有 try/except、results.append 也不会执行，于是返回值静默缺项。这正是「错误在 agentic 系统里会复合」的典型形态——主代理会把「少了一路结果」当成「已经汇总完毕」继续往下做。
8. 队友提出：「能不能让所有子代理共享同一条会话上下文，这样它们能互相看见进度、不重复劳动？」按本章的设计，这个改法的问题在哪儿？
Agent.__init__ 的签名是 session: Session | None = None 配 session or Session()，所以「能传入」恰恰是它的设计（第 3 个选项的事实描述是错的）。真正的代价在语义上：本章 run_sub_agent 之所以写 agent = Agent()，就是为了让每个子代理「在独立线程中运行，完成任务后合并返回结果」——用隔离换上下文容量。如果共享会话，ORM、迁移、测试脚本这些过程全部堆回同一条历史，与「让一个 Agent 单轮跑完全流程」的原始问题完全等价；此时该选的不是共享上下文，而是别拆子代理、老老实实顺序做（或者按 Anthropic 的做法把中间产物写到文件系统，只传轻量引用）。
9. 主代理说「创建两个页面，分别画小猪佩奇和海绵宝宝」，两个子代理各自跑起来后，下面哪个判断最准确？
课件的隔离发生在会话层：每个子代理 agent = Agent() 拿自己的 Session，Agent 的工具来自同一个按类级字典组织的 registry，write_file/bash_command 操作的是同一个工作目录。所以「不共享消息」并不等于「不共享世界」：两个子代理彼此看不见对方的产出，却可能落到同一个路径上（index.html、page.html 这类名字尤其容易撞）。正确做法是在 query 里把交付物路径、命名规范、可写范围交代死——这也是「子代理的任务描述必须包含目标、输出格式、工具与边界」的现实理由。第 2 个选项把「可能」说成了「必然」；第 3 个选项描述的行为在本章代码里并不存在。
