知识速览

先花几分钟把 ReAct 循环的骨架、本章的 agent/ 变更过一遍——细节都在《20.ReAct》里，测验和面试会考。

ReAct 是什么：想一步、做一步、看结果、再想

  • 原始定义：让模型以交替（interleaved）的方式同时产生「推理轨迹」与「任务动作」——推理帮模型诱导、跟踪、更新行动计划并处理异常；行动让它接入外部信息源（知识库、环境）去补充信息
  • 本章的落地（一行都不能少）： 
    def query(q: str, session: Session, model: Model):
    session.add_message({"role": "user", "content": q})
    # ReAct Loop
    while True:
        model.invoke_stream(session)                      # 想（推理 + 可能发起工具调用）
        call_msg = registry.invoke(session.messages[-1])   # 做（执行 tool_calls）
        if call_msg is None:
            break                                          # 这一轮没有工具调用 → 收尾
        else:
            session.messages += call_msg                   # 看结果（把 role=tool 消息写回上下文）
  • 为什么必须交替：工具结果只有写回 messages，模型下一轮才能基于真实环境的反馈修正计划；思考只做一次就等于退化回「链式思考 + 一次性执行」，一遇到命令报错、路径不存在就无法自救
  • 循环的出口：判据是 registry.invoke() 返回 None——即这条 assistant 消息里没有 tool_calls，说明模型已经给出最终回复

本章 agent/ 的四处变更

  • 新增 bash 工具 agent/tool/bash_command.py：subprocess.run(command, shell=True, executable=...（Windows 用 "cmd"，其它平台 "/bin/bash"), capture_output=True, text=True, timeout=30)；返回码为 0 时回 stdout（空则回「(命令执行成功，无输出)」），非 0 时回 [退出码 N] 加 stderr
  • 系统提示词注入操作系统信息：agent/prompt.py 新增 get_os()（platform.system()），render_prompt 的渲染上下文变成 language / cwd / os / is_git；system.j2 的 # Environment 小节多出 Operating system: {{ os }}
  • 新建 Session 自动注入：Session.__init__ 里 system_prompt 为空就 render_prompt("system")，并 self.tools = tools or registry.schemas()——系统提示词与工具 Schema 都不再需要调用方手工传
  • 打印格式简洁化：ModelPrinterListener 按事件类型分支——REASONING_START 打「思考中...」、CONTENT_START 打「内容：」、content 绿色逐字输出、TOOL_CALL_END 打印被调用的工具名
  • 工程账目：新增 2 个文件（tool/bash_command.py、分析.md），修改 5 个（printer.py、prompt.py、prompt/system.j2、session.py、tool/__init__.py），删除 1.json 与 uv.md

循环跑出来的那份「分析.md」

  • 它的来路：把「请帮我分析 ./agent 目录中的核心实现逻辑，将结果放到当前目录的 分析.md 中」交给 query()——Agent 靠 bash_command / read_file / write_file 三个工具自己看代码、自己写文件，最后 session.save() 把会话存进 agent/sessions/<id>.json
  • 它给出的架构结论：config.py（pydantic-settings 读 .env）、events.py（EventEmitter 发布-订阅）、model.py（OpenAI 封装 + Builder 流式处理）、session.py（消息与工具）、prompt.py（Jinja2 渲染）、printer.py（流式打印）、tool/（Tool 基类 + 注册表 + 三个工具）
  • 它识别出的设计模式：发布-订阅（EventEmitter）、策略模式（Reasoning / Content / ToolCalls 三类 Builder）、装饰器模式（@tool）、工厂模式（create_params_model 动态建 Pydantic 模型）、单例模式（全局唯一 registry）
  • 数据流一句话：用户输入 → Session.add_message → Model.invoke → 响应拆成 Reasoning / Content / Tool Calls 三路 → 工具调用走 Registry.invoke 执行并把 role=tool 结果写回 → 再次 invoke，直到没有工具调用

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《20.ReAct》覆盖的内容。

🌱 初级测验 · 概念

1. 本次代码变动中，新增的工具文件是哪个？它提供什么能力？
课件「本次代码变动」第一条：新增了 tool/bash_command.py，提供了执行 bash 命令的工具。它用 @tool(command="要执行的 bash/shell 命令") 注册，内部走 subprocess.run(..., shell=True, capture_output=True, text=True, timeout=30)。read_file.py 与 core/utils.py 是上一章就有的文件。
2. ReAct 主循环里，while True 是靠什么条件跳出的？
课件 query() 原文：call_msg = registry.invoke(session.messages[-1])；if call_msg is None: break。registry.invoke 从消息里取 tool_calls，取不到就直接 return None——意思是「模型这一轮没有再要求调用工具」，于是当前这条 content 就是最终回复。本章代码里没有轮数上限、也没有对异常的 try/except。
3. 本章 Session.__init__ 在「什么都不传」时会自动准备好哪两样东西？
课件「本次代码变动」第三条：新建 Session 时自动注入工具和提示词。代码里是 system_prompt = render_prompt("system")（再 add_message({"role": "system", ...})）与 self.tools = tools or registry.schemas()。Model 与 ModelPrinterListener 仍由调用方自己创建（见课件第一段 session = Session(); model = Model(); listener = ModelPrinterListener(model)）。

🌿 中级测验 · 应用

4. registry.invoke(session.messages[-1]) 里，为什么取的偏偏是「最后一条」消息？
循环顺序是「先 model.invoke_stream(session)，再取 session.messages[-1]」。模型调用结束会把这一轮的 assistant 消息 add_message 进去，所以 [-1] 正是那条可能携带 tool_calls 的回复；registry.invoke 从它身上提取 tool_calls 并逐个执行。如果是 role=tool 的结果消息，那已经是本函数自己产出的返回值了。
5. 关于 bash_command 里 subprocess.run 的参数，下列哪条描述完全正确？
逐个对照课件代码：shell=True 指定「通过 shell 执行」这条命令（executable 进一步指定用哪个 shell：Windows 是 "cmd"，其它平台 "/bin/bash"）；capture_output=True 让内部 Popen 把 stdout 与 stderr 都设为 PIPE，是「捕获」而不是「打印」；text=True 让三个流以文本模式打开，所以 result.stdout 是字符串；timeout=30 是秒数，超时后子进程会被杀死并重抛 TimeoutExpired，不是重试次数。
6. 「在系统提示词中注入当前操作系统的信息」这条变更，具体是怎么落地的？
课件「修改文件 agent/prompt.py」原文：def get_os() -> str: return platform.system()，并且 template.render(language=get_language(), cwd=get_cwd(), os=get_os(), is_git=get_is_git())；模板侧 system.j2 的 # Environment 小节是「Primary working directory / Operating system: {{ os }} / Is a git repository: {{ is_git }}」。模板本身只是文本 + Jinja2 占位符，不能自己调 Python。

🎯 高级测验 · 综合

7. 有人把循环改写成：model.invoke_stream(session) → call_msg = registry.invoke(session.messages[-1]) → if call_msg is None: break，但删掉了 session.messages += call_msg。推演一下会发生什么？
循环的第三拍「看结果」正是 session.messages += call_msg：registry.invoke 返回的 {"role": "tool", "tool_call_id": ..., "content": ...} 必须回到上下文，模型下一轮才能读到。删掉它等于每轮都把同一个问题重新问一遍——同一个 tool_call 可能被执行多次（比如同一份 分析.md 被反复覆盖、同一条命令被反复跑），而模型永远「不知道」已经做过了。这正是 ReAct 区别于「一次性 function calling」的关键：行动结果要回流给推理。
8. 审查本章 tool/__init__.py 的 invoke()：tool = self._tools[name] 之后紧接着写 if not tool: result = "无此工具，请仔细检查你传递的工具名称是否正确"。这段代码的实际行为是？
字典下标访问缺键会抛 KeyError，不会返回 None，所以 if not tool 这个分支在「工具名不存在」这条路径上永远走不到——错误会以异常形式打断整个 ReAct 循环。修法是 tool = self._tools.get(name)，或者用 try/except KeyError 把「无此工具」作为 role=tool 的内容回传给模型，让它自己改名重试。这也解释了为什么「工具不存在要回传而不是抛断」：对 Agent 而言，错误信息也是可用的环境反馈。
9. 那份由 Agent 自己跑出来的 分析.md 里，把本章工程的 @tool 装饰器归为哪种设计模式？它同时认定的「单例模式」落在哪个组件上？
分析.md 的「关键设计模式」表：发布-订阅 → EventEmitter；策略模式 → Builder 类族（不同 Builder 处理不同类型内容）；装饰器模式 → @tool，把普通函数包装为 Tool 对象；工厂模式 → create_params_model 动态创建 Pydantic 验证模型；单例模式 → registry，全局唯一的工具注册表。ModelPrinterListener 是事件监听器，Session 每次新建都是一个新会话。
