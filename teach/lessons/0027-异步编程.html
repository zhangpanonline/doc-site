知识速览

同步 ↔ 异步协议对照

同步异步
__iter__ / __next____aiter__ / __anext__
for x in itasync for x in it
__enter__ / __exit____aenter__ / __aexit__
with ctxasync with ctx

三个要点

  1. 协程里别调同步阻塞函数：time.sleep(1) 会卡死整个事件循环——用 await asyncio.sleep(1)，或 await asyncio.to_thread(time.sleep, 1) 丢给线程池。官方文档：asyncio.to_thread
  2. gather(..., return_exceptions=True) 让异常变成结果：每个结果是「正常值或异常对象」，用 isinstance(r, BaseException) 逐个判断——多智能体系统靠它让单个子任务失败不拖垮整体。官方文档：asyncio.gather
  3. CancelledError 清理后必须重新 raise：except asyncio.CancelledError: 里做完清理要 raise，否则任务被静默吞掉取消信号。官方文档：CancelledError

分级测验

点击选项立即获得反馈。答错也没关系——仔细读解释，它会把文档里对应的小节指给你。三级难度：初级考概念，中级考应用，高级考综合与陷阱。

🌱 初级测验 · 概念

1. 遍历异步生成器必须用？
异步生成器/异步迭代器用 async for 遍历（协议是 __aiter__/__anext__）。普通 for 会得到协程对象而不是值。详见「异步生成器与异步迭代器」一节。
2. 异步上下文管理器的协议方法是？
async with 背后是 __aenter__/__aexit__（都是 async def）。详见「异步上下文管理器」一节。
3. asyncio.run(main(), debug=True) 能检测出？
debug 模式会警告「Coroutine 'xxx' was never awaited」以及长时间阻塞的协程——新手忘记 await 的救星。详见「使用 debug 模式」一节。

🌿 中级测验 · 应用

4. gather(..., return_exceptions=True) 的作用是？
return_exceptions=True 时异常以对象形式出现在结果列表里，不抛出不中断；用 isinstance(r, BaseException) 逐个检查。详见「gather 异常处理」一节。
5. await asyncio.wait_for(slow(), timeout=2) 超时后抛出？
超时抛 TimeoutError（3.11+ 用 async with asyncio.timeout(2) 更现代）。详见「asyncio.wait_for」一节。
6. 协程中调用同步阻塞函数（如 time.sleep(1)）的正确姿势是？
asyncio.to_thread 把同步阻塞函数放进线程池执行，事件循环不被卡住；底层是 loop.run_in_executor(None, func)。详见「在异步中运行同步代码」一节。

🎯 高级测验 · 综合

7. 任务被取消时（收到 CancelledError），做了清理后应该？
except asyncio.CancelledError: 完成清理后必须 raise 重新抛出——否则取消信号被吞掉，任务「赖着不走」，优雅关闭模式就失效了。详见「最佳实践 7」。
8. 协程函数里写 time.sleep(1) 会怎样？
time.sleep 是同步阻塞，协程执行它时整个线程（连同事件循环）卡住——其他协程无法调度。改用 await asyncio.sleep 或 await asyncio.to_thread(time.sleep, 1)。详见「最佳实践 1」。
9. threading.Lock 与 asyncio.Lock 的区别是？
threading.Lock 协调OS 线程（等待时真的阻塞）；asyncio.Lock 协调同一事件循环内的协程——等待锁时用 await 让出，事件循环可运行其他任务。二者不可互换：协程里用 threading.Lock 会把整个循环卡死。

最终考核

下面是《27.异步编程》源课程作业（读懂多智能体异步调研系统代码）的改编题——这就是本课的最终考核。规则：不查资料、不运行代码，先在心里选出正确实现，再点击核对。

考核一（orchestrator 并行执行）：系统把调研需求分解为多个子任务后并行执行，单个失败不拖垮整体。下列实现中正确的是？
正确写法：raw_results = await asyncio.gather(*[...], return_exceptions=True)——列表推导创建协程对象，* 展开传给 gather 并发执行；return_exceptions 让单个失败以异常对象返回，后续用 isinstance(r, BaseException) 标记失败任务。第二个串行 ✗；第三个一个失败中断整批 ✗；第四个读不到结果 ✗。
查看内嵌参考答案（orchestrator 核心） 
raw_results: list[str | BaseException] = await asyncio.gather(
    *[execute_subtask(i + 1, len(subtasks), task)
      for i, task in enumerate(subtasks)],
    return_exceptions=True,
)
results: list[str] = []
for r in raw_results:
    if isinstance(r, BaseException):
        results.append(f"[执行失败] {r}")
    else:
        results.append(r)
考核二（ai_tools 异步流式解析）：用 httpx 异步请求流式接口，逐行解析 data: {...}、遇 [DONE] 结束、坏行跳过。下列实现中正确的是？
异步流式三件套：async with httpx.AsyncClient() + async with client.stream("POST", ...) + async for line in resp.aiter_lines()；行处理与第 21 课 SSE 解析相同（前缀判断 → [DONE] break → 容错）。第二个同步库阻塞事件循环 ✗；第三个心跳行崩 ✗；第四个容错差 ✗。
查看内嵌参考答案（ai_tools 核心） 
async def completions(messages) -> AsyncGenerator[str, None]:
    payload = {"model": MODEL_NAME, "messages": messages, "stream": True}
    async with httpx.AsyncClient(timeout=120) as client:
        async with client.stream("POST", _URL, headers=headers, json=payload) as resp:
            resp.raise_for_status()
            async for line in resp.aiter_lines():
                if not line or not line.startswith("data: "):
                    continue
                data_str = line[6:]
                if data_str.strip() == "[DONE]":
                    break
                try:
                    chunk = json.loads(data_str)
                    content = chunk["choices"][0].get("delta", {}).get("content", "")
                    if content:
                        yield content
                except (json.JSONDecodeError, KeyError, IndexError):
                    continue
考核三（gather 异常预测）：两个子任务，一个返回 "ok"、一个抛 ValueError，return_exceptions=True 时 results 的内容是？
return_exceptions=True：异常作为对象放进结果列表（位置与传入顺序对应）——['ok', ValueError(...)]。这就是 orchestrator 能标记「[执行失败]」的原因。
考核四（CancelledError 规范）：任务被取消时（收到 CancelledError），需要做清理（如释放资源），正确处理方式是？
except asyncio.CancelledError: 完成清理后必须 raise 重新抛出——否则取消信号被吞掉，任务「赖着不走」。第三个 finally 也可以（取消信号仍会传播），但题意是 except 中的规范处理。详见「最佳实践 7」。

四道考核全部答对，说明你已经能用官方 API 高效开发异步程序——可以继续学习《26.多线程和多进程》了。

💼 面试实战

下面是真实面试官会问的问题，选自中文互联网面试题集（出处附后）。先自己回答，再点击核对。三级面试难度：中级考应用，高级考陷阱，专家考机制与设计。

⚡ 中级面试题

面试题一（锁的区别·高频）：threading.Lock 与 asyncio.Lock 可以互换吗？
不可互换：threading.Lock 协调 OS 线程，等待时真阻塞；asyncio.Lock 协调同一事件循环内的任务，await lock 等待时让循环运行其他任务。协程里误用 threading.Lock 会卡死整个事件循环。出处：腾讯云「Python 并发编程模型：面试中的重点考察点」
面试题二（gather vs TaskGroup·追问）：两者都能并发运行协程，失败处理有何不同？
gather：默认任何异常立即传播（可用 return_exceptions 改）；TaskGroup（3.11+）：结构化并发——任一子任务异常会取消组内所有其他任务并保证退出前全部完成。选择依据：结果顺序与失败行为。出处：Skillup「Python 后端面试题（asyncio 高频面试题汇总）」

🔥 高级面试题

面试题三（异步死锁·深水区）：两个协程按相反顺序获取两把 asyncio.Lock，会发生什么？
与线程死锁同构：asyncio.Lock 默认无超时，两协程反向获取两把锁 → 互相等待 → 事件循环整体卡死（且没有报错）。工程实践：一致的锁顺序 + 更小临界区 + await asyncio.wait_for(lock.acquire(), timeout=...) 有界等待。出处：CSDN「终面倒计时 5 分钟：候选人用 trio 破解 asyncio 死锁危机」
面试题四（TaskGroup 异常·机制）：asyncio.TaskGroup 中某个子任务抛异常，会发生什么？
TaskGroup 是结构化并发：任一子任务异常 → 取消组内所有其他任务 → 退出后以 ExceptionGroup（3.11+）聚合抛出所有异常。与 gather 的「默认异常即抛、其余继续」形成对比——失败行为是两者的选择依据。出处：Skillup「Python 后端面试题（asyncio 高频汇总）」

🧠 专家面试题

专家题一（死锁诊断·工程）：生产环境异步服务疑似死锁，第一时间该做什么？
诊断异步死锁的标准动作：开 PYTHONASYNCIODEBUG（暴露「某任务长期 pending」「Event loop is closed」等静默失败），配合 asyncio.all_tasks() dump 各任务状态，定位卡在哪个 await（锁/网络）。「print 输出顺序不可信」是并发诊断的第一课。出处：PHP 中文站「如何在 Python 生产环境下调试异步死锁与任务阻塞问题」
专家题二（入口规范·深水区）：生产环境为什么不推荐裸用 asyncio.run？
asyncio.run 退出时会强制 cancel 所有未完成任务并静默关闭循环——异常未处理时静默退出、死锁信号（哪些任务没跑完）被掩盖。生产实践：手动管理循环，退出前用 asyncio.all_tasks() 检查残留任务、cancel 后 gather 收尾。出处：Runebook（Python 官方文档中文版）
