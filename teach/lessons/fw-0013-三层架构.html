三层架构

本课目标

完成本课后，你将能：

  1. 画出经典三层并说出每层职责与依赖方向（接口 → 业务 → 数据）
  2. 说清模型分化：model / BO / DTO 三种模型的定位与转换位置
  3. 讲出依赖倒置在分层里的含义：上层定义接口，下层实现
  4. 对照本课已完成代码（api/service/schema/model）说出哪层对应哪段

知识速览

先花几分钟把核心机制过一遍——细节都在《13.三层架构》里，测验和面试会考。

经典三层

  • 接口层：接收请求、参数校验、返回响应（本课的 app/api/ + schema DTO 校验）
  • 业务层：业务规则与用例编排，不关心 HTTP 细节（本课的 app/service/）
  • 数据层：持久化与查询（本课的 app/model/ + core/database）
  • 依赖方向：上层依赖下层；下层不得反向 import 上层

模型分化（课件示例）

  • model：持久化模型（password_hash、is_deleted 软删标记——只属于数据库的字段）
  • BO：业务对象，按领域语义拆分（UserIdentity/UserInfo 分组，password_hash 藏在 identity 里）
  • DTO：传输对象，只带客户端需要的字段（id/username/email——绝不出现 password_hash）
  • 转换发生在层与层之间：model ↔ BO ↔ DTO，各层只见自己需要的形状

分级测验

🌱 初级测验 · 概念

1. 经典三层是哪三层？
课件经典三层图：接口层（接请求回响应）→ 业务层（业务规则）→ 数据层（持久化）。对应本课代码 app/api/、app/service/、app/model/。
2. 课件模型分化示例里，password_hash 只出现在哪个模型？
课件代码：model.User 有 password_hash（持久化需要）；BO.UserIdentity 分组持有它（业务语义）；DTO.User 只有 id/username/email——密码哈希永远不出服务端边界。
3. 分层的依赖方向是？
经典三层箭头：请求从接口层进入，逐层向下；下层不知道上层的存在（service 不 import FastAPI 就是 ch07/ch08 边界原则的来源）。

🌿 中级测验 · 应用

4. is_deleted 软删除标记应该放在哪个模型？
课件 model.User 注释：is_deleted 是软删除标记——数据库持久化策略，业务层关心「用户是否有效」（可转化为 BO 语义），DTO 通常连字段都不暴露（被删用户对外就是不存在）。
5. 本课代码里 schema/ 的 DTO 对应模型分化的哪一类？转换在哪发生？
ch07 的 ProductResponse/CategoryBrief 就是 DTO；ProductService 里 ProductResponse.model_validate(product) 完成 model→DTO 转换——转换位置在层边界上（service 对外出口）。
6. 为什么 model.User 的字段到了 BO 里要拆成 UserIdentity 和 UserInfo 两个组？
课件 BO 示例：登录只关心 UserIdentity（username+password_hash），改资料只关心 UserInfo（email+phone）——BO 按用例聚合字段，业务代码不用扛着一整个扁平模型到处跑。

🎯 高级测验 · 综合

7. 依赖倒置在分层架构里的含义是？
课件依赖倒置图：业务层不该依赖「具体的数据库实现」，而是依赖「存取接口」——数据层提供实现。本课的落地：ch08 的 Depends/get_db 注入就是「上层声明需要什么，实现由容器交付」。
8. 有人把 ORM 对象直接 return 给接口层，违反了三层里哪条原则？
模型分化的意义就是「各层只见自己需要的形状」：ORM 对象带着 password_hash/is_deleted 直达接口层，既泄露出 DTO 不该有的字段，也让接口层绑死数据层结构——ch07 的 DTO 边界原则就是本课的实践。
9. 三层架构最大的代价是什么？课件为什么不一开始就三层？
课件章节顺序就是答案：01-04 章一个 main.py 能跑通全流程，07 章引入 service、08 章引入 api、13 章才系统讲分层——三层带来 model↔BO↔DTO 的转换代码与抽象成本，是业务复杂度上来了才该付的价钱。过早分层是过度设计。
