会话速查表

配合《会话互动教学课程》使用。

Session 骨架（本章 agent/session.py）

import json
import uuid
from pathlib import Path


class Session:
    def __init__(self):
        self.id = str(uuid.uuid4())      # 会话的持久身份
        self.messages: list[dict] = []   # 只增不改的消息列表

    def add_message(self, message: dict):
        self.messages.append(message)    # 追加，永远追加

    def save(self):
        sessions_dir = Path(__file__).parent / "sessions"   # 模块同级目录，不依赖 CWD
        sessions_dir.mkdir(parents=True, exist_ok=True)
        data = {"id": self.id, "messages": self.messages}
        with open(sessions_dir / f"{self.id}.json", "w", encoding="utf-8") as f:
            json.dump(data, f, ensure_ascii=False, indent=2)   # 中文不转义，便于排查

    @classmethod
    def load(cls, session_id: str):
        path = Path(__file__).parent / "sessions" / f"{session_id}.json"
        with open(path, encoding="utf-8") as f:
            data = json.load(f)
        session = cls()                  # 构造函数先生成一个新 uuid4……
        session.id = data["id"]          # ……再被文件里的 id 覆盖（保持同一身份）
        session.messages = data["messages"]
        return session
id
str(uuid.uuid4())；也是磁盘文件名 sessions/<id>.json。
messages
list[dict]，每项形如 {"role": …, "content": …}；本章删除了旧的 agent/message.py，统一用 dict。
add_message
只做 append——会话层的铁律就写在这一个方法里。
load
classmethod；先 cls() 再覆盖 id / messages。不做参数校验：文件缺失时抛 FileNotFoundError。

双入口调用矩阵（agent/model.py）

调用形态发给 API 的内容调用后会话变化典型用途
invoke(list[dict])传入的列表本身无（不持有会话）一次性请求、无记忆脚本
invoke(Session)session.messages追加 response.choices[0].message.to_dict()非流式多轮
invoke_stream(list[dict])传入的列表本身无流式单次输出
invoke_stream(Session)session.messages流结束后追加 {"role": "assistant", "content": full_content}，有思维链则补 msg[reasoning_field] = full_reasoning_content本章课件的多轮对话
分流写法
if isinstance(messages, Session): session = messages; messages = session.messages——一个入口吃两种参数。
自动回写
拿到回答后由 model 负责往会话里写 assistant 消息：调用方不要再手工 add 一条，否则历史里出现连续两条 assistant。
惰性陷阱
invoke_stream 是生成器：不迭代 = 请求不发出、回写不执行；中途 break = 请求已花钱、输出已展示，但那条 assistant 消息永远进不了历史。
思维链字段
先试 delta.reasoning_content，没有再试 delta.reasoning；最终按实际出现过的字段名写回，保证推理上下文不丢。

缓存与成本：三笔账

账目公式 / 事实工程动作
单轮 prompt 长度 第 n 轮 ≈ c + n·t（c = 系统提示词等固定开销，t = 每轮新增均值） 把固定部分放最前面；可变内容放最后
累计发送量 S(n) = Σ(c + k·t) = n·c + t·n(n+1)/2 = O(n²) 会话越长越贵；压缩要追加而非改写前缀
缓存命中 服务商先检查 prompt 的开头部分（prefix）是否已缓存：命中则复用，未命中则整段从头处理并缓存前缀 历史只增不改，新消息追加到 messages 数组末尾；观察 usage.prompt_tokens_details.cached_tokens
本章两条最佳实践
① 历史上下文不可修改——不满足会导致难以命中模型服务商的 prompt cache；② 上下文中应保留思维链——不满足会导致推理上下文丢失、模型回复质量下降。
持久化成本
save() 每轮 json.dump 整份 messages：历史长 n 时单次 O(n)、n 轮累计 O(n²) 的序列化与磁盘写。改成 append-only 增量写入即降到 O(n)，并可用「写临时文件 + rename」保证原子性。
前缀杀手
删早期消息、把历史整体重写成摘要、每轮往系统提示词里注入当前时间/用户名（见第 16 章「保持静态」）。
边界
会话 id 只是选择历史的键，不认证用户、不授权访问——load() 直接按文件名读 JSON，拿到 id 就能读整段对话，应用侧必须自己做鉴权。

易错点清单

重复的 assistant 消息
传了 Session 又手工 add_message(assistant) → 历史里两条连续 assistant，上下文被污染。
没消费生成器
resp = model.invoke_stream(session) 之后不迭代，请求根本没发；此时手工塞进去的 assistant 消息会被当成模型说过的话。
id 被换掉
恢复会话时不用 load() 而自己 Session() 再灌 messages，会得到一个新 id，磁盘上从此有两份互不相干的历史。
中文乱码式难排查
json.dump 忘了 ensure_ascii=False，会话文件里全是 \uXXXX，出问题时人工读不了。
会话目录绑死 CWD
把 sessions 写成相对路径，换个目录启动就找不到；本章用 Path(__file__).parent 定位。
没有窗口管理
历史只增不改却不设上限，最终会撞模型的上下文窗口上限直接报错——压缩要提前做，且以追加的方式做。
