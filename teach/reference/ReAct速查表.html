ReAct速查表

配合《ReAct互动教学课程》使用。

ReAct 主循环：三拍一出口

def query(q: str, session: Session, model: Model):
    session.add_message({"role": "user", "content": q})
    # ReAct Loop
    while True:
        model.invoke_stream(session)                      # ① 想：推理 + 可能发起 tool_calls
        call_msg = registry.invoke(session.messages[-1])   # ② 做：执行 tool_calls
        if call_msg is None:
            break                                          # 出口：本轮没有工具调用 → 收尾
        else:
            session.messages += call_msg                   # ③ 看结果：role=tool 写回上下文
核心机制
推理轨迹与任务动作交替（interleaved）出现：推理负责诱导、跟踪、更新行动计划与处理异常；动作负责接入外部信息源取回新信息。
三个动作
invoke_stream（想）→ registry.invoke（做）→ += call_msg（看结果）；下一轮又是「想」。
循环出口
registry.invoke() 返回 None——这条 assistant 消息里没有 tool_calls，当前 content 即最终回复。
为什么不能省第 ③ 步
结果不回流，模型每轮看到的上下文都停在「我要调用工具」，会重复发起同一调用：命令被重复执行、token 持续消耗、循环不收敛。
消息顺序硬约束
assistant（含 tool_calls）→ tool（每条结果带 tool_call_id）→ 再次请求；role=tool 的消息必须回应前面那条带 tool_calls 的 assistant 消息。

工具与参数速查

预注册工具作用
read_file读取文件内容
write_file写入文件内容
bash_command执行 shell 命令（30 秒超时）
subprocess.run(
    command,                       # 要执行的命令字符串
    shell=True,                    # 经 shell 执行（管道、通配符、变量展开可用）
    executable="/bin/bash" | "cmd" # shell=True 时：替换默认 shell（POSIX 默认 /bin/sh）
    capture_output=True,           # 捕获 stdout + stderr（不是打印）
    text=True,                     # 文本模式：stdout/stderr 是 str
    timeout=30,                    # 秒；到期 → 子进程被 kill 并 wait → 重抛 TimeoutExpired
)
  • 返回值约定：本章工具把「失败」也当成正常返回值（[退出码 N] + stderr），因为对模型来说错误信息就是可用的环境反馈。
  • 但超时没兜底：TimeoutExpired 会从 tool(**args) 一路抛穿，直接打断 ReAct 循环——生产里应捕获并翻译成 role=tool 的内容。
  • shell=True 的安全提示：官方要求先读 Security Considerations——shell 被显式调用后，转义与注入防范由应用负责（shlex.quote 等）。

易错点与设计模式

易错点现象修法
结果不写回上下文模型反复发起同一个工具调用，命令被重复执行保留 session.messages += call_msg
丢掉 assistant 消息出现「无主的 role=tool 消息」，请求被拒 / 模型对不上号先留含 tool_calls 的 assistant，再追加 tool 结果
工具名未注册self._tools[name] 先抛 KeyError，「无此工具」提示永远执行不到改 self._tools.get(name)，或捕获后作为 tool 内容回传
只循环「有工具就调」模型绕圈时不收敛，费用与延迟失控补显式停止条件（最大迭代 / 时限 / 预算 / 连续失败数）
直接暴露 shell越权执行、注入风险沙箱 + guardrails：限目录、限命令、限时、限可写范围、审计日志
设计模式（分析.md 结论）
发布-订阅 → EventEmitter；策略模式 → Reasoning / Content / ToolCalls 三类 Builder；装饰器模式 → @tool；工厂模式 → create_params_model；单例模式 → 全局唯一 registry。
数据流一句话
用户输入 → add_message → Model.invoke → 拆成 Reasoning / Content / Tool Calls → Registry.invoke 执行 → 结果写回 → 再次 invoke，直到没有工具调用。
