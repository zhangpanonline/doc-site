MCP协议速查表

配合《MCP协议互动教学课程》使用。

协议内核三要素

一句话：MCP 定义了 Agent 与外部工具的通信标准，落点是「角色 + 传输 + 消息格式」三件事。

要素取值记住这一句
通信角色MCP Client（通常是 Agent）↔ MCP Server（工具提供者）任何匹配 MCP 协议的程序都能当 Client——inspector 就是拿来当 Client 用的
通信方式stdio / http（现行规范称 Streamable HTTP）stdio 走 stdin·stdout 在本地进程间通信；HTTP 是独立进程、可多客户端
通信格式JSON-RPC 2.0官方硬约束：All messages MUST follow the JSON-RPC 2.0 specification
// JSON-RPC 2.0 信封（课件示例）
{
  "jsonrpc": "2.0",
  "id": "req-123",          // MCP 额外约束：不得为 null，同一会话不得重号
  "method": "tools/call",   // initialize | tools/list | tools/call | ...
  "params": { ... }         // 可选
}

为什么值得有标准：没有协议时，$M$ 个 Agent 对接 $N$ 个工具要做 $M \times N$ 套适配；有了协议，各方各自实现一次即可，总量降到 $M + N$。

一次会话的三条消息

消息方向作用
initializeClient → Server（Server 回响应）必须是第一次交互：协商协议版本、双方 capabilities、交换 clientInfo / serverInfo
tools/listClient → Server发现工具列表：工具名、描述、参数 Schema（前提是 Server 在 initialize 里声明了 tools 能力）
tools/callClient → Server调用工具：params 里带工具名与实参，响应回来的是工具结果
生命周期三段
Initialization（能力协商 + 版本协商）→ Operation（正常通信）→ Shutdown（优雅关闭）。
能力协商规则
声明才可用：Server 支持工具就必须声明 tools 能力；Client 看到能力声明后才应发 tools/list。工具一个都没出现，先查 initialize 的 capabilities。
消息配对
请求带 id，响应回同一个 id；通知（notification）没有 id，不需要应答。

stdio vs http（Streamable HTTP）

stdioStreamable HTTP
谁启动Client 把 Server 作为子进程启动Server 是独立进程，自行部署
信道标准输入 / 标准输出，消息以换行分隔、不得内含换行HTTP POST（发消息）+ GET（开 SSE 流接收）
客户端数一对一可处理多个客户端连接
日志往哪写只能写 stderr；stdout 只允许出现合法 MCP 消息stderr 不被 Client 捕获，用服务端日志聚合 / OpenTelemetry
必备请求头—POST 必须带 Accept: application/json, text/event-stream
安全底线进程隔离，无网络暴露校验 Origin 防 DNS rebinding；本地只绑 127.0.0.1；实现认证

选型判据：看谁在用、数据边界与运维成本——本机文件/凭据留 stdio；团队共享、集中升级走 HTTP，并把安全三件套补齐。

MCP 聚合站
awesome-mcp-servers、mcp.so、smithery.ai、glama.ai——找现成 Server 从这里起步。
易错点 ①
stdio Server 里用 print() 打日志 → 污染 stdout，Client 解析失败。日志一律 stderr。
易错点 ②
跳过 initialize 直接调工具 → 违反「初始化必须是首次交互」，能力与版本都没谈。
易错点 ③
把 id 写成 null 或重复使用 → MCP 明确禁止（标准 JSON-RPC 允许，MCP 不允许）。
