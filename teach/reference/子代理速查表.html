子代理速查表

配合《子代理互动教学课程》使用。

为什么要子代理：一条上下文 vs 多条上下文

维度单代理一个轮次跑完主代理 + 子代理
消息历史同一条 session.messages 持续增长每个子代理 Agent() 各自新建会话，主会话只留结论
典型动作reasoning + 一个超级庞大的 ReAct 循环主代理只做宏观需求分析/方案设计，其余派活
上下文内容ORM、迁移、DTO、Service、接口、测试的调用与结果全在里面子代理各自只处理「实现数据层 / DTO / 接口 / 测试」中的一件
结果形态过程即结果，模型自己带着全部细节只回传最后一条消息的 content（摘要）
可回看agent.session.save() 一份总会话总会话 + 每个 <name>-<id>.json 子会话

课件原话：单代理「最终会得到一个超级庞大的上下文，这会带来诸多问题」；子代理就是把这些过程挪出主上下文的手段。

create_agent 工具速查

@tool(agent_config="每个子代理的配置。每个子代理要配置名称、用户提示词…")
def create_agent(agent_config: list[dict[str, str]]) -> str:
    results: list[dict[str, str]] = []
    results_lock = threading.Lock()
    threads: list[threading.Thread] = []

    def run_sub_agent(name: str, query: str) -> None:
        agent = Agent()                      # ① 独立会话 = 上下文隔离
        responses = agent.invoke(query)      # ② 只带 query，不继承主会话
        content = responses[-1].message.get("content", "")   # ③ 只取摘要
        agent.session.save(f"{name}-")       # ④ 子会话落盘，可单独回看
        with results_lock:                   # ⑤ 共享列表加锁
            results.append({"name": name, "result": content})

    for config in agent_config:
        thread = threading.Thread(target=run_sub_agent,
                                  args=(config.get("name", "unnamed"),
                                        config.get("query", "")))
        threads.append(thread); thread.start()   # ⑥ 先全部启动
    for thread in threads:
        thread.join()                            # ⑦ 再逐个等待
    return json.dumps(results, indent=2, ensure_ascii=False)
环节写的是什么起什么作用
入参 agent_config[{"name": "sub-agent-1", "query": "…"}]name 给结果贴标签，query 是子代理的初始用户提示词（唯一任务交代）
返回json.dumps([{"name":…, "result":…}], ensure_ascii=False)主代理拿到的是结构化摘要列表，不是子代理的对话全文
注册registry.register(create_agent)写进 agent/tool/__init__.py，与 read_file/use_mcp/use_skill 同一条注册链

实测调用（课件原文）：

from agent.tool.create_agent import create_agent
resp = create_agent(agent_config=[
    {"name": "sub-agent-1", "query": "这是一个测试，请说：你好！"},
    {"name": "sub-agent-2", "query": "this is a test, reply: Hello!"},
])
print(resp)

并发三件事：start / join / Lock

thread.start()
把任务交给一个独立线程，「arranges for the object's run() method to be invoked in a separate thread of control」——启动顺序 ≠ 执行顺序，谁先跑完由调度决定。
thread.join()
「blocks the calling thread until the thread whose join() method is called terminates」。课件在全部 start() 之后统一 join，实现「等待所有子代理完成，汇总结果」；它保证都完成，不保证按序完成。
threading.Lock
用于保护共享数据（这里是多线程同时 append 的 results）。它保证写入不丢、不撕裂，不决定谁先写——返回 JSON 里 name 的顺序不可依赖。
未处理异常
线程 run() 里的异常交给 threading.excepthook()，默认打到 stderr，不会传播到 join 的主线程：表现为「结果静默少一项」，而不是整轮失败。
GIL 提醒
CPython 下「only one thread can execute Python code at once」；线程适合 I/O 密集（模型请求、网络、文件），CPU 密集要用 multiprocessing。

易错点清单（子代理专属）

  • 以为子代理能看到主代理的上下文：agent = Agent() 新建会话，子代理只知道 query。任务描述必须自带目标、输出格式、可用工具、边界。
  • 把隔离当成万能：隔离的只是消息历史——工作目录、文件系统、registry 里的工具是共用的，两个子代理完全可能写到同一个路径。
  • 依赖结果顺序：results 的先后由线程调度决定；要稳定顺序就自己按 name 重排或按索引写入。
  • 没做失败处理：一个子代理抛异常 → 少一项结果；主代理会把不完整当完整继续往下走。应 try/except 后回传 {"name":…, "error":…}。
  • 没有超时：无参 join() 会无限等；用 join(timeout) 并在返回后 is_alive() 判定是否超时。
  • 没有并发上限：agent_config 由模型生成，可能一次派几十个；按任务复杂度给预算并在工具层设上限。
  • 结果无限膨胀：把子代理的超长产物整段塞回主上下文，等于把省下的上下文又还回去；大产物落盘、只回传路径与摘要。
  • 成本低估：多代理系统「use about 15× more tokens than chats」，简单任务别拆。

什么时候拆 / 什么时候别拆

信号判断
子任务之间真正独立、可同时推进（多条搜索、多份素材、多个独立文件）适合并行子代理
信息量超出单条上下文窗口，需要多份「压缩后的结论」适合拆（先用子代理压缩，再汇总到主代理）
过程又长又脏（跑测试、抓文档、处理日志），结果只要一句结论适合拆（隔离高噪声输出）
步骤有硬依赖（数据层没建完就写测试）别并行、别拆；先由主代理定契约，再按依赖分层
需要频繁来回澄清、多阶段共享同一批上下文留在主会话里做
流程明确、任务很小、延迟敏感别拆；下单代理更快更便宜

拆了之后补四件套：失败结构化回传 · 超时与并发上限 · 产物外置到文件系统 · 每个子代理单独落盘可观测。
