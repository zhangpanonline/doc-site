## 为什么需要显式锁（官方定位）

官方原文：PG 提供多种锁模式用于控制对表中数据的并发访问——这些模式可以用在 **MVCC 无法给出期望行为的情境**中（如应用需要"先检查再决定"的原子性、跨表一致性）。

同时官方强调：**大多数 PostgreSQL 命令会自动获取恰当的锁**（原文例子：TRUNCATE 无法安全地与同一表上的其他操作并发执行，因此它获得一个 **ACCESS EXCLUSIVE** 锁）——绝大多数场景你不需要手动 LOCK。

**观察锁**：`pg_locks` 系统视图列出当前所有未解除的锁。

## 表级锁 vs 行级锁

官方给出两级：

| 级别 | 说明 | 高频点 |
|---|---|---|
| **表级锁** | 多种模式（ACCESS SHARE ~ ACCESS EXCLUSIVE）；`LOCK` 命令可显式获取 | 名字含 row 的（如 ROW EXCLUSIVE）**也是表级锁**——官方原文：这些名称是历史遗产 |
| **行级锁** | 行级（FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE） | `SELECT ... FOR UPDATE` 是"先查后改"原子化的标准姿势 |

## 死锁

官方在 §13.3.4 专章讨论死锁：两个事务互相等待对方持有的锁。要点：

- PG **自动检测死锁**并终止其中一个事务（报 deadlock detected）——不会无限挂起
- 预防：**一致的加锁顺序**（所有事务按相同顺序获取锁）、缩短事务、减少锁的持有时间
- 应用侧处理：捕获死锁错误并**重试**（死锁是并发系统的正常现象，重试是标准应对）
