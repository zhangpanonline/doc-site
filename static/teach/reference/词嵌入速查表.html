词嵌入速查表

配合《词嵌入互动教学课程》使用。

为什么需要词嵌入

Token ID 的问题说明
不能表示语义ID 只是一个文字符号的编号；单看编号无法表达它背后丰富的语义
不能做数学运算$33256 + 11789$ 没有含义——ID 之间的加减乘除无意义
结论需要用更多维度描述一个 token → 这就是词嵌入要解决的问题

核心概念

词嵌入（word embedding）
把一个 token 转成多维度数字向量的过程；「嵌入」的本意是把低维离散对象镶嵌、植入到连续的高维几何空间。
向量空间中的「接近」
把维度值放进空间，语义相近的 token 距离更近（例：$苹果\approx Apple$）。
向量运算关系
$国王 - 王后 \approx 男人 - 女人$、$男人+医生\approx男医生$、$2×开心≈狂喜$——语义关系在向量空间里变成了算术关系。
工程形态
一张矩阵 $E \in \mathbb{R}^{|V| \times d}$：$|V|$ = 词表大小，$d$ = 每个 token 的维度；第 $i$ 行就是 ID 为 $i$ 的 token 向量。
只规定维度个数
我们只规定有多少个维度，每一维的含义与取值交给训练去学——永远不要告诉机器答案。

上下文长度 vs 上下文窗口

概念含义类比
上下文长度本次实际传入模型的 token 数量用量
上下文窗口长度模型能容纳的最大 token 数量（硬上限）容量
约束：上下文长度 ≤ 上下文窗口长度
超出：被截断，或直接报错

做长度预算时两个数都要看：模型上限决定能不能放，本次用量决定要花多少 token 与费用。

易错点

  • 把 Token ID 当特征直接喂给模型（丢掉语义与距离关系）
  • 以为每一维的含义是人类指定的（实际只有维度个数是人为规定）
  • 把「上下文长度」与「上下文窗口长度」混用，算错 token 预算
  • 把「向量接近」理解成「字符串像」——它衡量的是语义，不是字面
