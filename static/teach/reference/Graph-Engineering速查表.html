Graph-Engineering速查表

配合《Graph-Engineering互动教学课程》使用。

三要素（官方定义）

组成官方定义职责归属
State共享数据结构，代表应用当前时刻的快照；通常用共享的 state schema 定义数据
Nodes编码 Agent 逻辑的函数：接收当前 state → 计算或副作用 → 返回更新后的 state计算
Edges决定下一个执行哪个节点的函数；可以是条件分支或固定跳转控制流

官方原话：把这些节点与边组合起来，就能构建会随时间演进状态的复杂循环工作流；真正的威力来自「如何管理这个状态」。

图 vs 线性 loop：怎么选

流程形状用什么理由
单主干：思考 → 调工具 → 再思考线性 loop（第 33 章）终止条件简单，while 循环足够
条件分支：按中间结果走不同处理链图分支必须显式建模，否则退化成嵌套 if
并行 + 汇合：多子任务同时跑再汇总图需要汇合点与状态合并规则
回退/重规划：失败回到上游节点图需要回到指定节点而不是重跑整条链

判断标准是流程形状，不是任务大小；只有一条主干时，上图反而增加复杂度。

三个工程约束

终止必须显式
条件边要有能走到结束节点的路径；否则循环只能靠运行时的步数/递归上限兜底并报错。
状态要可观测
节点只返回「对状态的更新」，因此每一步变化都可追踪；调试与回放依赖状态快照。
节点应尽量幂等
失败重试与断点恢复都会重放节点——副作用（写文件、发请求）要自己防重复，或挪到人工检查点。

落地检查清单

状态设计
  □ 每个字段都有明确归属与写入者（避免多人乱写）
  □ 能表达「进度 / 轮次 / 是否通过」——条件边的判据必须来自状态
  □ 并行分支写同一字段时，定义了合并规则（累加 / 按键合并 / 取最新）

节点设计
  □ 一个节点只做一件事，返回状态更新而不是改全局变量
  □ 带副作用的节点做了幂等或去重（key 唯一化）
  □ 节点的失败语义明确：抛错中断，还是写进状态交给条件边处理

连接与终止
  □ 至少有一个人工可达的结束出口
  □ 循环分支有收敛判据（质量阈值 / 问题清单清空 / 轮次上限）
  □ 断点恢复：能从快照继续，而不是重跑整图

易错点

  • 把 State 当节点私有变量——它是共享快照，所有人都读写同一份
  • 条件边只写「继续」，没有「结束」，靠步数上限收场
  • 判断依据藏在节点局部变量里，条件边读不到
  • 并行分支各写各的、后写覆盖前写（缺合并规则）
  • 为了「看起来先进」而上图：单主干任务用循环更简单可靠
