Prompt-Engineering速查表

配合《Prompt-Engineering互动教学课程》使用。

它经营上下文里的哪两格

上下文里的位置谁在管提示词工程能直接写吗
系统提示词提示词工程（第 16 章的原则：精简/自洽/全局约束/保持静态/结构化）能——但要求保持静态
用户问题提示词工程能
历史消息 / 工具结果上下文工程（第 31 章）不能——由会话与工具运行时产生
模型推理与回复模型自己不能——回复是模型的输出，不是可写对象

一句话：提示词工程 = 在文本进入模型之前，把指令写清楚。它离模型最近，但管不到模型内部的推理，也管不到工具返回了什么。

定义与四要素

定义（《Prompt Engineering Guide》）
一门相对年轻的学科，用于开发和优化提示词，以便高效地使用语言模型完成各类任务与应用；同时它也是理解大模型能力与局限的功夫。
要素 ①：指令
想要模型执行的特定任务或指令（Instruction）。
要素 ②：上下文
包含外部信息或额外的上下文信息（Context）。
要素 ③：输入数据
用户输入的内容或问题（Input Data）。
要素 ④：输出指示
指定输出的类型或格式（Output Indicator）。

四要素是可选组合，不是必须全填；关键是把「你想让模型做什么」写到模型不会误解。

通用技巧主线：迭代

1) 从简单开始（不要一上来写 400 行）
2) 逐渐添加元素与上下文
3) 过程中不断实验、对比效果
4) 具体明确，把指令放在提示开头
5) 用 ### / --- / XML 标签等清晰分隔符把「指令」与「上下文」分开

反模式：把提示词当一次性任务，上线后不再维护——模型的输入在变，提示词也需要迭代。

它站在哪：工程方法论序列

层管什么一句话判据
Prompt Engineering（30）文本进入模型之前的指令写法「把话写清楚」
Context Engineering（31）整个上下文状态：放什么、留多久、怎么压缩「管好整张桌子」
Harness Engineering（32）情境与状态、护栏（最小权限）、可观测「配好马具」
Loop Engineering（33）让 Agent 自我推动的循环：终止条件、预算、重试「让它自己转起来、还能停下来」
Graph Engineering（34）用节点与边组织多步流程与状态流转「把流程画成图」

官方口径（Anthropic《Effective context engineering for AI agents》）：上下文工程是提示词工程的自然演进，而不是替代——提示词工程负责「把指令写好」，上下文工程负责「每一轮都维护最优的 token 集合」。

易错点

  • 把「当前时间 / 当前用户」这类每轮变化的信息写进系统提示词——违反第 16 章的「保持静态」，也破坏缓存前缀
  • 用「加长系统提示词」解决跑偏问题（上下文状态问题要在第 31 章那层解决）
  • 把提示词工程当全部：它只是 Agent 工程的第一层
  • 指令与上下文混在一段里、没有分隔符，模型难以区分层级
