Context-Engineering速查表

配合《Context-Engineering互动教学课程》使用。

一句话定调

维度提示词工程上下文工程
管什么指令怎么写、怎么组织此刻窗口里该有哪几样东西（系统提示词、用户问题、历史、工具、MCP、Skill、外部数据）
动作写与改措辞编排（放什么、排在哪、什么时候加）+ 治理（可信、膨胀）
目标一次任务说清楚在多轮与长任务里持续维持输出质量

硬判据：上下文唯一的影响着模型的输出质量。提法来源：2025 年 6 月，Shopify CEO Tobi Lütke 表示更喜欢用「上下文工程」替代「提示词工程」——因为它更准确地描述了为 LLM 提供充分信息以完成任务的核心技能。

注意力偏差（Attention Bias）四条

特点定义工程含义
长度稀释上下文越长，注意力被分散到更多 token 上，关键信息权重被摊薄，模型更容易漏掉信息「都放进去」≠「都被读到」；先问这条信息是否服务于当前目标
长度分布外（OOD）上下文长度超过训练语料常见长度后，模型回复的置信度会有明显下降降级是渐变不是硬悬崖：窗口没爆也可能已经不准
信噪比噪声越多，越挤占模型对关键信息的注意力预算工具原始输出、过期中间结论是噪声；只回相关字段，其余落到窗口之外
首尾强化对开头（系统提示词）和结尾（最近输入）的关注天然高于中间（位置偏差 / Positional Bias）关键约束放开头或结尾；中间只放可被检索的细节

一句话：注意力的预算有限——上下文是取舍，不是收纳。

四类取舍：放什么 · 留多久 · 怎么压缩 · 排在哪

取舍判据常见做法
放什么是否服务于当前目标（关键约束、未解决的结论、思维链）给路径/查询这类轻量引用，让 Agent 按需把内容拉进来；剔除无关整段
排在哪首尾强化 + 缓存前缀静态内容（系统提示词、工具规范）放最前且逐字不变；动态事实靠后
留多久还要不要它参与后续推理历史只增不改；工具原始结果用完即可清理，完整数据留在窗口之外
怎么压缩先最大化召回，再提升精度用摘要替代长历史时以追加形态出现；最轻的一种是清掉已用过的工具结果

与第 16/17 章接上：缓存友好 / 成本友好

原则来自违反的代价
系统提示词保持静态（精简、自洽、全局约束、结构化）16.系统提示词前缀每轮都变 → 缓存难命中，token 成本上升
历史上下文不可修改、新消息追加到末尾17.会话难以命中服务商的 prompt cache，整段从头处理
上下文中保留思维链17.会话推理上下文丢失，模型回复质量下降
无状态 API 每轮全量重发历史17.会话第 n 轮 prompt 长 $c + n t$，前 n 轮累计 $O(n^2)$——会话越聊越贵
系统提示词（静态、逐字不变）        ← 缓存前缀
  用户问题 / 工具结果（只放相关字段） ← 动态、靠后
  历史消息（只增不改，思维链不删）    ← 追加到末尾
  当前输入                            ← 首尾强化的“尾”
编排
提示词、用户问题、工具、MCP、Skill 等内容在上下文中如何排列？什么时间加入什么内容？
治理 · 可信
如何确保上下文的内容安全可信？工具返回、检索结果、外部网页都是不可信输入。
治理 · 膨胀
如何在持续的循环中，管理和优化不断膨胀的上下文？（压缩、清理工具结果、上下文之外的笔记/记忆、子代理隔离）
验证抓手
每轮上下文组成与长度曲线（$O(n^2)$）、缓存命中 token 占比、同一组任务改造前后的回答质量对比——三个一起看，缺一个都可能自欺。
