知识速览

本章文档很短，但它是一个「框架性」的章节：名词先立住，再回头把前几章写过的代码按「外壳」视角重读一遍。测验和面试只考本章文档 + 18/19/20/21 章已经写过的判据。

Harness 是什么：从「选马」到「做马具」

  • 词源：Harness 意为马具。本章文档引的原作者判断是「马具对骑乘的影响非常大」，因此该词也被译为「驾驭工程」/「缰绳工程」
  • 核心主张：任务落地时，应把更多注意力从「选择什么马（模型）」转移到「选择什么样的马具（如何驾驭模型）」——同一匹马，马具不同，结果可以完全不同
  • 工程化定义（本章文档给出的原始出处）：harness engineering 就是「每当发现 agent 犯错，就花时间设计一个方案，让 agent 永远不再犯同一个错」
  • 两种落地形态：更好的隐式提示（把每条错误沉淀成 AGENTS.md 里的一行）＋ 真正的可编程工具（让 agent 能自己验证「我做对了」的脚本，例如跑过滤后的测试、截图对比）

本章三大核心关注点（文档原文口径）

  • 情境与状态管理：确保 AI 在复杂、长周期任务中能获得正确的上下文信息，并记住任务状态，避免「失忆」和「跑偏」；强调 召回 → 规划 → 行动 这个顺序
  • 护栏：像给系统设置权限一样，严格管理 AI 能调用哪些工具、访问哪些数据；核心理念是最小权限原则——只给 AI 完成当前任务所必须的权限，以防误操作或恶意利用
  • 可观测：需要做详细的设计，保证三个问题都有答案——模型知晓是否完成了任务？判断的依据是什么？从哪里获取判断需要的信息？
  • 三者不是并列的清单，而是「知道自己知道什么（情境）→ 只被允许做该做的（护栏）→ 能证明自己做对了（可观测）」的一条链

落到课程代码：外壳的五个部件

  • 工具面：18 章给出工具定义的最小 Schema（type: "function" + name / description / parameters，required 列表）；19 章用 Pydantic 动态建模参数，封装出 Tool 类、@tool 装饰器与全局 registry
  • 权限：最小权限在本工程里的落点是「只注册当前任务需要的工具」——session.tools = registry.schemas() 决定模型能看见什么；另一层是执行前参数校验（Tool.__call__ 先 param_model(**kwargs) 再调原函数）
  • 可观测：EventEmitter + ModelListener 的事件流（一次挂全事件）、Session.print_friendly() 的轨迹复盘；而「判断任务是否完成」的信息必须来自环境——工具真实返回的结果、命令的退出码与报错，而不是模型的自我陈述
  • 错误处理：Tool.__call__ 用 try/except + traceback.format_exception 把异常转成字符串结果回灌会话——单个工具失败不会让进程崩掉，模型还能读到错误自我修正；代价是「失败」与「正常返回」形态相同
  • 人工检查点：有副作用的动作（写文件、跑命令）要能停下来等人拍板；现场用 Session.save() 落盘、Session.load() 读回，避免「重跑一遍」把长任务的时间与成本再烧一次

🌱 初级测验 · 概念

1. 本章用「马具」来解释 Harness，原作者的比喻想表达的是？
本章文档原文：Harness 一词意为马具，原作者的意思是「在任务落地的时候，我们应该把更多的注意力从选择什么马（模型）转移到选择什么样的马具身上（如何驾驭模型）」，因此它也被翻译为「驾驭工程」/「缰绳工程」。注意它是注意力分配的主张，不是说模型不重要——同一匹马，马具不同，骑乘结果差别很大。
2. 「像给系统设置权限一样，严格管理 AI 能调用哪些工具、访问哪些数据，核心理念是最小权限原则」——这是本章哪个核心关注点？
这是本章文档对护栏的原文定义，紧跟的一句是「只给 AI 完成当前任务所必须的权限，以防误操作或恶意利用」。情境与状态管理管的是「上下文与任务状态」，可观测管的是「是否完成、依据是什么、信息从哪来」，都不是权限问题。
3. 本章说情境与状态管理强调的顺序是？
本章文档写得很明确：情境与状态管理「强调 召回 → 规划 → 行动」，目标是避免 AI 在长周期任务中「失忆」和「跑偏」。顺序的含义是：先把该知道的上下文拉回来，再决定怎么做，最后才动手——而不是先动手再回头找依据。

🌿 中级测验 · 应用

4. 本章「可观测」问的第三问是「从哪里获取判断需要的信息」。结合 21 章的 Agent 循环，下面哪一项最符合这个要求？
本章把可观测拆成三问：模型知晓是否完成了任务？判断依据是什么？从哪里获取判断需要的信息？前几章的代码给出的答案是环境真值：18/19 章把工具执行结果包成 role: "tool" 的消息并回 session.messages，21 章的循环再用「这一轮还要不要调工具」这个程序化检查决定去留。「模型自称完成」是措辞不是证据；responses 的长度只反映循环跑了几轮，与完成无关；temperature 影响采样，不影响判据。
5. 19 章的 Tool.__call__ 用 try/except 包住参数校验与函数执行，异常时 result = "".join(traceback.format_exception(...))。从 harness 的「错误处理」视角看，这个设计的好处与代价分别是？
看 Tool.__call__ 的代码：result = "" 起手，try 里校验参数并调用原函数，except 里把完整堆栈字符串塞进 result，最后统一 return result。所以「崩溃」被换成了「一段文本」，这对长任务很友好（Agent 不会因为读了一个不存在的文件就整体挂掉）；但文本既是错误报告、也是正常返回值，模型没有结构化的「这是失败」信号，配合 21 章那个while True（没有停止条件），就可能出现「反复调用同一个必然失败的工具」这种烧钱循环——这正是本章护栏要补的位置，而不是靠提示词叮嘱模型「别重试」。
6. 要把「最小权限原则」落到这套 agent/ 代码里，最直接的做法是？
最小权限的定义是「只授予完成任务所必须的数据与操作」。在这套代码里，注册面就是权限面：registry 里没有的工具，registry.schemas() 就不会把它写进 session.tools，模型根本看不到、也就调用不了——这是硬边界。提示词只是软约束（模型可能无视、也可能被注入的文本带偏）；「保留注册但注释函数体」更糟：Schema 还在，模型会一直尝试调用一个不存在的实现。第二层落到 19 章的参数校验：Tool.__call__ 先 param_model(**kwargs)，参数不对就走异常分支，不会带着脏参数去执行。

🎯 高级测验 · 综合

7. 线上现象：模型连续 7 轮都在调用同一个 write_file，每次都失败、每次都再试一遍，进程一直不结束、成本持续上涨。按本章三个关注点，最合理的处置顺序是？
按本章的三关注点排序：没有观测就没有诊断——先要知道每轮到底发生了什么（工具名、参数、返回的错误文本、耗时），才谈得上修；护栏是把限制写进代码——最大迭代次数/预算上限 + 同一工具+参数重复失败的熔断 + 危险动作审批，官方明确提醒 agent 的自主性意味着更高成本与误差累积，常要设停止条件来保持控制；最后回到情境与状态管理——把「这条路试过、失败原因是 X」沉淀进会话或状态文件，下一轮召回时不再重走死路。换模型（B）跳过了诊断；只加提示词（C）是软约束，模型完全可以无视——它不是权限边界；给每次调用都加人工确认（D）在诊断之前就把效率压死，且没解决「为什么一直失败」。顺带一句：这个现象本身也是 harness engineering 的入口——把这次错误变成一条「永远不再犯」的机制（上限 + 熔断 + 验证脚本）。
8. 本章引用的原始判断是：harness engineering 就是「发现 agent 犯了一个错，就工程化一个方案，让它永远不再犯同样的错」。下面哪一项最符合这个判据？
原始出处把这件事分成两种形态：更好的隐式提示（AGENTS.md，每一行都来自一次具体的 bad behavior）与真正的可编程工具（截图、跑过滤测试等）；并且给出一条经验：只要给 agent 一个能验证自己工作的办法，它多半会自己修掉错误、并防止回归。所以判据是「可执行、可复现的验证」，不是「再叮嘱一句」（叮嘱没有新信息，下一轮还会犯）、也不是换模型/调温度（那是换马和调马的脾气，不解决「它无法判断自己错了」这个根因）。C 同时命中两种形态，还天然带来一条可观测的判据。
9. 长周期任务里 Agent「失忆」：忘了前面已经确认过的约束，开始跑偏。按本章「情境与状态管理」，最对症的修法是？
本章对情境与状态管理的要求是「确保 AI 在复杂、长周期的任务中，能获得正确的上下文信息，并记住任务状态，避免失忆和跑偏」，并强调召回 → 规划 → 行动。关键词是「获得」与「管理」——状态由外壳负责维护和注入，不是模型的记忆责任：18/19/20/21 章里 session 管消息与工具 Schema、每轮把工具结果并回 session.messages、Session.save() 把会话落盘、Session.load(session_id) 读回，这些就是召回的基础设施。A 是「把上下文写成墙纸」，越长越稀释重点；B 与目标相反（跑偏时更需要收敛）；C 把状态管理托付给模型的自我复述，恰恰是「失忆」时最先失效的那一环。
