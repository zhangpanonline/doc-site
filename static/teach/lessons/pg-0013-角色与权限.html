角色与权限

本课目标

完成本课后，你将能：

  1. 说出 GRANT 的两种变体（对象特权 / 角色成员资格）与特权的三来源并集
  2. 解释 PUBLIC 的官方语义（所有角色含未来角色）与「授权选项不能授予 PUBLIC」

知识速览

先花几分钟把核心机制过一遍——细节与测验依据都来自官方文档 GRANT 参考 与 §5.8。

GRANT 两种变体（官方要点）

  • ① 对象特权：表/列/视图/函数/模式等对象上的特权，已授予的叠加
  • ② 角色成员资格：A 成为 B 的成员、继承 B 的特权
  • 角色实际特权 = 直接授予 + 成员角色特权 + PUBLIC 特权（三源并集）
  • PUBLIC：隐式定义的、总是包含所有角色（含未来创建）的组
  • WITH GRANT OPTION 可转授；不能授予 PUBLIC（官方）；对象拥有者默认全权

行级安全 RLS（官方要点）

  • 启用后所有普通访问必须被策略允许；无策略 = 默认否定（所有行不可见不可改）
  • 表的拥有者通常不受行安全策略限制（FORCE 后同样受限）；超级用户与 BYPASSRLS 角色始终绕过 RLS；TRUNCATE/REFERENCES 不受限
  • 策略可限定命令（ALL/SELECT/INSERT/UPDATE/DELETE）与角色
  • 策略表达式先于用户查询条件求值，不返回 true 的行不被处理——多租户隔离机制

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与官方文档覆盖的内容。

🌱 初级测验 · 概念

1. 官方说 GRANT 命令有哪两个基本变体？
官方原文：一个是在数据库对象上授予权限，另一个是授予角色的成员资格。
2. 官方对 PUBLIC 的定义是？
官方原文：PUBLIC 可以被认为是一个被隐式定义的、总是包含所有角色的组——包括稍后创建的角色。
3. 角色最终拥有的特权来自哪里（官方）？
官方原文：任何特定角色都将具有直接授予给它的特权、成员角色的特权以及授予给 PUBLIC 的特权。

🌿 中级测验 · 应用

4. 表启用 RLS 但没有创建任何策略，会发生什么？
官方原文：如果表上不存在策略，将使用一条默认的否定策略——所有行都不可见或不能被修改。
5. 官方说表的拥有者与 RLS 的关系是？
官方原文：表的拥有者通常不受行安全性策略的限制——多租户模式下这既是便利也是审计盲点。
6. 官方说 WITH GRANT OPTION 不能用于谁？
官方原文：授权选项不能被授予给 PUBLIC——否则人人都能转授。

🎯 高级测验 · 综合

7. RLS 策略表达式与用户查询条件的求值顺序是？
官方原文：对于每一行，在计算任何来自用户查询的条件或函数之前，先会计算这个表达式——不返回 true 的行不会被处理。
8. 官方说哪些表级操作不受 RLS 限制？
官方原文：应用在整个表上的操作不受行安全性限制，例如 TRUNCATE 和 REFERENCES——策略管的是行级访问。
9. SaaS 多租户隔离（每个租户只能看自己的数据）的标准 RLS 模式是？
租户 id 放会话设置（SET app.tenant_id），策略表达式按它过滤——应用层想绕过都不行，数据库层强制隔离。

最终考核

四道题覆盖本课全部要点——答完它们，角色与权限就过关了。

考核一：为什么「RLS 默认否定」是安全设计的好默认？
安全设计原则 fail-safe：配置遗漏的后果是「看不到」而不是「全泄露」——官方默认否定的价值就在这。
考核二：审计时发现「表拥有者角色」能绕过 RLS 看到全部租户数据。怎么办？
官方默认「拥有者通常不受限」；FORCE 可连拥有者也纳入策略——多租户审计的关键动作。
考核三：GRANT SELECT ON t TO PUBLIC 之后新建的角色也能查这张表吗？
官方原文：PUBLIC 指示特权要被授予给所有角色，包括那些可能稍后会被创建的角色。
考核四：角色 A 是角色 B 的成员，B 对表有 SELECT。A 能查吗？
官方原文：角色具有「授予给它作为成员所在的任何角色的特权」——成员资格即继承。

四道考核全部答对，说明你掌握了角色与权限——继续学习 pg-14 · 备份与恢复。
