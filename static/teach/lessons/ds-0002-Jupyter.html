知识速览

先花几分钟把这一章的骨架过一遍——细节都在《02.Jupyter》里，测验和面试会考。

三步起步：插件 → 工程 → 依赖

  • 装插件：VS Code 里安装 Jupyter 插件（Notebook 支持由此而来）
  • 初始化工程：uv init . 在当前目录建 uv 工程，生成 pyproject.toml
  • 装 Jupyter：uv add --dev jupyter——Jupyter 是开发期工具，用 --dev 加到 dependency-groups，而不是运行时依赖
  • 跑通：新建 .ipynb 文件，选择虚拟环境中的 python，运行第一个单元格

为什么数据科学课程用 Notebook

  • Notebook 把代码 + 运行结果 + 说明文字放在同一个文件里，一次运行就能看到表格、图表的输出
  • 数据科学与 AI Agents 场景里最常见的交互是：读入一份数据（CSV / 数据库 / 接口）→ 逐段试探性地转换、清洗、观察中间结果
  • Notebook 的「分段执行 + 立即看到结果」正好匹配这种探索式工作方式——这也是后续每一章课件都是 .ipynb 的原因
  • 反过来看：Notebook 的单元格是按需执行的，不保证按从上到下的顺序跑；交付前要重启内核并从头执行一遍确认结果可复现

环境要点（最容易踩的一条）

  • 解释器必须选本工程的虚拟环境（.venv），不要用系统 Python：否则 numpy / pandas 装到了别处，Notebook 里会 ModuleNotFoundError
  • 依赖统一用 UV 追加：uv add <package>；开发期的工具库用 uv add --dev <package>（例如 Jupyter 本身）
  • VS Code 右上角的解释器选择器里，选带 .venv 路径的那一项
  • 刚给工程加完包时，正在运行的 Notebook 内核不一定能立刻看到新包——必要时重启内核再 import

🌱 初级测验 · 概念

1. 要在一个 .ipynb 文件里编辑并运行单元格式代码，VS Code 至少需要装哪个插件？
课件「安装 VS Code 插件」一节：安装 VSCode 插件 Jupyter。装好插件后 VS Code 才具备 Notebook 的编辑与运行能力，本章的实操从这里开始。
2. 初始化本章的 uv 工程，用哪条命令？
课件「初始化工程并安装 Jupyter」原文：uv init .——初始化一个 uv 工程。uv 用它生成工程的 pyproject.toml，并把当前目录认作工程根目录。
3. 本课程的课件全部是 .ipynb 文件，这么安排的直接原因是？
课件「为什么数据科学课程用 Notebook」：Notebook 把代码、运行结果、说明文字放在同一个文件里，一次运行就能看到表格、图表的输出；「分段执行 + 立即看到结果」正好匹配读入数据 → 逐段试探性转换的探索式工作方式。速度、.py 的依赖管理、虚拟环境都不是原因。

🌿 中级测验 · 应用

4. 安装 Jupyter 本身用 uv add --dev jupyter、而不用 uv add jupyter，因为？
课件「环境要点」：开发期的工具库用 uv add --dev <package>，例如 Jupyter 本身。运行时依赖与开发期工具分成两个字段，交付/部署时只装运行时那一份，不把 Notebook 工具带进产物。
5. 已经跑过 uv add numpy，Notebook 里 import numpy 却报 ModuleNotFoundError。第一步应该检查什么？
课件「环境要点」：解释器必须选本工程的虚拟环境（.venv），不要用系统 Python——否则 numpy / pandas 装到了别处，Notebook 里会 ModuleNotFoundError；修法是去 VS Code 右上角的解释器选择器里选带 .venv 路径的那一项。import 的位置与写法都不是原因。
6. 一个 Notebook 的内核已经在运行，此时你在终端执行 uv add pandas。想让它生效，最稳妥的做法是？
解释器与内核在运行时就绑定好了已加载的包集合，工程环境的变更不会自动注入正在运行的内核。稳妥做法是安装完重启内核再 import；重启后记得从头执行依赖的单元格，避免留下隐式状态（见「为什么数据科学课程用 Notebook」一节）。

🎯 高级测验 · 综合

7. 新建工程的执行顺序：① 新建 .ipynb ② 运行 uv add --dev jupyter ③ 运行 uv init . ④ 运行 uv add numpy ⑤ 在解释器选择器里选 .venv。只考虑「顺畅、不返工」，正确的顺序是？
先 uv init . 才有工程（③）；再按课件把 Jupyter 作为开发期工具装上（②）、把本章要用的库用 uv add 追加（④）；然后新建 .ipynb（①），最后在解释器选择器里选工程 .venv（⑤）。①→⑤ 先建文件再选解释器不算错，但「没有工程就先建 Notebook」会立刻踩到「装了却 import 不到」；⑤ 排在 ③ 之前更是无从选起。
8. 同事在自己的机器上克隆了你的数据科学工程，执行 uv sync 后 import numpy 正常，但 Notebook 里找不到 jupyter 相关功能。最可能的原因是？
本课把两者放在了不同字段：uv add numpy → 运行时依赖，uv add --dev jupyter → 开发期（dependency-groups）。这正是「开发期工具不进交付产物」的设计意图；不理解这条的人往往会在交付镜像里漏装或多装东西。选项 4 是混淆项：--dev 的依赖同样会被锁定。
9. AI 助手给了你一份 Notebook：第 3 个单元格用 df 做了清洗，第 5 个单元格基于清洗结果生成图表。你直接跳到第 5 个单元格运行却报 NameError: name 'df' is not defined；重启内核从头跑到尾，结果又一切正常。这个现象说明了什么？
课件只承诺「分段执行 + 立即看到结果」这一探索优势，没说单元格会按顺序自动执行：变量是在内核里累积的隐式状态，跳着执行就会遇到未定义，改动上游后不重跑则下游用的是旧值。可靠交付的前提是重启内核从头执行一遍（或把逻辑抽到 .py），这与「环境要点」里强调的解释器/内核绑定是同一类「环境状态」问题。
