索引

配合《06.索引》使用预计 15–20 分钟9 道分级测验 + 4 道最终考核 + 6 道面试实战（中/高/专家各 2 道）

本课目标

完成本课后，你将能：

  1. 说清索引为什么快（B+ 树思想）以及它的代价
  2. 会写 CREATE INDEX / ANALYZE，会用 EXPLAIN 看执行计划——最终考核考的就是这个
  3. 判断什么时候该建索引、什么时候索引会失效

知识速览

先花几分钟把核心机制过一遍——细节都在《06.索引》里，测验和考核会考。

索引演示的本质

无索引：50 万行全表扫 ─ EXPLAIN type=ALL ─▶ 一页页翻，O(n)
CREATE INDEX + ANALYZE ─ 走 B+ 树 ─▶ 几次 IO 定位，O(log n)

⚙️ 索引 = 书的目录：没有它只能逐页翻；有了它先查目录再翻到对应页。范围查询（时间区间）更是直接顺着叶子链表扫。

要点三连

  1. B+ 树为什么适合磁盘：非叶子只存 key → 树矮（2~4 层）→ IO 次数少；叶子用链表相连 → 范围查询顺着扫；所有数据在叶子 → 查找路径稳定。
  2. ANALYZE 的作用：更新统计信息，让优化器知道数据分布与索引存在——不 ANALYZE，优化器可能仍选全表扫描。
  3. 索引的代价：占磁盘空间；每次 INSERT/UPDATE/DELETE 都要维护索引，写变慢。所以不是越多越好。
  4. 索引失效的常见场景：对索引列做运算/函数（WHERE created_at + 1 > …）、LIKE 以 % 开头、复合索引不满足最左前缀、类型不匹配隐式转换。

分级测验

三道一组，先做后点——点击选项立刻出对错与解释。

🌱 初级 · 概念

1. 没有索引时，WHERE 条件查询的执行方式是？
无索引 = 全表扫描（EXPLAIN 里 type=ALL）：把整张表一行行读出来比对 WHERE。50 万行最多比对 50 万次——这就是索引演示「测试 1」慢的原因。
2. 索引最形象的比喻是？
索引 = 目录：数据是书页，索引是「关键字 → 页码」的映射。B+ 树就是精心组织的目录结构，让「查目录」本身也只要几次 IO。
3. 创建索引的主要代价是？
代价：① 索引文件占空间；② 写操作变慢——INSERT/UPDATE/DELETE 除了改数据还要同步维护索引结构。所以「索引不是越多越好」，只为高频查询字段建。

🌿 中级 · 应用

4. 演示脚本里，建完索引后为什么还要执行 ANALYZE？
优化器靠统计信息（数据分布、行数、索引）选择执行计划。刚建索引时统计信息过时，可能仍选全表扫描。ANALYZE 刷新统计后，优化器才会正确选索引路径。
5. 时间范围查询 WHERE created_at >= '2024-06-01' AND created_at < '2024-07-01'，B+ 树索引为什么特别高效？
B+ 树叶子节点按 key 有序且用链表相连：先走树找到 '2024-06-01' 的位置（几次 IO），然后沿链表一路读到 '2024-07-01' 之前——只碰相关页，这正是演示里速度差几个数量级的原因。
6. EXPLAIN 输出中表示「全表扫描」的 type 是？
type 从好到差：system > const > eq_ref > ref > range > index > ALL。ALL = 全表扫描（最差）；本演示中建索引后应看到 range（范围扫描）或更好的类型。index 是只扫索引树（比 ALL 好一点但仍是全量）。

🎯 高级 · 综合

7. 为什么磁盘数据库用 B+ 树而不是普通二叉树/红黑树？
磁盘的性能瓶颈是 IO 次数（每次寻道+传输），不是比较次数。二叉树/红黑树是为内存设计的，节点多、树高、IO 多。B+ 树非叶子只存 key，一个 16KB 页能装几百个 key，树高 2~4 层即可容纳千万行——查询只需 2~4 次 IO。
8. 哪种写法会让 created_at 上的索引失效？
对索引列做运算/函数会破坏「值 → 位置」的直接映射，优化器只能放弃索引（可改写为 created_at > '2024-06-01' - interval '1 day' 把运算挪到常量侧）。同理 LIKE '%xxx'、隐式类型转换也会失效。
9. 复合索引 (a, b) 上查询 WHERE b = 1，会怎样？
复合索引先按 a 排序、再按 b——跳过 a 直接查 b，索引失去排序定位能力（最左前缀原则）。范围查询还会中断后续列的匹配。所以设计复合索引时，把等值、高频的列放最左。

最终考核

本节源课程没有作业，下面四道题由《06.索引》的演示脚本改编——这就是本课的最终考核。规则：不查资料，先在脑中推演演示的每一步，再点击核对。全部答对且能讲清理由，才算过关。

考核一：演示的正确步骤顺序是？
正确流程：① 灌 50 万行 → ② ANALYZE 刷新统计 → ③ 无索引 EXPLAIN（type=ALL，慢）→ ④ CREATE INDEX → ⑤ 再次 ANALYZE（让优化器感知）→ ⑥ 有索引 EXPLAIN（走索引，快）→ ⑦ DROP INDEX 清理。对照组必须控制变量。
考核二：无索引测试的 EXPLAIN 里，执行计划会显示什么特征？
PG 里全表扫描显示 Seq Scan（= type:ALL）。50 万行要一页页全读，执行时间以百毫秒计。这正是「测试 1」与「测试 2」对比的基线。
考核三：建索引后，同一句时间范围查询的执行计划应变为？
有 B+ 树索引后，范围查询走 Index Range Scan（type=range）：树中定位起点 → 叶子链表连续扫到终点，只读相关页面，耗时从「扫 50 万行」降到「扫命中区间」。
考核四：演示结束后为什么要 DROP INDEX idx_order_created_at？
演示用的索引是临时实验：真实业务里是否要这个索引要按查询模式评估。留着它，之后每次写订单都要额外维护——所以演示完清理掉（测试数据 DELETE 同理）。这也呼应「索引不是越多越好」。

💼 面试实战

下面是真实面试官会问的问题，选自中文互联网面试题集（出处附后）。先自己回答，再点击核对。三级面试难度：中级考应用，高级考陷阱，专家考机制与设计。

⚡ 中级面试题

面试题一（必考）：为什么索引能加快查询？
索引 = 「排好序的快速查找数据结构」（B+ 树）：树高 2~4 层、几次 IO 定位到行，替代逐行比对。比喻成书的目录。出处：CSDN「MySQL 索引、锁、三大范式一篇搞定」
面试题二（回表概念）：二级索引查到主键后，为什么还要「回表」？
InnoDB/PG 类似：二级索引叶子存的是主键（或行指针），要拿整行数据得再查一次主键索引（聚簇）——这次「再查」就是回表。若查询列全在索引里（覆盖索引，EXPLAIN Extra=using index），则可免回表。出处：牛客网「秋招结束，回馈牛客」· 索引考点

🔥 高级面试题

面试题三（最左前缀）：联合索引 (a, b, c)，哪条查询能用上索引？
联合索引按 a → b → c 依次排序，查询必须从最左列开始连续匹配。a=1 AND b=2 ✓；跳到 b、c 或中间断层都不行。注意：a 上的范围查询会「中断」后续列匹配（a>1 AND b=2 里 b 用不上）。出处：CSDN「MySQL 索引、锁、三大范式一篇搞定」
面试题四（失效场景）：以下哪条 SQL 会导致索引失效？
LIKE '%张%'（前导 %）索引失效：B+ 树按前缀有序，「任意位置含张」无法用树定位。此外：对列运算、隐式类型转换、OR 关联非索引列、范围后断最左前缀等都会失效。LIKE '张%' 则可以用索引。出处：牛客专刊「数据库索引-笔面试必考点 15 讲」

🧠 专家面试题

面试题五（结构对比）：B+ 树相比 B 树的优势是？
两大优势：① 非叶子只存 key → 同页容更多 key → 树更矮 → IO 更少；② 叶子用双向链表相连 → 范围查询定位起点后顺链扫，反向遍历也方便。B 树数据散在各级节点、叶子无链。出处：牛客网「秋招结束，回馈牛客」· B+ 树考点
面试题六（慢查询治理）：一条慢 SQL 的排查路径是？
标准路径：EXPLAIN 分析 → 看 type（至少到 range、最好 ref）、rows 估算、Extra（using filesort 要优化排序、using temporary 用了临时表）→ 针对 WHERE/ORDER BY/GROUP BY/JOIN 列建合适索引或改写 SQL（覆盖索引、避免列运算、避免前导 %）。无脑全列建索引是典型反面答案。出处：力扣「MySQL 高频面试题，硬 gang 面试官」
