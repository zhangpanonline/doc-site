uv 替代关系

传统工具uv 对应作用
pipuv pip安装包（全局模式）
venv / virtualenvuv venv虚拟环境
pyenvuv python install/pinPython 版本管理
pip-toolsuv lock / uv sync锁定与同步依赖
pipxuv tool / uvxCLI 工具管理
poetry / pdmuv init/add/remove项目依赖管理
build + twineuv build / uv publish构建与发布

三个要点

  1. 项目级 vs 全局级：uv add/sync/run 关联 pyproject.toml 与 uv.lock（推荐）；uv pip install 是兼容 pip 的全局模式。官方文档：uv
  2. uv.lock 锁定整个依赖树：uv add 自动解析并锁定精确版本；别人拉代码后 uv sync 按锁文件重建一致环境。
  3. uvx 临时运行、uv tool 持久安装：uvx ruff check . 用完即弃（临时环境自动清理）；uv tool install ruff 长期保留。团队协作用 uv add --dev ruff 写进项目。

🌱 初级测验 · 概念

1. uv 是做什么的？
uv 是 Astral 出品的 Rust 工具，一站式替代 pip/venv/pyenv/build/twine 等，主打 10-100 倍速度。详见「UV 简介」一节。
2. 初始化一个库（src layout）项目的命令是？
uv init --lib 生成 src layout 的库项目；uv init 是应用项目；--vcs none 跳过 git。详见「初始化项目」一节。
3. uv add requests 会自动完成哪些事？
uv add 四步走：解析依赖树 → 安装到虚拟环境 → 更新 pyproject.toml 的 dependencies → 生成/更新 uv.lock。详见「安装依赖」一节。

🌿 中级测验 · 应用

4. 别人拉取你的代码后，重建一致环境的命令是？
uv sync 按 uv.lock（或 pyproject）安装全部依赖，保证环境与锁文件一致。详见「同步环境」一节。
5. uvx ruff check . 与 uv tool install ruff 的区别是？
uvx 在临时虚拟环境跑一次就清理；uv tool install 长期安装（uv tool list/upgrade/uninstall 管理）。详见「Running Tools」一节。
6. Makefile 在 uv 项目里的核心价值是？
Makefile 是「约定层」：新人只需 make test/make build，不用记底层命令，CI 也天然适配。详见「Makefile」一节。

🎯 高级测验 · 综合

7. 把已有代码改造成 uv 工程，正确的操作顺序是？
改造流程：uv init --lib 建骨架 → 源码放进 src/包名/ → uv add httpx python-dotenv aiofiles 写依赖 → [project.scripts] 配命令行入口 → uv sync 同步环境。源码答案 p1 正是按此结构。
8. 发布后用户终端输入 my-cli 即调用 my_project 包的 main() 函数，pyproject 应写？
[project.scripts] 的格式：命令名 = "模块路径:函数名"——my-cli = "my_project:main"。等号右边冒号前是模块、冒号后是函数。第二个少了冒号函数 ✗；第三个段名错 ✗；第四个 Makefile 只影响本地调用 ✗。
9. 用 uv 把包发布到阿里云私有制品仓库，正确的命令是？
私有发布：先 uv build 产出 dist/，再 uv publish --publish-url 私有仓库地址 --username/--password 凭证 dist/*。不带参数默认发 PyPI ✗；build 只构建不发布 ✗；install 是安装不是发布 ✗。

💼 面试实战

下面是真实面试官会问的问题，选自中文互联网面试题集（出处附后）。先自己回答，再点击核对。三级面试难度：中级考应用，高级考陷阱，专家考机制与设计。

⚡ 中级面试题

面试题一（现代工具链·高频）：uv 相比 pip + venv 的改进是什么？
uv 的三大卖点：① 快（Rust 实现，比 pip 快 10-100 倍）；② 一站式（pip/venv/pyenv/build/twine/poetry 的功能合一）；③ 可复现（uv.lock 锁定完整依赖树）。面试中熟悉 uv/poetry 是「知识更新及时」的信号，只靠手写 requirements.txt 且无锁文件会被视为工程能力不足。出处：腾讯云开发者社区（Python 面试高频考点中文版）
面试题二（锁文件·追问）：uv.lock 与手写的 requirements.txt 有什么区别？
手写 requirements.txt 通常只列直接依赖（可能带范围）；uv.lock 记录整个依赖树（含所有传递依赖）的精确版本——这才是「任何机器上都能复现相同环境」的保证，也是区分现代工程与「在我机器上能跑」的关键。出处同面试题一

🔥 高级面试题

面试题三（锁文件漂移·机制）：pyproject.toml 与 uv.lock 不一致时，uv sync 会怎样？
锁文件是「可复现」的根基：uv sync 发现 lock 与 pyproject 不一致时会提示漂移（默认仍按 lock 装，保证环境确定），需要更新依赖时显式 uv lock --upgrade 或 uv add 重新解析。理解了漂移处理才真正理解锁文件。出处：uv 官方文档（中文技术社区广泛收录）
面试题四（CI 缓存·工程）：CI 里跑 uv，如何加速依赖安装？
uv 的全局缓存（~/.cache/uv）跨项目复用下载的包——CI 中把该目录配置为缓存键，依赖没变时安装接近零成本。这是 uv 工程化的标准实践（GitHub Actions 的 cache 步骤即可）。出处同面试题三

🧠 专家面试题

专家题一（工具选型·设计）：uv、poetry、pip+venv 如何选？
工程选型逻辑：新项目默认 uv（速度 10-100 倍、一站管理、锁文件可复现）；已有 poetry 项目不必强迁；存量 pip 项目可渐进迁移（uv 兼容 requirements.txt）。选型理由（速度/可复现/迁移成本）比工具名本身更重要。出处：Maxiom「Python Developer Interview Questions（2026）」中文面试集收录
专家题二（自动化边界·工程）：Makefile 与 CI 的职责边界是？
Makefile 是本地统一入口（新人 make test 即可，不记底层命令）；CI 是每次提交的自动看门（隔离环境跑检查/测试/构建）——CI 里调用的正是 Makefile 的目标（make lint / make test），两者是「约定层 + 自动化层」的分工而非替代。出处：uv 官方文档（中文技术社区广泛收录）
