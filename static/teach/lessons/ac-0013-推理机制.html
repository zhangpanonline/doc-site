推理机制

配合《13.推理机制》使用预计 15–20 分钟9 道分级测验 + 面试实战

本课目标

完成本课后，你将能：

  1. 说清一次自回归推理为什么分成预填充 Prefill 与解码 Decode 两个阶段，各自在算什么、瓶颈在哪
  2. 解释 K-V 缓存省掉了哪些重复计算，它的显存代价随什么增长，并会算每 token 的缓存大小
  3. 复述温度、Top-K、Top-P 三种采样策略的机制差异，说清 Top-P 为什么比 Top-K 更灵活
  4. 用官方参数定义审查 AI 给出的推理配置，并把首 token 延迟与逐 token 间隔分开看待

知识速览

先花几分钟把推理的三个关键词过一遍——预填充、K-V 缓存、采样策略，细节都在《13.推理机制》里，测验和面试会考。

推理的两个阶段：预填充 Prefill 与解码 Decode

  • 自回归生成分成两个阶段：先 预填充 Prefill 处理输入，再 解码 Decode 逐个吐字（官方原文：This process involves two phases: the prefill phase and the decode phase）
  • Prefill：把整段输入 token 一次送进模型，算出中间状态（keys 和 values），用来生成第一个新 token。因为输入全长已知，这是一次矩阵×矩阵运算，高度并行，能把 GPU 吃满
  • Decode：自回归地一次生成一个 token，直到命中停止条件。每个新 token 都要看之前所有轮次的输出状态（K/V），本质是矩阵×向量运算，算力用不满；延迟由「数据从显存搬到计算单元」的速度主导——也就是访存受限（memory-bound）
  • 两个阶段的延迟指标必须分开看：Prefill 决定首 token 延迟 TTFT，Decode 决定相邻 token 间隔 ITL；调参时也要分开调，不能用一个「平均速度」混着算
  • 想直观感受逐 token 生成，用课件给的 transformer-explainer，能看到概率分布怎么随参数变化

K-V 缓存：用显存换计算

  • 它解决什么：Decode 每一步都要用到前面所有 token 的 K/V；如果每步都重算，重复计算会随序列长度急剧膨胀。把已算出的 K/V 张量留在显存里，新元素直接追加进缓存，下一步直接复用（官方原文：To avoid recomputing all these tensors for all tokens at each time step, it is possible to cache them in GPU memory）
  • 常见形态：多数实现里每一层都有自己的 K-V 缓存
  • 代价是显存：批量推理时每个请求的缓存要单独分配，占用随批量大小与序列长度线性增长——长上下文与 RAG 场景的吞吐瓶颈就在这里
  • 每 token 缓存大小：$$\text{bytes per token} = 2 \times n_{\text{layers}} \times (n_{\text{heads}} \times d_{\text{head}}) \times \text{precision\_in\_bytes}$$ 第一个因子 $2$ 是 K 与 V 两份；$(n_{\text{heads}} \times d_{\text{head}})$ 通常等于 $d_{\text{model}}$
  • 算例：Llama 2 7B（$n_{\text{layers}}=32$、$d_{\text{model}}=4096$、FP16 即 2 字节）→ $2 \times 32 \times 4096 \times 2 = 524288$ 字节 ≈ 512 KB/token；单条 8192 上下文 ≈ 4 GB，并发 16 条 ≈ 64 GB——而 FP16 的 7B 权重才约 14 GB

采样策略：温度 Temperature / Top-K / Top-P

  • 模型每一步输出的是整个词表上的概率分布（logits 经 Softmax）；「采样策略」决定怎么从这张分布里挑出下一个 token
  • 温度 Temperature：在 Softmax 之前把所有 logits 除以 $T$，即 $p_i = \dfrac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$。$T=1$ 不作干预；$T<1$（如 0.5）分布更尖锐，高概率的词更高、低概率的词更低，文本更稳定、保守、确定；$T>1$（如 1.5）分布更平滑，词间概率差距缩小，文本更随机、多样、有创造力。官方表述：温度调制概率质量函数，低温把函数变陡（steepens）→ 更确定，高温把它压平（flattens）→ 更随机
  • Top-K 采样：只从概率最高的 K 个词里随机抽取，其余词的采样概率直接置零。比如 K = 50：先选出概率最高的 50 个词，过滤掉剩余海量词汇，再在这 50 个词的新分布上采样。K 是固定值
  • Top-P（核采样，Nucleus Sampling）：按概率从高到低累加，直到累积概率超过 P，只从这个动态的「核心」词集合里采样。比如 P = 0.9，就只从累积概率超过 0.9 的最小词集合中采样。课件说它是目前最主流、效果最好的采样方式之一，比 Top-K 更灵活：K 固定，而 P 是动态的——分布集中时采样集很小、输出更确定，分布分散时采样集很大、输出更多样
  • 官方 API 口径：Top K 是「模型为下一个 token 考虑的最可能候选的数量」，Top P 是「考虑的最可能候选的百分比」（如 0.8 就是从概率分布的前 80% 里选）
  • 工程细节：vLLM 里 temperature=0 即贪心（greedy），实现上会把 top_p 强制为 1.0、top_k 强制为 0、min_p 强制为 0.0；top_k=0（或 -1）的含义是「考虑全部 token」而不是「不考虑任何 token」。另外，推理模型（如 GPT-5 系列）根本不支持 temperature / top_p 这些采样参数

分级测验

🌱 初级测验 · 概念

1. 一次自回归推理被分成哪两个阶段？
课件「理解」一节列出的第一件事就是预填充 Prefill；官方原文把这个过程说成两个阶段：This process involves two phases: the prefill phase and the decode phase。前半段处理输入（算 K/V、生成第一个 token），后半段自回归地一个个吐 token。反向传播是训练阶段的事，不属于推理。
2. 温度 Temperature 控制的是什么？
课件原文：温度控制输出概率分布的「锐利」或「平滑」程度——在 Softmax 之前，将所有 Logits 除以温度值 T。它不动参数量、不动窗口、也不动生成长度，只重塑这张概率分布的形状。
3. 设置 Top-P（核采样）为 P = 0.9，模型实际是从哪里采样？
课件原文：从累积概率达到 P 的最小词集合中采样；比如 P = 0.9，模型会按概率从高到低累加词，直到累积概率超过 0.9，然后仅从这个动态的「核心」词汇子集中采样。它不是固定个数（那是 Top-K 的 9 个词），也不是「以 P 的概率走贪心」。

🌿 中级测验 · 应用

4. 关于 K-V 缓存的作用与代价，下面哪一条正确？
官方原文说得很清楚：为了避免每个时间步对所有 token 重算这些张量，把它们缓存进 GPU 显存，每轮新算出的元素直接追加到运行中的缓存。代价是显存——批量推理时每个请求的缓存要单独分配，占用随批量与序列长度线性增长。缓存只影响计算复用与显存，不改变 Decode 的矩阵×向量本质，也不影响精度。
5. 一个客服 Agent 要把用户问题分类成固定 JSON 字段（希望同样的输入尽量给同样的输出）；另一个营销文案 Agent 要同题出多稿。温度该怎么设？
课件原文：T < 1（如 0.5）分布变得更尖锐，高概率的词概率更高、低概率的词更低，文本更稳定、保守、确定；T > 1（如 1.5）分布变得更平滑，各词之间的概率差距缩小，文本更具随机性、多样性、创造力。官方也把这件事说成低温 steepens（更陡 → 更确定）、高温 flattens（更平 → 更随机）。所以结构化分类要低温，创意文案要高温，方向别弄反。
6. 课件为什么说 Top-P 比 Top-K 更灵活？
课件原文：它比 Top-K 更灵活，因为 K 是固定的，而 P 是动态的——当概率分布很集中时，采样集很小，输出更确定；当分布很分散时，采样集很大，输出更多样。两者都是在缩小候选池，都要先有 Softmax 后的概率，也都保留随机性。

🎯 高级测验 · 综合

7. 用户反馈：问一个 3 万字文档的问题，「第一个字要等 8 秒，之后每个字出得挺快」。按 Prefill / Decode 的分工，诊断与优化方向是？
官方把两件事分得很清楚：Prefill 把输入并行处理完（矩阵×矩阵，吃满 GPU），Decode 才是一个个吐 token 且访存受限。长输入导致首字慢，病灶在 Prefill / TTFT，跟采样参数无关（温度、top_p 只改变采样分布，不减少 Prefill 的计算量）。vLLM 官方文档给出的正是这两条路：把 prefill 与 decode 放进不同实例以分别调 TTFT 与 ITL；以及用分块预填充避免 prefill 任务插进解码过程、抬高尾部延迟。
8. Llama 2 7B：32 层、hidden size 4096、FP16（2 字节）、K 与 V 各一份。按官方公式，K-V 缓存每 token 多大？batch = 16、上下文 8192 时是什么量级？
官方公式：Size of KV cache per token in bytes = 2 * (num_layers) * (num_heads * dim_head) * precision_in_bytes，第一个 2 是 K 和 V 两份。代入 $2 \times 32 \times 4096 \times 2 = 524288$ 字节 ≈ 512 KB/token；再乘序列长度 8192 ≈ 4 GB，乘 batch 16 ≈ 64 GB。官方同时给了一个对照：FP16 的 7B 权重约 14 GB。所以长上下文 + 高并发的瓶颈往往不是权重而是缓存；缓存也不是只在 Prefill 用——它本来就是给 Decode 复用才存在的。
9. 有人想「跑 5 次拿 5 个候选再投票选最佳」，写下 SamplingParams(temperature=0.0, top_p=0.9, top_k=50, n=5)，结果 5 条输出完全一样。根因是？
vLLM 官方文档对 temperature 的定义最后一句就是 Zero means greedy sampling；源码里更直接：temperature 低于阈值时先执行 self.top_p = 1.0、self.top_k = 0、self.min_p = 0.0，再做贪心校验——也就是说贪心下你写的 top_p / top_k 会被覆盖。n 的官方定义是「为同一个 prompt 返回的输出条数」，路径只有一条时自然 5 条全同。要多样性得让 temperature > 0（或设 seed 后采样），而不是靠叠加过滤参数。
