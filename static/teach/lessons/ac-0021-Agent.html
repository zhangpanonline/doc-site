知识速览

先花几分钟把「编排层 + 监听层 + 流式解析」三条线过一遍——细节都在《21.Agent》里，测验和面试会考。

Agent 是什么：把四件东西装到一起的编排层

  • 课件定义：AI Agent 是通过自主规划、调用工具、持续观察反馈并迭代行动，独立推进复杂任务直至目标达成的人工智能运行单元
  • 职责分工：agent/agent.py 是入口/编排层；Model（模型层）、Session（会话层）、tool/（工具层）、Listener（监听层）各管一段，Agent 只负责串起来 + 驱动循环
  • 构造：Agent(*, session=None, model=None, model_listener=None)——三个参数都是关键字参数、都可省略；self.session = session or Session()、self.model = model or Model()；一旦传入 model_listener，构造时就执行 self.listener.listen(self.model)
  • 循环：先 session.add_message({"role": "user", "content": q})；然后 while True：resp = model.invoke_stream(session) → call_msg = registry.invoke(session.messages[-1])；返回 None 就 break，否则 session.messages += call_msg 继续下一轮；每轮的 resp 都收进 responses 列表
  • 本章的四处课前修改：系统提示词更简洁、封装出 agent.py、封装抽象的监听器、Session 新增 print_friendly

监听层：事件驱动是怎么解耦的

  • 事件常量（agent/events.py）：推理事件 reasoning_start / reasoning / reasoning_end、内容事件 content_start / content / content_end、工具调用事件 tool_call_start / tool_call / tool_call_end，以及完成事件 complete
  • 事件总线：EventEmitter 用「事件名 → 回调列表」的映射（defaultdict(list)）管理监听器；on(event, callback) 注册、emit(event, **data) 触发该事件下的所有回调——一个事件可以挂多个监听器
  • 抽象监听器 ModelListener(ABC)：listening 标志默认 True；listen(model) 取出 Event 上所有事件常量，逐个 model.on(event=e, callback=self._model_print_callback)——一行代码把监听器挂到全部事件；统一回调先查 listening，再转发给抽象方法 _handler(e, **args)
  • 子类只写业务：ModelPrinterListener._handler 按事件分支打印——reasoning_start 打印「思考中...」、content_start 打印「内容：」、content 绿色输出增量片段、tool_call_end 青色打印「调用工具：xxx」
  • 解耦收益（分析.md 设计亮点 2）：EventEmitter + ModelListener 把「模型推理」与「副作用」（打印、日志、前端推送）分开——Model 只负责发射事件，谁来消费它不关心

流式解析与生命周期：Builder、InvokeResult、print_friendly

  • 三个 Builder 同时消费每个 chunk：ReasoningBuilder 盯推理字段（兼容 reasoning_content / reasoning）、ContentBuilder 盯 content、ToolCallsBuilder 盯 tool_calls；谁先拿到值谁就先发 start 事件，之后每个增量发一次中间事件
  • 结束判定：is_end 看 chunk.choices[0].finish_reason 是否非空；ReasoningBuilder 额外提前收尾——一旦 delta 里出现 content 或 tool_calls，就认为「思考阶段结束、正文/工具开始」
  • 工具调用要拼装：流式下 tool_calls 被切成分片，append_value 按 tc_delta.index 归位（不够就补齐占位），把 arguments 字符串按序拼接；_normalize_tool_calls 再把对象统一成 dict，好直接进 session.messages
  • 结果封装：InvokeResult 带 message（可入会话）与 raw（原始响应），print_raw() 用来看单次调用的原始数据
  • 会话可读化：Session.print_friendly() 按角色分段输出（系统消息 / 用户消息 / 工具调用 / AI消息 / 调用结果），工具参数截断到 70 字符、工具结果截断到 50 字符——排错时先用它看「模型到底收到了什么」
  • 别忽略的隐患：while True 没有任何停止条件。官方提醒，Agent 通常在任务完成时终止，但也常需要最大迭代次数这类停止条件来保持控制——否则模型只要一直发起工具调用，循环与成本就没有上限

🌱 初级测验 · 概念

1. 本章新增的 agent/agent.py 里，Agent 类承担的角色是？
分析.md 的架构图把它写得最清楚：Agent (入口/编排) 之下才是 Model / Session / Tool / Listener 四层，最底下是 EventEmitter 事件总线。API 调用与流式解析在 model.py，消息与工具 Schema 在 session.py，函数包装在 tool/core/tool.py。
2. ModelListener.listen(model) 做了什么？
课件 listener.py 原文：events = [v for k, v in Event.__dict__.items() if not k.startswith("__")]，再 for e in events: model.on(event=e, callback=self._model_print_callback)。它不区分事件种类，统一挂同一个回调，由 _handler 在子类里分支处理。
3. 为什么要单独抽出监听层（listener.py + printer.py），而不是在 Model 里直接 print？
分析.md 设计亮点 2 原文：事件驱动架构用 EventEmitter + ModelListener 解耦了模型推理与副作用（打印、日志等）。这也解释了为什么 ModelListener 是抽象基类——同一套事件流可以派生多个监听器（控制台、文件日志、WebSocket），Model 一行都不用改。

🌿 中级测验 · 应用

4. 关于 Agent.__init__(self, *, session=None, model=None, model_listener=None)，下面说法正确的是？
签名里的 * 表示后面全是关键字参数；self.session = session or Session()、self.model = model or Model() 说明两者可省略——Session() 自己会渲染系统提示词、Model() 自己会读配置。监听器是可选增强：if self.listener: self.listener.listen(self.model)，没有监听器，Agent 照样能跑，只是终端不打印过程。另外这里是引用同一个 session 对象，不是拷贝——所以外部持有它就能用 print_friendly() 复盘。
5. session.print_friendly() 与 print(session) / str(session) 的区别是？
课件 session.py 里 __str__ 是 json.dumps({"id": ..., "messages": ..., "tools": ...}, ensure_ascii=False, indent=2)——完整、精确，但工具 Schema 一多就淹没在 JSON 里。新增的 print_friendly() 按 role 分段打标签（系统消息 / 用户消息 / 工具调用 / AI消息 / 调用结果），并把工具参数截到 70 字符、工具结果截到 50 字符。排错顺序通常是：先 print_friendly() 看对话骨架对不对，需要细节时再 print(session) 或 result.print_raw()。
6. 流式推理里三个 Builder 的工作方式是？
课件 _process 里是 for chunk in response: for b in builders: b.emit(chunk)——三个 Builder 都看得到每个 chunk，各自用 getattr(delta, field_name, None) 判断自己有没有值。增量事件是每个 chunk 都发（emit(event_name, chunk_value=value, ...)），finish_reason 只决定何时发 end 事件。ToolCallsBuilder 只收集工具调用，文本由 ContentBuilder 收集。

🎯 高级测验 · 综合

7. 同样发来一条工具调用，为什么非流式下 _normalize_result_from_response 直接取 message.tool_calls 就行，而流式下 ToolCallsBuilder.append_value 必须按 tc_delta.index 归位、再把 arguments 逐片拼接？
非流式响应是一个已经组装好的对象，所以 _normalize_result_from_response 能直接遍历 [reasoning_field, "content", "tool_calls"] 取值。流式则相反：只有分片。课件因此写了 append_value——用 tc_delta.index 找到（或补齐）对应槽位，tc["function"]["arguments"] += args 逐片累加，最后 _normalize_tool_calls 把对象统一成 dict。顺手记住一个后果：参数在流式途中是半截 JSON，不能提前 json.loads——这正是「边解析边发射事件」要付出的代价。
8. 这一版 Agent.invoke 用 while True，靠 registry.invoke(self.session.messages[-1]) 返回 None 退出。风险与修法分别是？
循环的退出条件完全依赖模型「这一轮不再要求调工具」，而工具有副作用（read_file / write_file / bash_command）时，模型可能反复试探、反复执行。Anthropic 官方在讲自主 Agent 时明确提醒：任务通常在完成时终止，但也常需要设置停止条件（例如最大迭代次数）来保持控制。注意 responses.append(resp) 是把每轮结果都收进列表（不覆盖），所以 responses[0] 只是第一轮的中间结果，最终答案在最后一轮——调用方必须知道这一点。
9. 排查现象：「Agent 行为正常，最终答案也对，但终端把模型正文和工具名各打印了两遍。」按本章实现，最可能的根因是？
链路是：EventEmitter 用 Event 名到回调列表的映射管理监听器，on 的行为就是 self._listeners[event].append(callback)（课件 events.py），emit 则遍历该列表逐个调用——挂两次就回调两次。重复注册的常见来源：手工又调了一次 listener.listen(agent.model)、或者用同一个 listener 构造了两个 Agent（Agent 构造时会自动 listen）。修法：注册前查重，或让 listen 幂等（例如内部记 (id(model), id(self)) 已注册集合）。Builder 每个 chunk 只 emit 一次、print_friendly 只涉及消息列表，都解释不了「事件流」翻倍。
