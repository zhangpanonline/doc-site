MCP Client

本课目标

完成本课后，你将能：

  1. 以客户端身份连上 MCP 服务器，并按 initialize → tools/list → tools/call 的顺序完成第一次工具发现与调用
  2. 说清 stdio 与 Streamable HTTP 两种传输的连接方式差异，以及为什么一个返回二元组、一个返回三元组
  3. 用 @asynccontextmanager 把「连接 + 初始化」封装成 connect_mcp，再向上长出 MCPClient 的多服务器管理能力
  4. 解释 run_async 为什么要在独立线程里跑 asyncio.run，并判断什么时候不该做同步封装

知识速览

先花几分钟把本章的骨架过一遍——细节都在《25.MCP Client》里，测验和面试会考。

一次客户端会话的固定三步

  • 装依赖：!uv add mcp==1.28.1（python-sdk 的 v1.28.1）
  • 第 1 步 initialize：await session.initialize()——协商协议版本与能力，官方规范把它定为客户端与服务器之间的第一次交互
  • 第 2 步 发现工具：tools = await session.list_tools()（协议方法 tools/list），打印时用 tools.model_dump_json(indent=2, ensure_ascii=False)
  • 第 3 步 调用工具：await session.call_tool(name="get_current_time", arguments={"timezone": "Asia/Shanghai"})（协议方法 tools/call）
  • 三步都发生在同一个会话里：async with 连接 → async with ClientSession(read, write) → 拿到 session 后才能做后两步

两种传输：stdio 与 Streamable HTTP

  • stdio：客户端把服务器作为子进程启动，用标准输入输出传换行分隔的 JSON-RPC 消息。参数用 StdioServerParameters(command="uvx", args=["mcp-server-time"])，连接写 async with stdio_client(server_params) as (read, write)——二元组
  • Streamable HTTP：服务器是独立进程、可服务多个客户端，客户端连的是一个 MCP endpoint URL。写法是 async with streamable_http_client("https://learn.microsoft.com/api/mcp") as (read_stream, write_stream, _)——三元组，第三个值用 _ 丢掉，这正是本章最常见的抄错点
  • 两种传输拿到 read / write 之后的代码完全一样：ClientSession(read, write) → initialize()；差别被 connect_mcp 吃掉
  • 本章实测对象：本地 uvx mcp-server-time（工具 get_current_time、convert_time）与微软托管的 https://learn.microsoft.com/api/mcp（工具 microsoft_docs_search、microsoft_code_sample_search、microsoft_docs_fetch）

三层封装：connect_mcp → 单服务器函数 → MCPClient

  • 配置驱动：mcp = {"servers": {"time": {"type": "stdio", "command": "uvx", "args": [...]}, "microsoft-learn": {"type": "http", "url": "..."}}}，每个服务器带一个 type 字段
  • 第一层 connect_mcp(server_config)：@asynccontextmanager 装饰的异步生成器，按 type 选传输、建会话、initialize()，然后 yield session；不认识就 raise ValueError。
  • 第二层 list_server_tools / call_server_tool：async with connect_mcp(config) as session: 一行进上下文，直接 return await session.list_tools() / session.call_tool(tool_name, arguments or {})
  • 第三层 MCPClient：__init__ 存下 config["servers"]；alist_tools() 遍历所有服务器，产出 [{"server": 服务器名, "tools": 结果}]；acall_tool(server_name, tool_name, arguments) 按名字取配置再调用
  • 同步封装 run_async(coro)：新开 threading.Thread 在里面 asyncio.run(coro)，t.join() 后取结果或重新抛出异常。原因：asyncio.run() 不能在已有事件循环运行的线程里调用，而 Jupyter 自己维护着一个事件循环；每个线程有独立事件循环，所以新线程里是安全的
  • 最终 MCPClient.list_tools() / call_tool() 就是「run_async 包异步方法」的同步皮；本章工程变更 = 新增 1 个文件 agent/tool/use_mcp.py、修改 0 个文件

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《25.MCP Client》覆盖的内容。

🌱 初级测验 · 概念

1. 客户端连上一个 MCP 服务器后，做「工具发现 + 工具调用」之前必须先完成哪一步？
课件里每一段示例都严格按 await session.initialize() → await session.list_tools() → await session.call_tool(...) 的顺序写，注释直接标了 # initialize / # tools/list / # tools/call。官方规范也把初始化阶段定为「客户端与服务器之间的第一次交互」。
2. HTTP 版本的示例为什么把连接写成 as (read_stream, write_stream, _)，而不是像 stdio 那样只接两个值？
课件把两个传输的解包形状并排展示：stdio_client(params) as (read, write) 对 streamable_http_client(url) as (read_stream, write_stream, _)。两者后面接 ClientSession(read, write) 的写法完全一致，区别只在传输层——第三个值不是状态码、也不是必须手动传的会话 id，用 _ 丢掉即可。
3. 用 stdio 传输时，配置里的 command: "uvx" + args: ["mcp-server-time"] 实际意味着什么？
课件的注释写着 # Using uv to run the server：stdio 传输下客户端负责把服务器拉起来，官方规范的原话是「The client launches the MCP server as a subprocess」，消息走 stdin/stdout。uvx 在这里只是「按需运行一个 Python 工具包」的启动器，不是网络服务名。

🌿 中级测验 · 应用

4. 下面这段配置传给 connect_mcp，会发生什么？
{"type": "sse", "url": "https://example.com/mcp"}
connect_mcp 只认两个分支：if type == "stdio" 与 elif type == "http"，其余一律走 else: raise ValueError(f"不支持的服务器类型: {server_config['type']}")。更值得注意的是抛出时机：这个异常发生在 MCPClient.alist_tools() 的 for 循环里，会打断整轮遍历——一个配置写错的服务器，能让其他本来正常的服务器也拿不到工具列表。
5. tools = await session.list_tools() 之后，tools 身上最方便用来打印的工具发现结果的方法是？
课件在 stdio、HTTP、封装后三个小节的示例里，打印一律用 tools.model_dump_json(indent=2, ensure_ascii=False)——说明 list_tools() 返回的是 Pydantic 模型结果对象，model_dump_json 是它的正规出口；ensure_ascii=False 是为了中文描述不被写成 \uXXXX。json.dumps 不认识这个类型会直接报错；content[0].text 是 tools/call 结果的形状（工具执行产出的内容），两个结果对象的字段完全不同。
6. 为什么 run_async(coro) 要专门开一个线程，而不是在 MCPClient.list_tools() 里直接 asyncio.run(self.alist_tools())？
课件把原因写得很直白：asyncio.run()「要求在调用时没有其他事件循环在运行」，而「Jupyter 自身维护了一个事件循环，直接调用会报错」；解决方法是利用 threading 在独立线程中运行，「每个线程拥有自己的事件循环，互不干扰」。注意第 1 个选项是错的：run_async 里 t.start() 之后立刻 t.join()，是串行等待，并没有并发。

🎯 高级测验 · 综合

7. 只想调用 time 服务器上的一个工具，却有 300 个 MCP 服务器配置在 mcp["servers"] 里。用课件的 MCPClient，一次 acall_tool("time", ...) 大概要付出什么连接成本？
acall_tool 的实现是 config = self.servers[server_name] 然后 async with connect_mcp(config) as session: return await session.call_tool(...)——按名字取一个配置，只连这一个，async with 退出时连接关闭。代价是每次调用都要重连并重新 initialize（stdio 还要重启子进程）；遍历所有服务器的只有 alist_tools()，它才是 300 次那一头。这也解释了为什么工具列表往往要缓存下来复用，而不是每次问模型前都重刷。__init__ 只存字典、不建连接——第 3 个选项描述的是一个并不存在的实现。
8. 用 HTTP 服务器实测时，模型编了一个不存在的工具名（例如把 microsoft_docs_search 写成 microsoft_search）。按 MCP 官方规范，客户端可能看到哪两种截然不同的结果？
MCP 规范把错误分成两套机制：协议错误走标准 JSON-RPC error（示例给的正是 Unknown tool: invalid_tool_name，code -32602）；工具执行错误走工具结果里的 isError: true。本章实测 mcp-server-time 时，call_tool(name="no_such_tool") 得到的是后一种：isError: true + 文本 Error processing mcp-server-time query: Unknown tool: no_such_tool，并不抛异常。客户端封装时如果不检查 isError，就会把「调用失败」当正常结果回灌给模型——反过来，这也恰好是让模型自己纠错的机会。
9. 队友说：「既然 run_async 能把异步包成同步，那我在 Agent 的工具执行函数里也套一层，工具就能同步调 MCP 了。」Review 这个方案，最大的问题是什么？
run_async 的存在是有明确场景的：在已经有事件循环的环境（Jupyter）里，为「不方便写 await 的调用方」提供同步入口。Agent 的工具执行链路本身就在异步上下文里，直接 await session.call_tool(...) 才是正解；套一层线程 + asyncio.run 等于把已经异步的东西搬去别的线程再搬回来，白白付出线程创建、事件循环创建与跨线程同步的开销。
更实质的损失是语义：课件的 run_async 里是 t.join() ——不能取消、不带超时，而 MCP 规范明确建议「为所有发出的请求设置超时」；同时每次 run_async 都新建事件循环，无法复用一条长连接，也没法把服务器的 progress 通知、取消通知接回来。第 3 个选项不成立：它只读字典、不写；第 4 个选项也不成立：run_async 收的是协程，参数早就绑定好了。
