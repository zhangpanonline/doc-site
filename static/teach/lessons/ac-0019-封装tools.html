封装tools

配合《19.封装tools》使用预计 15–20 分钟9 道分级测验 + 面试实战

本课目标

完成本课后，你将能：

  1. 说清「函数 → 参数模型 → Schema → session.tools → 模型 → 执行 → 结果回灌」这条流水线的每一环由谁负责
  2. 用 Pydantic 的 BaseModel 与 create_model 动态生成参数模型，既做参数校验又产出 JSON Schema
  3. 读懂 Tool 类的三件套——name / description / schema() 与 __call__——以及 tool 装饰器如何把参数描述聚合到函数定义处
  4. 说明 _ToolRegistry 的 register / schemas / invoke 各自解决哪段距离，并识别其中的错误处理陷阱

知识速览

先花几分钟把本章的骨架过一遍——细节都在《19.封装tools》里，测验和面试会考。

要封装的那条流水线

  • 上一章的完整流程是：定义函数 → 手动拼 JSON Schema → 绑定到 session.tools → 调用模型 → 执行工具；手拼 Schema 又长又容易写错
  • 本章的目标只有一句话：「希望在代码层面更加简洁优雅地完成这条流水线」
  • 封装后的分工：Tool 负责「一个函数 ↔ 一份 Schema」，_ToolRegistry 负责「工具 ↔ session ↔ 模型返回的 tool_calls」
  • 工具入口收敛到 agent/tool/：core/tool.py（Tool + 装饰器）、core/utils.py（create_params_model）、read_file.py / write_file.py（具体工具）、__init__.py（registry 单例 + 注册）

Pydantic：校验与 Schema 一步到位

  • uv add pydantic==2.13.4 装依赖；BaseModel + Field(description=…, default=…) 定义参数
  • 实例化即校验：自动适配默认值（Counter() → n=0）、自动转换类型（Counter(n="123") → 123）、无法转换则报错（Counter(n=[1,2,3]) → ValidationError）
  • model_dump() 拿字典喂给原函数，model_json_schema() 直接拿参数 Schema——一次定义，两处复用
  • create_model("dynamic_model", filepath=(str, Field(description="…")), …) 让模型名和字段在运行时才确定：字段定义是「(类型, 默认值或 Field)」的元组，这正是 create_params_model 的骨架
  • create_params_model 用 inspect.signature 遍历参数：param.default is param.empty → 必填（Field(description=desc)，不设默认值）；有默认值 → 可选（Field(default=param.default, …)）。模型名取 f"{func.__name__}_params"

Tool 类、装饰器与调度中心

  • Tool(func, param_descriptions={…})：name=func.__name__、description=inspect.getdoc(func) or ""、param_model=create_params_model(func, param_descriptions)
  • schema() 返回 {"type": "function", "function": {name, description, parameters}}；parameters.properties 是遍历 param_model.model_json_schema() 后只保留 type 与 description（prop.get("type", "string")），required 沿用参数模型的 required
  • __call__：「调用 tool 和调用原函数行为一致」——先 param_model(**kwargs) 校验，再 str(self.func(**validated.model_dump())) 把结果转成字符串；异常时用 traceback.format_exception 把完整堆栈作为结果返回，工具链不会因一次失败而中断
  • @tool(filepath="…", content="…") 是语法糖：tool(**args) 返回 decorator，它把被装饰函数包成 Tool(func, param_descriptions=args) 并替换掉原函数名——从此函数定义处就是参数描述的归属地
  • _ToolRegistry：register(tool) 按 tool.name 存进 _tools；schemas() 返回列表可直接赋给 session.tools；invoke(message) 从助手消息里取 tool_calls，逐条 json.loads(arguments) 后执行，产出 {"role": "tool", "tool_call_id", "name", "content"} 列表；没有 tool_calls 时返回 None（表示此次无须调用工具）

分级测验

🌱 初级测验 · 概念

1. create_params_model(func, param_descriptions) 内部实际调用的 Pydantic API 是？
课件「再次认识 Pydantic」先演示 create_model("dynamic_model", filepath=(str, Field(description="…")), …)「动态创建模型」，再在「实现 create_params_model 函数」里把签名结果拼成字段元组后 return create_model(model_name, **args)。Field 只是字段定义的零件，真正造模型的是 create_model。
2. Tool.schema() 返回的字典，最外层是什么形状？
课件 schema() 原文：外层是 "type": "function"，内层 "function" 里才是 name / description / parameters；parameters 再按 properties 与 required 展开。第四个选项是 registry.invoke() 产出的工具结果消息，别混淆。
3. Tool 的 name 与 description 分别从哪里来？
课件 Tool.__init__ 原文：self.name = func.__name__、self.description = inspect.getdoc(func) or ""、self.param_descriptions = param_descriptions or {}。也就是说 param_descriptions 只提供参数级的描述文本，工具名与工具描述必须来自函数本体——这也是后面要做装饰器的动因之一。

🌿 中级测验 · 应用

4. 用 create_params_model 处理 def read_file(filepath: str, limit: int = 100)，生成的参数模型 Schema 里 required 是什么？
课件原文把两种情况分得很清楚：无默认值的参数走 args[pname] = (py_type, Field(description=desc))（必填，不设默认值），有默认值的走 Field(default=param.default, description=desc)（可选）。所以 filepath 进 required、limit 不进。若题目里两个参数都有默认值，required 会是空列表——但绝不会「没有这个键」，schema() 里写的是 param_schema.get("required", [])。
5. 下面这段代码执行后，模块里的 write_file 变成了什么？
课件装饰器原文只有三行：def decorator(func): return Tool(func, param_descriptions=args)——返回值是 Tool 实例，名字被替换。这带来两个直接后果：① 工具方法可以直接 registry.register(write_file)，并且 write_file.schema() 随时可用；② 它不再是函数，后续想再拿它做 inspect.signature() 反射（比如再包一层装饰器）会失败；同时它在模块级被调用时只会走 Tool.__call__ 的关键字参数路径。
6. Tool.schema() 组装 parameters.properties 时，对参数模型 Schema 里的每个字段做了什么？
课件原文是一个字典推导：{name: {"type": prop.get("type", "string"), "description": prop.get("description", "")} for name, prop in param_schema.get("properties", {}).items()}。所以 title、default 这类 Pydantic 附加键会被丢掉——参数是否可选由顶层 required 列表表达，不在单个 properties 里。若参数没有类型标注，create_params_model 会退回 Any，其 Schema 不含 type，于是这里回落到 "string"。

🎯 高级测验 · 综合

7. 一轮对话里模型同时返回了 3 个 tool_calls。registry.invoke(session.messages[-1]) 的返回值形状是？
invoke 先做 tool_calls = message.get("tool_calls", [])，空则返回 None；否则 for tc in message.get("tool_calls", []) 逐条执行并 results.append({...})——所以是「一次调用、批量执行、列表返回」，每项靠 tool_call_id 与请求配对。注意这正说明了返回类型为啥写成 list[dict] | None：调用方必须处理 None（第 9 题就踩在这上面）。
8. AI 把工具改成类方法后，Agent 启动时报错，日志里能看到 Field required [type=missing]。最可能的根因是？
Field required [type=missing] 是 Pydantic 校验失败的提示，说明 param_model(**kwargs) 收到了缺字段的输入。链路只有三处可能：① 模型给的 arguments 键名与函数参数名不一致（param_descriptions 只改描述、不改参数名）；② 该参数在函数里有默认值，但 create_params_model 没走 param.default is param.empty 的分支，于是被当成必填；③ 调用方把 arguments 解析错了。注意 Tool.__call__ 的 except 会把 完整堆栈字符串当结果返回，所以这类错误往往不抛异常，而是悄悄回灌进上下文——排查时要去工具结果里读堆栈。
9. 课件完整流程里的这段代码有什么隐患？
call_msg = registry.invoke(session.messages[-1]) 在模型没有发起工具调用时返回 None（课件注释原文：「工具调用结果，None 表示此次无须调用工具」）。而 session.messages += call_msg 是 __iadd__，本质等价于 list.extend(None) → TypeError: 'NoneType' object is not iterable。课件完整流程里用的是 if call_msg: 做守卫，所以示例本身是安全的；但把这段逻辑搬进循环或写成无守卫版本，就会在「纯聊天轮」上炸掉。改法二选一：保留 None 语义 + 调用方判空，或让 invoke 统一返回空列表（调用方就不用记「可能为 None」）。
