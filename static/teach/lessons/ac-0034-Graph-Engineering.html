知识速览

先花几分钟把这张图的三个零件认全——细节都在《34.Graph Engineering》里，测验和面试会考。

三个零件：State / Nodes / Edges（官方定义）

  • State（状态）：一个共享数据结构，代表应用当前时刻的快照——通常用一个共享的 state schema 定义
  • Nodes（节点）：编码 Agent 逻辑的函数——接收当前 state 作为输入，执行计算或副作用，返回更新后的 state
  • Edges（边）：决定「下一个执行哪个节点」的函数——可以是条件分支，也可以是固定跳转
  • 官方原话：把这些节点与边组合起来，就能构建会随时间演进状态的复杂循环工作流；真正的威力来自「如何管理这个状态」

图 vs 线性 loop：怎么选

  • 线性 loop 够用：任务只有一条主干（思考 → 调工具 → 再思考），终止条件简单——第 33 章的循环就能覆盖
  • 需要图：出现条件分支（按中间结果走不同处理链）、并行（多个子任务同时跑再汇合）、回退/重规划（失败回到上游节点）
  • 判断标准是流程形状，不是任务大小：需要「多条路径 + 汇合点」时，用 while 循环硬写会迅速变成面条代码
  • 与第 29 章呼应：子代理分派天然是图的一个分支；图只是把这种编排显式建模出来

图带来的三个工程约束

  • 终止必须显式：条件边要有能走到 END 的路径；否则图会在节点间无限打转——运行时通常有递归/步数上限，超限直接报错
  • 状态要可观测：节点只返回「对状态的更新」，调试时要能看到每一步状态怎么变的（回放/快照），否则出错只能靠猜
  • 节点应尽量幂等：失败重试、断点恢复都会重放节点；带副作用的节点（写文件、发请求）必须自己防重复

分级测验

🌱 初级测验 · 概念

1. 在图式编排里，「状态 State」指的是什么？
官方定义：State 是一个共享数据结构，表示应用当前状态的快照，通常由共享的 state schema 定义。它不是节点私有的，而是节点之间传递与更新的共同对象。
2. 「边 Edges」的职责是？
官方定义：Edges 是「根据当前状态决定下一个执行哪个节点」的函数，可以是条件分支或固定跳转。执行计算的是 Nodes，不是 Edges。
3. 官方说图的「真正威力」来自哪里？
官方原文强调：把节点与边组合起来能构建复杂循环流程，但真正的威力来自「如何管理这个状态」——状态设计才是图式编排的核心难点。

🌿 中级测验 · 应用

4. 下面哪种需求最需要从线性 loop 升级为图？
判断标准是流程形状：出现条件分支 + 汇合点（或并行再汇总）时，while 循环会迅速退化成面条代码；工具数量、模型位置、提示词写法都不改变流程形状。
5. 节点函数从「接收当前 state」到「返回更新后的 state」，这个约定带来什么直接后果？
节点只返回「对状态的更新」是图的关键契约：好处是每一步状态变化都可观测、节点可被重放与重试；代价是节点需要幂等（否则重放会重复副作用）。
6. 一个图跑到「审查 → 修改 → 审查」的循环里停不下来，最终报了步数/递归超限。最可能的原因是？
图里的循环必须有「满足条件就退出」的路径：条件边要能在某次判断后指向结束节点（或由状态里的计数/质量阈值决定退出）。否则运行时只能靠步数上限兜底并报错。

🎯 高级测验 · 综合

7. 把「并行三个子任务再汇合」建进图里，最需要在状态设计上考虑什么？
并行分支会同时更新状态：如果没有约定合并规则（累加、按键合并、取最新等），后写的一方会覆盖前一方。状态 schema 里「字段如何合并」是并行图最容易踩的坑。
8. 团队要做一个「长周期代码迁移 Agent」：扫描 → 分批改造 → 每批跑测试 → 失败的批回到改造步骤，全部通过后产出报告。这里图的哪个特征最关键？
这个流程的核心是「按测试结果决定回退还是前进」，也就是条件边；同时状态里必须能表达批次进度与失败原因，否则回退后无法知道该从哪继续——这也是断点恢复的前提。
9. 为什么说「带副作用的节点必须自己防重复」？
图把节点当作可重放的纯函数来对待：失败重试、从快照恢复都会再次执行节点。写文件、发请求、下单这类副作用要么做成幂等（按 key 去重），要么挪出节点交给显式的人工检查点。
