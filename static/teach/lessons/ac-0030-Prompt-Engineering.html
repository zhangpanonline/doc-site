Prompt Engineering

本课目标

完成本课后，你将能：

  1. 用一句话说清提示词工程在做什么——它经营的是上下文里的哪两格（系统提示词、用户问题），以及模型推理与回复在链路里的位置
  2. 复述本章指定学习资源《Prompt Engineering Guide》的骨架：提示词要素、通用技巧、技术、应用
  3. 说清 Prompt Engineering 在课程「六、工程方法论（30–34）」里的位置，以及它与 Context / Harness / Loop / Graph Engineering 的递进关系
  4. 把前 29 章学到的系统提示词原则（精简、自洽、全局约束、保持静态、结构化）接进「提示词工程」这条方法论主线

知识速览

本章课件很短：标题、一个指向《Prompt Engineering Guide》的 GitHub 链接、一张图。所以这一课只讲三件事——那张图说的是什么、提示词工程是什么、它在 Agent 工程体系里站在哪。细节都在《30.Prompt Engineering》与它给出的那份指南里，测验和面试会考。

本章那张图：提示词工程作用在哪一格

  • 图里只有一个动作：「提示词的工程」引出两条箭头，分别落在上下文里的系统提示词与用户问题上——它经营的就是这两格文本
  • 这两格与「回复」被同一个框圈住，框的名字叫上下文；整个上下文送进模型做推理（Reasoning），再由模型产出回复。回复是模型的输出，不是提示词工程能直接写的对象
  • 接上第 16 章：系统提示词往往出现在所有消息的最前面，模型在训练过程中会重点关注它；系统提示词的核心原则是精简、自洽、全局约束、保持静态、结构化
  • 接上第 17 章：会话每一轮都会把系统提示词 + 历史消息 + 新的用户消息拼起来交给模型——提示词工程管的，是这份拼接结果里你能亲手写的那部分文本
  • 一句话记忆：提示词工程 = 在「文本进入模型之前」把指令写清楚；它离模型最近，但管不到模型内部的推理，也管不到工具返回了什么

提示词工程是什么：定义与四要素

  • 本章指定资源的定义：《Prompt Engineering Guide》仓库 README 原文——Prompt engineering is a relatively new discipline for developing and optimizing prompts to efficiently use language models (LMs) for a wide variety of applications and research topics.（提示词工程是一门相对较新的学科，用于开发与优化提示词，以便在各种应用与研究场景中高效地使用语言模型。）
  • 它同时是一门「理解模型」的功夫：指南紧接着说，提示词工程技能有助于更好地理解大语言模型的能力与局限——所以写提示词不是玄学，而是拿它当探针去摸模型的边界
  • 提示词的四个可选要素（指南《提示词要素》原文）：指令——想要模型执行的特定任务或指令；上下文——包含外部信息或额外的上下文信息；输入数据——用户输入的内容或问题；输出指示——指定输出的类型或格式。指南明确：并非所有以上要素都是必须的
  • 通用技巧的主线是迭代（指南《设计提示的通用技巧》）：从简单开始，逐渐添加元素和上下文，并在过程中不断实验；同时要具体、把指令放在提示的开头，或用 ### 这类清晰分隔符把指令与上下文分开
  • 一句话记忆：要素齐全 + 结构清晰 + 反复迭代，把「你想让模型做什么」写到模型不会误解

它站在哪：工程方法论序列与学习路径

  • 序列里的位置：课程目录把 30–34 章编为「六、工程方法论」——Prompt → Context → Harness → Loop → Graph Engineering，本章是这条线的开篇
  • 与上下文工程的关系（官方定义）：Anthropic 在《Effective context engineering for AI agents》里把上下文工程称为提示词工程的自然演进，而不是替代——提示词工程指「为获得最佳结果而编写与组织 LLM 指令的方法」，其主要关注点是「如何写出有效的提示词，尤其是系统提示词」；上下文工程指「在 LLM 推理过程中策划与维护最优 token 集合的策略」，包括提示词之外还会落进上下文的一切（系统指令、工具、MCP、外部数据、消息历史）
  • 再往后三章各自的关注点：Harness Engineering 管「情境与状态管理 + 护栏 + 可观测」；Loop Engineering 管「让 Agent 自我推动的循环」；Graph Engineering 管「用图组织多步流程」。它们都不再只是「写一段文本」
  • 学习路径（本章给的就是一条外链）：先把指南的 Introduction 读一遍——LLM 设置 → 基本概念 → 提示词要素 → 通用技巧 → 示例；再按需进入 Techniques（zero-shot / few-shot / 思维链 / 自洽性 / 提示链 / ReAct / RAG …）与 Applications（函数调用、生成数据、生成代码 …），最后用 Prompt Hub 找现成范例
  • 一句话记忆：提示词工程是 Agent 工程的第一层，不是全部；上下文每一轮都在变，所以后面还要学「管理整个上下文状态」

🌱 初级测验 · 概念

1. 按本章课件那张图，「提示词的工程」直接经营的是上下文里的哪两部分？
课件图里「提示词的工程」只引出两条箭头，分别落在「系统提示词」和「用户问题」上；这两格和「回复」一起被圈在名为「上下文」的框里，整体送进模型做推理（Reasoning），再由模型产出回复。回复是模型的输出，不是提示词能直接写的对象；工具与 MCP 也不在这张图的作用面上。
2. 本章指定学习资源《Prompt Engineering Guide》对「提示词工程」的定义是？
指南 README 原文：Prompt engineering is a relatively new discipline for developing and optimizing prompts to efficiently use language models (LMs) for a wide variety of applications and research topics. 训练/微调属于第 14 章的训练阶段；接工具属于第 18–19 章；扩窗口属于上下文层的事——都不是本章的定义。
3. 本课程把 30–34 章编为「六、工程方法论」，本章 Prompt Engineering 在其中的位置是？
课程目录第六部分「工程方法论」是 30–34 章：Prompt → Context → Harness → Loop → Graph Engineering。原理篇（03–14）讲神经元、注意力、训练与推理；协议与扩展篇（24–29）讲 MCP、Skill、子代理。本章是工程方法论这条线的开篇，也是全课程从「原理 + 工程实现」转向「方法论」的第一章。

🌿 中级测验 · 应用

4. 指南把提示词拆成若干可选要素。提示词「把下面这段客服对话分为：投诉 / 咨询 / 退换。对话：……（一段文本）……类别：」中，最后的「类别：」属于哪个要素？
指南《提示词要素》的定义：指令＝想要模型执行的特定任务或指令；上下文＝外部信息或额外的上下文信息；输入数据＝用户输入的内容或问题；输出指示＝指定输出的类型或格式。开头那句「把对话分为投诉/咨询/退换」是指令，「对话：……」是输入数据，而「类别：」在告诉模型用什么字段、什么形式交出结果——属于输出指示。指南也强调四个要素并非都必须出现，这一例就几乎没有额外上下文。
5. 指南《设计提示的通用技巧》的第一条是「从简单开始」。某团队花一周写出 400 行系统提示词、上线后再没改动过。按这条技巧，最关键的缺失是？
指南原文：「在开始设计提示时，你应该记住，这实际上是一个迭代过程，需要大量的实验才能获得最佳结果……你可以从简单的提示词开始，并逐渐添加更多元素和上下文。」一次写成、之后不动，等于放弃了整条主线。few-shot 只是可选要素之一（指南明确「并非所有以上要素都是必须的」），把它说成「没有示例一定答错」是过度断言；是否用英文、窗口多大，都不是这条技巧的判断依据。
6. 第 16 章要求系统提示词「保持静态」，本章图又把系统提示词划进提示词工程的作用面。两条合起来，对「当前时间、当前登录用户是谁」这类每轮都可能变的信息，正确做法是？
第 16 章的五个原则里，这一条叫「保持静态」，并且正面案例是空的——课件用「当前用户是：<动态内容>，时间是：<动态内容>」当反面案例。本章把系统提示词交给「提示词工程」，意思是把稳定规则写清楚写好，而不是把它变成每轮重写的拼接板。注意区分：第 16 章的 system.j2 里确实有 {{ cwd }}、{{ is_git }}、{{ language }} 这类环境变量，但它们是「结构固定、取值随环境」的事实，取舍原则仍是「尽量固定」——高频变化的会话态信息（时间、用户、当前任务）更适合待在用户消息、工具结果或由上下文编排去安排。

🎯 高级测验 · 综合

7. 官方把上下文工程定义为「在 LLM 推理过程中策划与维护最优 token 集合」。以下四项工作里，哪一项不属于提示词工程，而属于上下文工程？
官方原文把两件事分开：提示词工程是「为获得最佳结果而编写与组织 LLM 指令的方法」，其主要关注点是「如何写出有效的提示词，尤其是系统提示词」；上下文工程是「在 LLM 推理过程中策划与维护最优 token 集合的策略」，包括那些「落在提示词之外、却仍会进入上下文」的一切（系统指令、工具、MCP、外部数据、消息历史）。A、B、C 动的都是指令本身，属于提示词工程；D 动的是每一轮真正进入模型的 token 集合——压缩、清理、隔离，属于上下文工程，也正是第 29 章子代理与第 23 章 Skill 按需加载在方法论上的位置。
8. 一个工具型 Agent 跑到第 30 轮开始漏信息、跑偏。团队第一反应是继续加长系统提示词。按本章图与官方对上下文状态的说明，最合理的诊断顺序是？
本章的图只画了「系统提示词 / 用户问题」两格，但多轮 Agent 的真实输入远不止这两格——官方列出的上下文状态还包括系统指令、工具、MCP、外部数据、消息历史，并指出 Agent 在循环中「会产生越来越多可能与下一轮推理相关的数据，这些信息必须被循环地精炼」。所以先定位层级：提示词本身有歧义、自相矛盾、规则残缺，就改提示词（第 16 章的精简 / 自洽 / 结构化）；历史被稀释、工具结果膨胀、该加载的 Skill 没按需进来，那是上下文编排的活（第 23 章 Skill、第 29 章子代理）。加长提示词与换大窗口都把问题归错了层，还直接撞上「精简」原则。
9. 团队把提示词工程当成一次性任务：上线前写死系统提示词，之后不再维护。按本章与官方给两者的关系，最准确的判断是？
官方把上下文工程称为提示词工程的「自然演进」而非替代：提示词工程聚焦怎么写提示词，尤其是系统提示词；而一旦 Agent 要在多轮、更长时间跨度上工作，就需要管理整个上下文状态。官方还给了一句判据——「与『写一段提示词』这种离散任务不同，上下文工程是迭代的，每次决定往模型里传什么时都会发生一次策划」。所以「写死之后就完事」在单轮分类/生成任务上还说得过去，在 Agent 循环里不成立；但反过来把它说成「提示词工程过时了」同样是误读——本章这张图画的正是它不可替代的那一格。
