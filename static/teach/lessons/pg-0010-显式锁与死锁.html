显式锁与死锁

来源：官方文档 §13.3 显式锁定（postgres.cn）非渡一课程内容预计 15–20 分钟9 道分级测验 + 4 道最终考核 + 面试实战

本课目标

完成本课后，你将能：

  1. 说出官方对显式锁的定位（MVCC 无法给出期望行为的情境）与「命令自动取锁」的常识

知识速览

先花几分钟把核心机制过一遍——细节与测验依据都来自官方文档 §13.3。

显式锁的定位（官方要点）

  • 锁模式用于MVCC 无法给出期望行为的情境中、由应用控制的锁（官方原文）
  • 大多数命令自动获取恰当的锁——官方例：TRUNCATE 取得 ACCESS EXCLUSIVE 锁防止并发冲突
  • pg_locks 系统视图：查看当前未解除的锁列表
  • LOCK TABLE ... IN 模式 显式获取表级锁（手动锁定的入口）

表级锁与行级锁

  • 表级锁：ACCESS SHARE ~ ACCESS EXCLUSIVE 多模式；名字含 row 的（ROW EXCLUSIVE 等）也是表级锁——官方原文「这些名称是历史遗产」
  • 行级锁：FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE——SELECT ... FOR UPDATE 把「先查后改」变原子

死锁（§13.3.4）

  • 两个事务互相等待对方的锁 → PG 自动检测并终止其中一个（deadlock detected，不会无限挂起）
  • 预防：一致的加锁顺序、缩短事务、缩短锁持有时间
  • 应用侧：捕获死锁错误重试——死锁是并发系统正常现象

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与官方文档覆盖的内容。

🌱 初级测验 · 概念

1. 官方说显式锁用于什么情境？
官方原文：这些模式可以用于在 MVCC 无法给出期望行为的情境中由应用控制的锁。
2. 官方说大多数命令与锁的关系是？
官方原文：大多数命令会自动获取恰当的锁——官方例子：TRUNCATE 无法与其他操作并发，故取得 ACCESS EXCLUSIVE 锁。
3. 查看当前未解除的锁用哪个视图？
官方原文：要检查当前未解除的锁列表，可以使用 pg_locks 系统视图。

🌿 中级测验 · 应用

4. ROW EXCLUSIVE 是什么级别的锁？
官方原文：所有锁模式都是表级锁，即使名字包含 row——这些名称是历史遗产。
5. 「先查余额再扣款」要原子化，标准写法是？
FOR UPDATE 锁定被检查的行——其他事务要改这行必须等，竞态窗口被锁闭合。
6. 两个事务互相等待对方持有的锁，PG 会怎样？
PG 有死锁检测器：发现死锁即终止其中一个事务（deadlock detected）——不会无限等待。

🎯 高级测验 · 综合

7. 预防死锁最常用的工程手段是？
死锁四条件里的「循环等待」靠全局一致的加锁顺序破坏——最便宜且改动最小的预防。
8. 应用收到 deadlock detected 错误，正确的应对是？
被终止的事务本来就该能安全重放——死锁在并发系统里是正常现象，重试是标准应对。
9. 转账 A→B 与 B→A 并发可能死锁；按账户 id 排序后按序 FOR UPDATE 的意义是？
先锁 id 小的行再锁大的——两个事务永远同序取锁，循环等待不可能发生。

最终考核

四道题覆盖本课全部要点——答完它们，显式锁与死锁就过关了。

考核一：为什么「SELECT ... FOR UPDATE」要放在事务里使用？
行锁随事务结束释放——锁的保护期必须覆盖「检查→修改→提交」的整个过程。
考核二：TRUNCATE 与 SELECT 并发执行时，官方说 TRUNCATE 会怎样？
官方原文：TRUNCATE 无法安全地与同一表上的其他操作并发执行，因此它在表上获得 ACCESS EXCLUSIVE 锁来强制。
考核三：业务代码持有行锁期间又调了一个慢外部 API（2 秒）。问题在哪？
官方预防原则之一就是「缩短锁的持有时间」——持锁期间做慢 IO 等于把所有竞争方都拖住。
考核四：pg_locks 里看到 grant = false 的一行，表示什么？
pg_locks 的 granted 字段：true=持有、false=等待中——排查锁等待时先看 grant=false 的行是谁在等谁。

四道考核全部答对，说明你掌握了显式锁与死锁——继续学习 pg-11 · EXPLAIN 进阶与查询优化。
