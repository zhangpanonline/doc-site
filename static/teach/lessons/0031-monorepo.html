知识速览

先花几分钟把核心机制过一遍——细节都在《31.monorepo》里，测验和考核会考。

workspace 三步

1. 根项目 members = ["packages/*", "app/*"]
2. uv init --lib packages/shared 等创建成员
3. [tool.uv.sources] shared = { workspace = true } ─ 源码级引用 ─▶ 改 shared 立即全仓生效

⚙️ uv sync --all-packages 解析全部成员依赖，生成统一 uv.lock 与根 .venv。

三个要点

  1. [tool.uv.sources] 是 workspace 核心：声明 shared = { workspace = true } 后，依赖从工作区源码链接而不是 PyPI 下载；同名时 workspace 优先。官方文档：uv workspaces
  2. 三种引用模式：workspace = true（仓内成员，改码即时生效）；path = "../utils"（仓外本地路径）；git = "..." rev = "v0.1.0"（Git 仓库）。
  3. members 支持 glob：packages/* 直接子目录；packages/** 含嵌套；多个目录写多行。

🌱 初级测验 · 概念

1. Monorepo 相比 MultiRepo 的核心优势是？
MultiRepo 要发版才能共享；Monorepo 用 workspace 源码链接，改 shared 全仓立即生效，跨包改动一次提交。详见「Multirepo VS Monorepo」对比表。
2. 根 pyproject 声明 workspace 成员的段是？
[tool.uv.workspace] members = ["packages/*", "app/*"]——members 支持 glob 模式。详见「第一步：初始化根项目」。
3. 成员包依赖另一个成员包，正确写法是？
两处都要写：dependencies = ["shared"] 声明依赖 + [tool.uv.sources] shared = { workspace = true } 告诉 uv「从工作区取，别去 PyPI」。只写前者会去 PyPI 找 ✗。详见「第三步：成员包依赖」。

🌿 中级测验 · 应用

4. 解析全部成员依赖并统一安装的命令是？
uv sync --all-packages 读取所有成员 pyproject、解析完整依赖树、生成统一 uv.lock、建根 .venv。详见「第四步：同步安装」。
5. 运行指定成员包的脚本，命令是？
uv run --package 成员包名 指定以哪个成员的依赖环境运行。直接 python 运行拿不到 workspace 依赖 ✗。详见「第五步：运行」。
6. workspace 中的包与 PyPI 同名时，uv 会？
同名时 workspace 优先；要强制走 PyPI 写 { workspace = false }。详见「第三步」提示框。

🎯 高级测验 · 综合

7. 根项目要纳入 packages/ 与 app/ 下的成员，正确的 members 写法是？
可以配置多个目录：members = ["packages/*", "app/*"]。第二个不是只能一个 ✗；第三个 ** 匹配所有嵌套子目录，会纳入不想要的深层目录（源工程 app/web-service 是两层，用 app/* 即可）✗；第四个不是合法写法 ✗。
8. agents 包依赖 shared 包，pyproject.toml 正确写法是？
两处一致：dependencies = ["shared"] + [tool.uv.sources] shared = { workspace = true }。workspace = false 是强制走 PyPI ✗；sources 键名与依赖名不一致则链接失败 ✗；没有 @workspace 语法 ✗。
9. 引用「工作区外的本地包」与「Git 仓库里的包」，分别用什么写法？
三种模式：仓内 workspace = true；仓外本地 path = "../utils"；Git 仓库 git = "URL", rev = "版本"（可引用未发布到 PyPI 的依赖）。详见「包间依赖的三种模式」。

最终考核

下面是《31.monorepo》源课程作业（手工复现 workspace 工程并发布 shared/agents）的改编题——这就是本课的最终考核。规则：不查资料、不运行代码，先在心里选出答案，再点击核对。

考核一（根配置）：根项目要纳入 packages/ 与 app/ 下的成员，正确的 members 写法是？
可以配置多个目录：members = ["packages/*", "app/*"]。第二个不是只能一个 ✗；第三个 ** 匹配所有嵌套子目录，会纳入不想要的深层目录（源工程 app/web-service 是两层，用 app/* 即可）✗；第四个不是合法写法 ✗。
考核二（成员依赖）：agents 包依赖 shared 包，pyproject.toml 正确写法是？
两处一致：dependencies = ["shared"] + [tool.uv.sources] shared = { workspace = true }。workspace = false 是强制走 PyPI ✗；sources 键名与依赖名不一致则链接失败 ✗；没有 @workspace 语法 ✗。
考核三（引用模式）：引用「工作区外的本地包」与「Git 仓库里的包」，分别用什么写法？
三种模式：仓内 workspace = true；仓外本地 path = "../utils"；Git 仓库 git = "URL", rev = "版本"（可引用未发布到 PyPI 的依赖）。详见「包间依赖的三种模式」。
考核四（复现预测）：按源作业手工复现 my-monorepo（根 + packages/shared + packages/agents + app/web-service，agents 依赖 shared、web-service 依赖 agents），uv tree --package web-service 的输出会包含？
依赖树沿 web-service → agents → shared 逐层展开，成员包从工作区源码链接（依赖解析发生在本地，无需 PyPI 上存在这些包）——若写成「标注来自 PyPI」则说明 sources 配置没生效。

四道考核全部答对，说明你已经掌握 Monorepo——可以继续学习《30.断点调试》了。

💼 面试实战

下面是真实面试官会问的问题，选自中文互联网面试题集（出处附后）。先自己回答，再点击核对。三级面试难度：中级考应用，高级考陷阱，专家考机制与设计。

⚡ 中级面试题

面试题一（monorepo vs multirepo·工程必问）：什么场景选 Monorepo？
Monorepo 适合紧密协作的微服务、SDK 集合、工具链：源码级共享（不发版即时生效）、跨包改动一次原子提交、统一工具与规范、CI 可增量检测。团队独立、版本节奏不一致的场景则 MultiRepo 更合适——选型看协作密度而非技术时髦。出处：CSDN「100 道 Python 面试必背题目（工程实践篇）」
面试题二（workspace 机制·追问）：[tool.uv.sources] shared = { workspace = true } 的作用是？
这是 uv workspace 的核心机制：声明后 shared 依赖从工作区内的同名成员包源码链接（本地直接引用，修改即时生效），不会去 PyPI 下载；同名冲突时 workspace 优先。出处：uv 官方文档 Using workspaces（中文技术社区广泛收录）

🔥 高级面试题

面试题三（循环依赖·深水区）：workspace 里 shared 与 agents 互相依赖（循环依赖），uv 会怎样？
workspace 的依赖图是有向无环图（DAG）：成员间循环依赖会让 uv 解析报错——依赖环意味着职责划分出了问题。解法：抽出公共部分下沉（如 shared 的公共段拆成 shared-core），让依赖方向单向。出处：uv 官方文档 Using workspaces
面试题四（发布策略·工程）：monorepo 里多个包，发布策略如何选？
Monorepo 的最佳实践是基于变更的逐包发布：只发布本次改动实际影响的包（配合 uv build --package 包名），版本各自独立——全量发布会造成无谓的版本号膨胀与下游升级负担。这是「单一仓库、多包版本」的工程核心。出处：CSDN「100 道 Python 面试必背题目（工程实践篇）」

🧠 专家面试题

专家题一（同名冲突·机制）：workspace 成员包与 PyPI 上同名包都存在，如何强制用 PyPI 版本？
同名时默认 workspace 优先；要强制走 PyPI 写 [tool.uv.sources] 包名 = { workspace = false }——这是「本地影子包」与「发布版」并存的开关。理解这个开关说明吃透了 sources 的解析优先级。出处：uv 官方文档 Using workspaces
专家题二（增量 CI·工程）：monorepo 的 CI 如何避免「改一个包、全量重测」？
Monorepo CI 的关键是增量检测：通过依赖图计算本次变更影响了哪些包（本包 + 依赖它的下游包），只对这些包跑测试/构建——全量重测在包多时无法接受。这是 monorepo 选型时「统一 CI，可增量检测受影响的包」优势的具体实现。出处同面试题四
