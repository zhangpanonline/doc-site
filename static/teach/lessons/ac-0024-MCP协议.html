知识速览

先花几分钟把本章的骨架过一遍——细节都在《24.MCP协议》里，测验和面试会考。

MCP 要解决什么

  • 课件第一句就是全部动机：MCP 定义了 Agent 和外部工具的通信标准（官网 modelcontextprotocol.io）
  • 官方定义：「MCP (Model Context Protocol) is an open-source standard for connecting AI applications to external systems.」——它的自我类比是 「AI 应用的 USB-C 接口」
  • 没有标准时，每个 Agent 对接每个工具都要单独写一套适配代码，适配量是 $M \times N$；有了标准协议，双方各自实现协议即可，适配量降到 $M + N$
  • 协议是分层的：Base Protocol（JSON-RPC 消息）与 Lifecycle Management（初始化、能力协商、会话控制）是所有实现必须支持的；Resources / Prompts / Tools、Sampling、Roots 等按需实现（MUST / MAY 是规范里的硬性分级）

协议内核三要素

  • 通信角色：客户端 MCP Client（通常是 Agent）↔ 服务端 MCP Server（工具提供者）。任何匹配 MCP 协议的程序都可以作为 MCP Client——所以调试器 inspector 也能当 Client 用
  • 通信方式：stdio——Client 把 Server 作为子进程启动，通过 stdin / stdout 在本地进程间通信；http——通过 HTTP 协议通信（现行规范里叫 Streamable HTTP，是 2024-11-05 版 HTTP+SSE 的替代者）
  • 通信格式：JSON-RPC 2.0。信封固定四个字段——jsonrpc / id / method / params（params 可省略）；规范原文：「All messages between MCP clients and servers MUST follow the JSON-RPC 2.0 specification.」
  • MCP 在标准 JSON-RPC 之上加了两条约束：id 不能为 null，且同一会话内不得复用已用过的 id——它靠 id 把响应配回请求

通信内容与能力协商

  • initialize（初始化）必须是 Client 与 Server 的第一次交互：一次谈定协议版本兼容性、双方能力（capabilities）、实现信息（clientInfo / serverInfo）——这个过程就叫能力协商
  • 能力只有声明过才允许使用：Server 支持工具，必须在 initialize 响应里声明 tools 能力；Client 看到之后才去调 tools/list
  • tools/list（发现工具列表）：拿到工具名、描述与参数 Schema；tools/call（调用工具）：params 里带工具名与实参
  • 生命周期一共三段：Initialization（能力协商 + 版本协商）→ Operation（正常通信）→ Shutdown（优雅关闭）
  • 观测全程用 inspector（通常用于调试 MCP Server，可以清楚看到通信内容）：npx -y @modelcontextprotocol/inspector@1.0.0（课程口径；官方当前文档写作 npx @modelcontextprotocol/inspector，同一个包）；官方 time 测试服务器 uvx mcp-server-time；微软官方文档服务 https://learn.microsoft.com/api/mcp

🌱 初级测验 · 概念

1. MCP（模型上下文协议）定义的是哪两者之间的通信标准？
课件原文：「MCP 定义了 Agent 和 外部工具 的 通信标准」。官方文档的表述是「an open-source standard for connecting AI applications to external systems」——落点始终在「AI 应用 ↔ 外部系统（数据源、工具、工作流）」。
2. MCP 规定的通信格式是？
课件「协议内核」第三条：通信格式：JSON-RPC 2.0，并给出示例信封 {"jsonrpc": "2.0", "id": "req-123", "method": "tools/call", "params": {...}}。官方规范把这句写成了硬约束：「All messages between MCP clients and servers MUST follow the JSON-RPC 2.0 specification.」
3. MCP 标准里的两个通信角色分别是谁？
课件「协议内核 · 通信角色」原文：客户端 MCP Client——通常是 Agent；服务端 MCP Server——工具提供者。并且「任何匹配 MCP 协议的程序都可以作为 MCP Client」，所以课程里用 inspector 来充当 Client 调试 Server。

🌿 中级测验 · 应用

4. 在 stdio 传输下，一条 JSON-RPC 消息是怎么从 Client 走到 Server 的？
课件原文：stdio「通过 stdin、stdout 在本地进程间通信」。官方规范补充了细节：Client 启动 Server 子进程，消息是单行 JSON-RPC（以换行分隔，内部不得含换行），且 stdout 只允许出现合法的 MCP 消息。HTTP 是另一种传输，不是 stdio 的实现方式。
5. 下面四条里，哪一条是 MCP 在标准 JSON-RPC 2.0 之上额外加的约束？
官方 Base Protocol 原文：「Unlike base JSON-RPC, the ID MUST NOT be null.」「The request ID MUST NOT have been previously used by the requestor within the same session.」其余三条是 JSON-RPC 2.0 本身就有的通用规则，不是 MCP 的额外约束。id 的存在意义就是让响应能配回请求，所以不能为空、不能重号。
6. 一个 stdio 版 MCP Server，作者在工具函数里写了 print("calling get_time") 打调试日志。最可能的后果是？
官方规范 stdio 一节：「The server MUST NOT write anything to its stdout that is not a valid MCP message.」「The server MAY write UTF-8 strings to its standard error (stderr) for logging purposes.」官方调试文档也说得很直白：「Local MCP servers should not log messages to stdout (standard out), as this will interfere with protocol operation.」——日志一律走 stderr。这类故障的表现往往离原因很远（表现为连不上、初始化失败），排查时要先怀疑 stdout 被污染。

🎯 高级测验 · 综合

7. 一个自研 Client 连上 MCP Server 后，跳过 initialize 直接发 tools/call。按规范的生命周期，问题出在哪？
官方 Lifecycle 原文：「The initialization phase MUST be the first interaction between client and server.」这一阶段建立协议版本兼容性、交换并协商能力、交换实现信息。而 Tools 一节规定：「Servers that support tools MUST declare the tools capability」——没有能力协商，Client 就无法判断该不该、能不能调用工具，也可能用错协议版本。生命周期只有三段：Initialization → Operation → Shutdown。
8. 把一个原本本地 stdio 的 MCP Server 改造成 Streamable HTTP、暴露到内网给多个 Agent 共用。按官方安全要求，上线前必须补的措施是？
官方规范 Streamable HTTP 的 Security Warning 三条原文：①「Servers MUST validate the Origin header on all incoming connections to prevent DNS rebinding attacks」；②「When running locally, servers SHOULD bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0)」；③「Servers SHOULD implement proper authentication for all connections」。另外，Client 发 POST 时 必须同时声明 application/json 与 text/event-stream，把 Accept 收窄成只允许 JSON 反而会让合规的 SSE 响应被拒——选项 D 与官方要求相反。
9. 用 inspector 连上一个 Server，按「协商能力 → 发现工具 → 调用 time 工具」的顺序操作。其中「调用 time 工具」这一步发出的请求，method 字段应该是什么？
课件「通信内容」表给出的就是这条主线：initialize（初始化）→ tools/list（发现工具列表）→ tools/call（调用工具）。「调用工具」一定落在 tools/call，其 params 里带工具名与实参。initialize 是会话第一步（能力协商），tools/list 只负责「有哪些工具」，notifications/message 是通知类消息、没有 id、不用于发起调用——四者职责互不重叠也是本节要记的点。
