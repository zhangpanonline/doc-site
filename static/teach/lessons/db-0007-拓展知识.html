知识速览

先花几分钟把核心机制过一遍——细节都在《07.拓展知识》里，测验和考核会考。

PG 能力地图（高频几项）

  1. 备份与恢复：pg_dump 倒出存档、pg_restore 还原——上线第一件事。
  2. 视图 vs 物化视图：视图 = 存 SQL 的虚拟表（实时）；物化视图 = 把结果存成物理表（快、但需定时刷新）。
  3. 触发器：插/改/删时自动执行逻辑（审计日志、自动 updated_at）。
  4. CTE：WITH 名字 AS (子查询) 给嵌套 SQL 命名，可读性 + 递归查询。
  5. GIN/GiST 索引：给 JSONB、数组、全文、地理位置用的特殊索引；BRIN 是超轻量块范围索引（时间序列日志）。
  6. VACUUM：回收 MVCC 死元组、释放空间、更新统计——PG 的「保洁工」。
  7. 复制：流复制（高可用/备机）、逻辑复制（按表按行选择性同步）。

数据库分类

关系型（SQL）  表+行，强 ACID，JOIN        PostgreSQL / MySQL
文档型          JSON 文档，Schema-less       MongoDB
键值型         K-V，超高读写                Redis
列族型         列族，海量写入               HBase / Cassandra
图数据库        节点+边，深度关联            Neo4j
（键值/列族/图 统称 NoSQL；文档型常归入 NoSQL）

三范式一句话

1NF  列不可再分（一个格子一个值）
2NF  非主键列完全依赖主键（复合主键时不能只依赖一部分）
3NF  非主键列之间无传递依赖（院系名不能跟着院系ID一起塞进学生表）

分级测验

三道一组，先做后点——点击选项立刻出对错与解释。

🌱 初级 · 概念

1. 视图（View）与物化视图（Materialized View）的区别是？
视图 = 虚拟表：只存查询定义，每次查都现场算（实时、慢查询也实时慢）。物化视图 = 结果落地成物理表：查得快，但数据是上次刷新的快照——适合大报表、定时刷新的看板。
2. VACUUM 的作用是？
MVCC 下 DELETE/UPDATE 产生 dead tuple，空间不自动回收。VACUUM 定期清理旧版本、回收磁盘、更新统计信息——频繁更新/删除的表变慢、磁盘不释放时想到它（autovacuum 会自动跑）。
3. 图数据库最适合的场景是？
图数据库 = 节点 + 边，天生擅长多跳关联（几度人脉、最短路径、商品推荐）。订单流水要强 ACID 用关系型；热点缓存用 Redis；全文检索用 PG 的 tsvector 或专门引擎。

🌿 中级 · 应用

4. 审计日志（对某表的每次修改自动记录）最适合用哪个能力？
触发器 = 表上插/改/删时自动执行的逻辑：审计日志、数据同步、自动更新 updated_at 都是典型用法。注意它逻辑隐蔽、难调试，慎用。
5. 时间序列日志（TB 级、天然按时间有序、只做范围查询），最合适的索引是？
BRIN = Block Range Index：按磁盘块范围记「这块的数据范围」，占空间极小，适合「超大表 + 数据天然有序（时间序列日志）+ 范围查询」的组合。GIN/GiST 面向 JSONB/数组/全文/地理；Hash 只管等值。
6. 想在 PG 里直接查另一个 MySQL 库的表做临时报表，用什么？
FDW（Foreign Data Wrapper）= 外部表：在 PG 里像查本地表一样查 MySQL/Oracle/CSV——跨库整合、数据迁移、临时报表的利器。逻辑复制是持续同步，不是「查」；表继承是父子表结构复用。

🎯 高级 · 综合

7. 学生表里同时存「院系ID」和「院系名称」，违反哪条范式？怎么修？
学生表主键是学号；「院系名称」不直接依赖学号，而是依赖非主键列院系ID → 传递依赖 → 违反 3NF。修法：拆出「院系表（ID, 名称）」，学生表只留院系ID 外键。
8. 订单明细表主键 (订单ID, 商品ID)，但「商品名称」列只依赖商品ID——违反哪条？
复合主键下，非主键列必须依赖「整个」主键。商品名称只依赖 (订单ID, 商品ID) 中的商品ID → 部分依赖 → 违反 2NF。修法：商品名称放商品表，明细表只留商品ID 外键（这正是电商数据库设计里的做法）。
9. 「一行里电话列存 138xxx, 139xxx 两个号码」违反哪条范式？
1NF 要求列原子性：一个格子只存一个值，不存数组/逗号串。多电话的正确设计：拆电话子表（用户 1:N 电话）。逗号串之后按号码查询、去重都会很痛苦。

最终考核

本节源课程没有作业，下面四道题由《07.拓展知识》内容改编——这就是本课的最终考核。规则：不查资料，先在脑中作答，再点击核对。全部答对且能讲清理由，才算过关。

考核一（能力选配）：下列「场景 → 能力」配对，全部正确的是？
配对：流/逻辑复制 → 读写分离与灾备；BRIN → 天然有序的巨表范围查询；触发器 → 审计日志。另两组也常用：表分区 → 按时间淘汰的超大表；物化视图 → 定时刷新的统计看板。
考核二（选型）：社交 App 的「好友关系 + 二度人脉推荐」，主数据库之外应该补什么？
「谁认识谁、几度可达」是典型的图问题（节点+边），图数据库的多跳遍历远快于关系型的多层 JOIN 递归。主库仍用关系型存用户资料；好友图放 Neo4j 类图库是业界常见组合。
考核三（范式诊断）：下面哪张表设计同时违反了 2NF 和 3NF？
orders 表里 customer_name 不直接依赖主键 id，而是依赖非主键列 customer_id → 传递依赖（3NF）；若换个角度按联合主键审视也是部分依赖（2NF）。修法：customer 信息拆进 customers 表，orders 只留 customer_id。其余三项是合规设计。
考核四（能力辨析）：大报表查询很慢，且业务能接受数据延迟 1 小时，最佳优化是？
能接受延迟 → 物化视图：复杂聚合先算好存成物理表（每小时 REFRESH），查询变「读表」。普通视图每次现场算，不解决慢；CTE 只改善可读性；GIN 是 JSONB/全文索引，不是万能加速器。

💼 面试实战

下面是真实面试官会问的问题，选自中文互联网面试题集（出处附后）。先自己回答，再点击核对。三级面试难度：中级考应用，高级考陷阱，专家考机制与设计。

⚡ 中级面试题

面试题一（必考）：说说数据库三大范式？
标准答案：1NF 每列原子不可再分；2NF 非主键列完全依赖主键（消除部分依赖）；3NF 非主键列无传递依赖。可再补一句：范式是减少冗余的指导原则，工程上偶尔会为了性能做反范式冗余。出处：CSDN「MySQL 索引、锁、三大范式一篇搞定」
面试题二（选型）：Redis 和 PostgreSQL 的本质区别是？
模型不同：Redis = K-V 内存库，超高读写、操作简单，但无 JOIN、数据要能放进内存；PG = 关系型磁盘库，强 ACID、SQL、事务。典型分工：Redis 做缓存/计数/会话，PG 做数据的家。出处：牛客专刊「数据库索引-笔面试必考点 15 讲」

🔥 高级面试题

面试题三（陷阱题）：关于视图，下列说法正确的是？
视图 = 命名的查询定义，不存数据、不缓存结果，每次现场算——它的价值是简化复杂 SQL、权限控制（只暴露部分列/行）、接口稳定，而不是提速。要提速的是物化视图。出处：CSDN「3.数据库部分面试题」
面试题四（场景陷阱）：JSON 数据都存 MongoDB，对吗？
PG 原生支持 JSON/JSONB：JSONB 二进制存储、可建 GIN 索引、按字段查询高效——关系型与 NoSQL 能力可以混用（课件能力表专门列了 JSON/JSONB 与 GIN/GiST 索引）。选型看的是查询模式与一致性要求，不是「存了什么格式」。出处：CSDN「3.数据库部分面试题」

🧠 专家面试题

面试题五（高可用设计）：主库突然宕机，靠什么能力自动顶上？
高可用 = 流复制：主库的 WAL 实时同步到备机，主库宕机后备机提升为新主（配合 repmgr/Patroni 等做自动故障转移）。逻辑复制用于按表按行选择性地同步（数据分发/跨版本），不是故障接管。
面试题六（反范式权衡）：为什么实际项目里有时故意违反三范式？
范式减少冗余但增加 JOIN（查询成本）。工程上常做受控冗余：订单表存下单时的商品名/单价快照（商品改价不影响历史订单）——这不是没学好范式，而是性能与历史可追溯性的刻意权衡。关键在「受控」：知道冗余了、谁来维护它。出处：CSDN「MySQL 索引、锁、三大范式一篇搞定」
