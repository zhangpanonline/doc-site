会话

配合《17.会话》使用预计 15–20 分钟9 道分级测验 + 面试实战

本课目标

完成本课后，你将能：

  1. 说清「模型 API 无状态」与「会话对象」的关系：多轮对话靠的是每轮把历史消息整条重发
  2. 读懂 agent/session.py：uuid4 生成 id、messages 列表、add_message、save 与 load（classmethod 恢复同一个 id）
  3. 读懂 agent/model.py 的双入口：invoke / invoke_stream 都能吃 list[dict] 或 Session，并自动把 assistant 回复写回会话
  4. 判断会话工程的三个高危点——生成器惰性导致丢消息、历史被改写导致缓存失效、每轮重发整段历史带来的 token 成本增长

知识速览

先花几分钟把「无状态 API → 会话对象 → 持久化与成本」这条线过一遍——细节都在《17.会话》里，测验和面试会考。

从「两次独立调用」到「一个会话」

  • 问题出在哪：课件先演示两次独立调用——第 1 次发「uv是什么？」，第 2 次只发 system +「如何安装？」。模型服务端的 Chat API 是无状态的：它不记得上一轮，所以它根本不知道「如何安装」安装的是什么
  • 会话写法：session = Session() → add_message(system) → add_message(user: uv是什么？) → model.invoke_stream(session)；第二轮只需再 add_message(user: 如何安装？)，整条历史会自动带上
  • 会话说白了就是三件套：id（str(uuid.uuid4())）、messages: list[dict]、add_message——它就是「一份只增不改的消息列表」的容器
  • 工程后果：因为每轮都要把整份历史放进报文，历史越长，每轮越贵——这直接引出下面的缓存与成本问题

model.py 的双入口与「自动回写」

  • 参数的双重身份：def invoke(self, messages: list[dict] | Session) 与 invoke_stream 同一个签名——先 if isinstance(messages, Session)，把 session 记下来，再把 messages = session.messages 抽出来发给 API
  • invoke 的回写：session.add_message(response.choices[0].message.to_dict())——直接把响应的消息对象转成 dict 存回去
  • invoke_stream 的回写：边流边累积 full_content 与 full_reasoning_content，循环结束后构造 {"role": "assistant", "content": full_content}；只要出现过 reasoning_content / reasoning 字段，就把它一并塞进这条消息（msg[reasoning_field] = full_reasoning_content）再 add_message
  • 所以别重复写：传了 Session 之后不要再手工 add_message 一条 assistant 消息，否则历史里会出现两条连续 assistant 消息，把上下文搅乱
  • 为什么思维链要留在上下文里：课件的两条最佳实践之一是「上下文中应保留思维链」——不满足会导致推理上下文丢失，模型回复质量下降

持久化：save / load 与两条代价

  • save：目录固定为模块同级的 sessions（Path(__file__).parent / "sessions"），mkdir(parents=True, exist_ok=True) 后写 f"{self.id}.json"，内容 {"id": …, "messages": …}，用 json.dump(..., ensure_ascii=False, indent=2) 保持中文可读
  • load：@classmethod，读 {session_id}.json；先 cls() 造实例（构造函数会先生成一个新 uuid4），再用文件里的 data["id"] 与 data["messages"] 覆盖——所以「会话 id 是持久身份，不由构造函数决定」
  • 代价一 · 成本随轮数增长：第 1 轮只发 1 轮内容，第 2 轮发 2 轮，第 n 轮发 n 轮。设每轮平均新增 $t$ 个 token、系统提示词 $c$ 个 token，则第 n 轮的 prompt 长度为 $c + n\,t$，前 n 轮累计发送量是 $$S(n)=\sum_{k=1}^{n}(c+k\,t)=n\,c+\frac{t\,n(n+1)}{2}=\frac{t}{2}n^{2}+O(n)$$ ——平方级增长。这也是「会话越聊越贵」的数学形态。
  • 代价二 · 缓存命中靠前缀：官方机制是「请求先检查 prompt 的开头部分（prefix）是否已缓存，命中就复用」；多轮对话要命中，就得把新消息追加到 messages 数组末尾。课件的另一条最佳实践正是「历史上下文不可修改」——不满足会导致难以命中模型服务商的 prompt cache。删改、重排、把历史整体替换成摘要，都会让前缀变化、整段从头处理
  • 一句话抓手：历史只增不改、新消息只追加到末尾、思维链不删——这是会话层的三条铁律

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《17.会话》覆盖的内容。

🌱 初级测验 · 概念

1. 本章 Session 的会话 id 是怎么来的？
本章代码「新增文件 agent/session.py」原文：self.id = str(uuid.uuid4())。save() 用它当文件名（f"{self.id}.json"），load() 读回来后再用 data["id"] 覆盖实例上的 id——也就是说 id 是这份会话的持久身份，而不是每次构造时随便新生成一个。
2. model.invoke_stream(session) 被完整消费之后，session.messages 里会发生什么？
本章代码「修改文件 agent/model.py」：invoke_stream 在流结束后执行 msg = {"role": "assistant", "content": full_content}，并且在出现过思维链字段时补上 msg[reasoning_field] = full_reasoning_content，最后 session.add_message(msg)。所以会话里长出来的是一条带思维链的 assistant 消息——这正是「上下文中应保留思维链」这条最佳实践的落点。
3. 课件把「两次独立调用」和「会话写法」摆在一起对比，核心差别是？
课件第 2 次独立调用只发了 render_prompt("system") + 「如何安装？」，模型无从知道上文问的是 uv；换成会话后，第二轮只需要 session.add_message({"role":"user","content":"如何安装？"})，历史里已经存着上一轮的 user 与 assistant 消息，会一起发送。Chat API 本身无状态，所谓「记住」= 客户端每轮重发历史。

🌿 中级测验 · 应用

4. Session.load(session_id) 这个 classmethod 具体做了什么？
本章代码原文：session = cls() → session.id = data["id"] → session.messages = data["messages"]。构造函数里刚生成的 uuid 立刻被文件里的 id 覆盖——所以恢复出来的会话 id 与保存前一致。load 里没有任何参数校验与异常处理：文件不存在时抛的是 FileNotFoundError。
5. 一个会话连问 10 轮，系统提示词每次 800 token，每轮新增内容（提问 + 回答）平均 200 token。第 10 轮请求的 prompt 长度、以及 10 轮累计发送量分别约为？
无状态意味着每轮全量重发：第 n 轮长度约为 800 + 200n，第 10 轮 = 800 + 2000 = 2800。累计量 S(10) = Σ(800 + 200k) = 8000 + 200×55 = 19000，即 S(n) = nc + t·n(n+1)/2 = O(n²)——这就是「会话越聊越贵」的来源。第 2 个选项漏掉了前 9 轮，第 4 个选项误以为客户端只发新增内容。
6. 为什么「历史上下文不可修改」对成本这么重要？
官方机制是「请求先检查 prompt 的开头部分（prefix）是否已缓存，命中就复用；未命中就从头处理并把前缀缓存下来」，并且明确建议多轮对话「把新元素追加到 messages 数组末尾」。课件把这条总结成最佳实践：「历史上下文不可修改——不满足会导致难以命中模型服务商的 prompt cache」。第 1、2、4 条都是虚构机制。

🎯 高级测验 · 综合

7. 有人把本章调用简写成：先 resp = model.invoke_stream(session)，紧接着 session.add_message({"role": "assistant", "content": "我来整理一下"})，然后从不迭代 resp。后果是？
invoke_stream 是个生成器函数：self._client.chat.completions.create(...)、for chunk in stream、末尾的 session.add_message(msg) 全都在函数体里——不调用 next()，一行都不执行。Python 官方教程的原话是：生成器「用 yield 来返回数据，每次对它调用 next() 时，生成器从上次离开的地方继续」。所以这里既没有请求、没有回答、也没有回写，反而把一条编造的 assistant 消息塞进历史——下一轮它会作为「模型说过的话」一起发出，污染上下文（前缀也与真实对话不一致）。
8. 要同时改善「缓存命中率」与「会话持久化成本」，下面哪种改法最对？
两半分别对应两笔账。① 缓存：官方结论是把新元素追加到 messages 数组末尾、前缀保持不变才命中；截断历史（第 1 项）与改写系统提示词（第 3 项）都在动前缀——后者还违反第 16 章的「保持静态」。② 持久化：本章 save() 每轮 json.dump 整份 messages，历史长 n 时单次写入 O(n)、n 轮累计 O(n²) 的序列化与磁盘写，只是「历史只增不改」的另一面。挪到 /tmp（第 2 项）既不省这份开销，也丢了持久性。
9. 要给线上 Agent 加「会话恢复 + 历史压缩」，要求尽量不丢推理上下文、也不整段丢掉缓存。哪个方案最合理？
本章两条最佳实践正好回答这题：历史上下文不可修改（否则难以命中 prompt cache）、上下文中应保留思维链（否则推理上下文丢失、回复质量下降）。第 2 项删早期消息和第 3 项整体重写都改变了前缀，命中率归零、成本一次性回到全量；第 4 项不设上限，迟早撞上下文窗口——那时不是「重启」而是线上报错。合理做法是只追加：把摘要当成一条新消息追加，或在历史之外维护旁路摘要，原历史保持逐字不变，同时按本章 model.py 的做法把 reasoning 字段一并写回会话。
