知识速览

先花几分钟把核心机制过一遍——细节都在《24.部署-CICD》里，测验和面试会考。

CI 与 CD 的职责

  • CI 持续集成：代码提交触发——装依赖（uv sync）+ 跑测试（make test-unit，注释里的 test/test-e2e/test-smoke 按需开）+ 通知
  • CD 持续交付：构建镜像 → 推 ACR → 部署集群（kubectl + Helm）
  • 三个镜像仓库：duyi-service-ci（跑测试的环境）、duyi-service-cd（构建部署镜像的环境）、python（3.14-slim 基础镜像）

CD 的密钥与命令

  • 6 个环境变量：KUBECONFIG_BASE64（k8s 配置编码）、ACR_USERNAME/ACR_PASSWORD、DOCKER_SERVER、DB_PASSWORD、JWT_SECRET_KEY
  • 三步命令：还原 kubeconfig → 重建拉取凭证 secret（dry-run 管道 apply）→ helm 部署（TAG=${CI_COMMIT_REF_NAME}）
  • 版本纪律：image.tag=$TAG——分支名/commit 作为镜像版本，不再 latest

分级测验

即时反馈：点击选项立刻显示对错与解释。题目只考本课与《24.部署-CICD》覆盖的内容。

🌱 初级测验 · 概念

1. CI/CD 全称是？
课件开头：CI/CD 全称持续集成与持续交付——ch12 开发日常「提交 PR 后进入流水线」指的就是它。
2. CI 流水线在代码提交后做什么？
课件 CI 流水线：触发方式代码提交 → 自定义镜像源 → 执行命令 uv sync --frozen --all-packages + make test-unit（test/test-e2e/test-smoke 被注释，按需开启）→ 通知插件。
3. 为什么 CI 和 CD 用两个不同的镜像仓库？
课件三个仓库：duyi-service-ci（跑测试的环境）/ duyi-service-cd（构建部署的环境）/ python（3.14-slim 基础镜像）——流水线各阶段用各自的镜像，互不干扰，也避免测试工具污染构建产物。

🌿 中级测验 · 应用

4. CD 第一步「还原 kubeconfig」为什么用 base64？
课件：KUBECONFIG_BASE64 是 k8s config 的 base64 编码（cat ~/.kube/config | base64）——多行文本塞进流水线变量要靠编码；CD 里 echo | base64 -d > /tmp/kubeconfig 还原。
5. secret 创建命令里的 --dry-run=client -o yaml | kubectl apply -f - 是什么套路？
课件 CD 命令：kubectl create ... --dry-run=client -o yaml（生成不执行）| kubectl apply -f -（声明式应用）——流水线反复跑不报「已存在」错，幂等。
6. TAG=${CI_COMMIT_REF_NAME} 在部署里起什么作用？
课件 CD：TAG=${CI_COMMIT_REF_NAME}（流水线内置变量=分支名）→ helm --set image.tag=$TAG——镜像版本与代码版本绑定，杜绝 latest 漂移（ch22/23 反复强调的纪律在此自动化）。

🎯 高级测验 · 综合

7. CI 里 make test-e2e / test-smoke 为什么被注释掉了？
课件 CI 命令：make test-unit 生效，test/test-e2e/test-smoke 注释——单元测试秒级、每次提交必跑；e2e 起真库真服务慢，冒烟要求环境完整——按 ch12 的策略，成熟期再把红线测试接进流水线硬门禁。
8. CD 的 6 个环境变量里，哪个最危险？泄露了各会发生什么？
课件变量清单分级：KUBECONFIG_BASE64=集群管理员级权限（能删光所有服务）；ACR_PASSWORD 可 push 恶意镜像；DB_PASSWORD/JWT_SECRET_KEY 直通生产库与伪造身份。全部只存流水线密钥区（非代码库），ch02/ch21/ch23 的密钥纪律的终点。
9. 从 ch21 到 ch24，发布链路最终形态是什么？
四章递进：ch21 docker run 手工 → ch22 ACR 仓库化 → ch23 k8s/Helm 集群化 → ch24 云效流水线自动化——git push 即触发集成验证与交付部署，ch12 开发日常第 6 步「进入流水线」完整落地。
